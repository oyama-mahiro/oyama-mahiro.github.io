# 阶段4-10 TensorRT、ncnn与OpenVINO的基本定位

ONNX（Open Neural Network Exchange，开放神经网络交换格式）负责保存模型的计算图、算子、权重和输入输出信息。`.onnx`文件本身不会调度CPU、GPU或NPU执行计算，推理框架读取模型后才会完成图优化、硬件适配和实际计算。

因此，在RKNN以外的设备上部署ONNX模型时，首先要确定目标硬件及其推理框架，然后判断这个框架是直接读取ONNX，还是要求先把ONNX转换成自己的模型格式。本章只建立TensorRT、ncnn与OpenVINO的基本使用路线，不展开TensorRT插件、CUDA核函数、ncnn自定义层和各框架的量化细节。

## 1 ONNX模型在不同设备上的两种部署路径

### 1.1 推理框架直接读取ONNX模型

第一条路径是让推理框架直接读取`.onnx`文件。例如，阶段4-3和阶段4-4使用的ONNX Runtime可以直接创建ONNX推理会话；OpenVINO也可以直接读取ONNX并为指定设备编译模型。

这条路径的文件关系比较简单：

```text
model.onnx
    ↓ 推理框架读取模型
解析计算图并选择执行后端
    ↓
准备输入Tensor并执行推理
    ↓
取得输出Tensor
```

程序部署时需要同时携带ONNX文件和对应的推理库。目标机器还要安装匹配的硬件驱动；例如，使用GPU执行后端时，只有推理库而没有正确的GPU驱动，模型仍然无法在GPU上执行。

### 1.2 ONNX转换为目标框架模型后运行

第二条路径是在部署前运行目标框架的转换器或编译器，把ONNX计算图转换为更适合目标硬件执行的模型文件。板端或主机程序随后加载转换结果，不再把原始ONNX作为推理入口。

```text
model.onnx
    ↓ 目标框架的转换器或编译器
算子映射、图优化、精度选择和硬件编译
    ↓
目标框架模型文件
    ↓ 对应Runtime加载
目标设备执行推理
```

RKNN采用的就是这条路线：RKNN Toolkit2在PC上生成`.rknn`文件，RKNN Runtime在板端加载它。TensorRT通常生成Engine，ncnn通常生成`.param`与`.bin`，OpenVINO则可以生成中间表示文件。

转换后的文件通常包含框架专用的图结构、权重布局或硬件实现信息。它的通用性低于ONNX，因此必须由匹配的Runtime加载，并遵守该框架对版本、芯片和算子的要求。

### 1.3 直接加载ONNX时仍可能发生运行时编译

“直接读取ONNX”只表示用户不需要提前保存另一套模型文件。推理框架仍会在内存中处理模型。

以OpenVINO直接加载ONNX为例，实际过程为：

```text
应用程序调用compile_model()
    ↓
OpenVINO前端读取ONNX计算图
    ↓
OpenVINO转换并优化内部模型
    ↓
目标设备插件编译模型
    ↓
返回CompiledModel供程序推理
```

所以，直接加载可以减少文件转换步骤，但首次加载时间可能包含模型转换和设备编译。预先转换模型则可以把部分工作移动到部署前完成。

## 2 根据目标硬件选择推理框架与模型格式

推理框架首先由目标硬件决定。模型来自PyTorch还是其他训练框架，只影响模型如何导出；最终在哪类芯片上执行，才决定后续工具链。

| 目标设备 | 常见推理框架 | ONNX的常见处理方式 | 推理程序加载的文件 |
| --- | --- | --- | --- |
| 通用x86或ARM CPU | ONNX Runtime | 直接读取 | `.onnx` |
| NVIDIA GPU或Jetson | TensorRT | 构建TensorRT Engine | `.engine`或`.plan` |
| ARM、Android和移动端CPU/Vulkan GPU | ncnn | 使用pnnx转换 | `.ncnn.param`与`.ncnn.bin` |
| 受支持的Intel CPU、GPU、NPU | OpenVINO | 直接读取ONNX，或转换为IR | `.onnx`或`.xml`与`.bin` |
| 厂商专用NPU | 厂商编译器与Runtime | 通常转换为厂商模型 | 以厂商工具链为准 |

这里的“GPU支持”必须落实到具体厂商和具体设备。OpenVINO重点支持Intel硬件，不能据此推断它会使用任意NVIDIA或AMD独立显卡。NVIDIA GPU通常选择TensorRT或ONNX Runtime的CUDA执行后端。

确定候选框架后，再依次确认下面几件事：

1. 目标芯片、操作系统和CPU架构是否位于官方支持范围内。
2. 转换器是否支持模型使用的ONNX算子和Opset版本。
3. 框架是否支持模型的静态或动态输入形状。
4. 目标设备是否支持模型计划采用的FP32、FP16或INT8精度。
5. 应用程序使用C++还是Python，以及目标系统能否部署对应Runtime。
6. 转换产物是否绑定工具版本、驱动版本或具体硬件型号。

这套判断顺序比单独比较框架名称更重要。同一个YOLO11n ONNX在NVIDIA GPU、Intel CPU和ARM移动端上，后续格式与调用库都会发生变化。

## 3 直接使用ONNX模型的执行过程

### 3.1 ONNX Runtime执行提供器与目标设备

ONNX Runtime中的执行提供器（Execution Provider，EP）是连接通用ONNX计算图与具体计算后端的模块。CPU、CUDA、TensorRT和DirectML等后端通过不同EP接收可执行的ONNX节点。

创建推理会话时，`providers`按照优先级排列。下面的配置先尝试CUDA，剩余可执行节点再交给CPU：

```python
import onnxruntime as ort

session = ort.InferenceSession(
    "model.onnx",
    providers=[
        "CUDAExecutionProvider",
        "CPUExecutionProvider",
    ],
)

# 这里显示会话中实际启用的执行提供器及其优先顺序。
# 它不能单独证明每一个节点都已经在CUDA上执行。
print(session.get_providers())
```

`CUDAExecutionProvider`还要求目标机器具有兼容的NVIDIA驱动、CUDA相关运行库以及匹配的ONNX Runtime GPU软件包。若机器只安装了CPU版ONNX Runtime，这个EP不会凭借配置字符串自动出现。

输入、执行和输出接口与阶段4-3相同：通过`get_inputs()`确认输入接口，准备名称、形状和数据类型均匹配的NumPy数组，再调用`session.run()`。C++对应流程已在阶段4-4介绍，本节不重复完整代码。

### 3.2 算子不受支持时的构建失败与CPU回退

执行提供器只接管自己支持的节点。ONNX Runtime创建会话时会划分计算图，把不同子图交给不同EP。某个GPU EP不支持一个节点时，存在两种常见结果：

- 会话同时启用了`CPUExecutionProvider`，并且CPU内核支持该节点：这个节点可以回退到CPU执行。
- 没有可执行该节点的EP：会话创建或推理阶段报错。

CPU回退会增加CPU与GPU之间的数据传递，也可能导致模型虽然运行成功，GPU加速效果却很差。`session.get_providers()`只说明哪些EP已经注册到会话，不能说明每个节点最终分配到了哪里。需要确认节点分配时，应开启ONNX Runtime日志或性能分析功能，查看图划分和节点执行记录。ONNX Runtime执行提供器的工作方式及当前支持列表以[官方Execution Providers文档](https://onnxruntime.ai/docs/execution-providers/)为准。

## 4 TensorRT转换和运行ONNX模型的方法

### 4.1 TensorRT面向的设备与Engine模型格式

TensorRT是NVIDIA提供的深度学习推理优化与运行软件开发工具包（Software Development Kit，SDK），主要面向NVIDIA GPU。它读取训练完成的模型，选择适合目标GPU的算子实现、精度和执行策略，并生成可由TensorRT Runtime执行的Engine。

TensorRT常把序列化后的Engine称为Plan。`.engine`和`.plan`只是常见文件后缀，文件内容均由TensorRT序列化接口生成，后缀本身不改变格式。

```text
yolo11n.onnx
    ↓ ONNX Parser解析
TensorRT Network
    ↓ Builder优化和选择GPU实现
yolo11n_fp16.engine
    ↓ TensorRT Runtime加载
NVIDIA GPU执行
```

### 4.2 ONNX解析、图优化与Engine构建过程

第一次接触TensorRT时，可以使用随TensorRT提供的`trtexec`命令行工具完成ONNX解析、Engine构建和基础性能测试。下面以固定输入的YOLO11n为例：

```bash
# --onnx指定源模型，--saveEngine指定生成文件。
# --fp16允许Builder在目标GPU支持时选择FP16实现。
trtexec \
  --onnx=yolo11n.onnx \
  --saveEngine=yolo11n_fp16.engine \
  --fp16
```

`--fp16`表示允许使用FP16，并不保证每一层都采用FP16。Builder会根据GPU支持情况和可用实现选择各层执行精度。

如果ONNX输入包含动态高度和宽度，Builder需要知道允许构建的形状范围。下面假设模型输入名为`images`；实际名称必须通过Netron或ONNX Runtime的`get_inputs()`确认：

```bash
# minShapes：Engine允许的最小输入形状。
# optShapes：Builder重点优化的常用形状。
# maxShapes：Engine允许的最大输入形状。
trtexec \
  --onnx=yolo11n_dynamic.onnx \
  --saveEngine=yolo11n_dynamic_fp16.engine \
  --fp16 \
  --minShapes=images:1x3x320x320 \
  --optShapes=images:1x3x640x640 \
  --maxShapes=images:1x3x1280x1280
```

后续输入必须位于这个范围内。例如，`1×3×640×640`可以使用该Engine，`1×3×1600×1600`超出了最大形状，执行上下文无法为它建立有效输入形状。

`trtexec`内部对应的核心模块是ONNX Parser、Builder、BuilderConfig和序列化接口。项目需要更细致地控制工作空间、动态形状或精度时，可以改用TensorRT C++或Python Builder API。当前阶段先掌握`ONNX → Engine`的输入输出关系即可。NVIDIA给出的ONNX转换路线和`trtexec`用法可参考[TensorRT官方ONNX部署文档](https://docs.nvidia.com/deeplearning/tensorrt/latest/getting-started/quick-start-onnx-deployment.html)。

### 4.3 TensorRT Runtime加载Engine并执行推理

程序得到Engine后，Runtime阶段不再需要ONNX Parser和Builder。主要对象与作用如下：

| TensorRT对象或接口 | 作用 |
| --- | --- |
| `IRuntime` | 反序列化磁盘中的Engine数据 |
| `ICudaEngine` | 保存已构建模型，并提供输入输出名称、形状和类型信息 |
| `IExecutionContext` | 保存一次或一条推理执行流所需的动态状态 |
| `setInputShape()` | 为动态输入设置本次实际形状 |
| `setTensorAddress()` | 把输入输出名称与GPU缓冲区地址关联 |
| `enqueueV3()` | 将模型计算提交到指定CUDA Stream |

完整执行顺序为：

```text
读取Engine文件到内存
    ↓
IRuntime反序列化并得到ICudaEngine
    ↓
ICudaEngine创建IExecutionContext
    ↓
设置动态输入形状并查询实际输出形状
    ↓
为输入输出分配GPU内存并绑定地址
    ↓
把输入从CPU内存传到GPU内存
    ↓
enqueueV3()提交推理
    ↓
把需要的输出传回CPU并等待CUDA Stream完成
```

这里的输入输出地址通常指CUDA设备内存。OpenCV读取的图像位于CPU内存，程序仍需完成预处理，并通过CUDA内存复制或其他受支持的数据通路把输入交给GPU。TensorRT Runtime的详细接口及执行上下文关系可参考[官方Runtime说明](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/capabilities.html#runtime-phase)。

### 4.4 TensorRT Engine的版本、硬件与动态形状限制

TensorRT Engine包含Builder为特定环境选出的GPU实现。默认情况下，Engine与TensorRT版本、运行平台和构建它的GPU环境存在兼容关系。TensorRT提供版本兼容和硬件兼容配置，但这些配置有明确限制，不能把Engine视为跨设备通用模型。

实际项目中更稳妥的方式是保存原始ONNX和构建命令，在目标GPU或与目标环境匹配的构建机器上重新生成Engine。若模型使用了额外插件，运行环境还必须提供匹配的插件库，否则Engine可能无法反序列化或执行。

动态形状的有效范围也在构建阶段确定。运行时可以在已构建范围内选择具体尺寸，无法临时扩大Engine的最大输入范围；需要更大尺寸时必须重新构建Engine。

## 5 ncnn转换和运行ONNX模型的方法

### 5.1 ncnn面向的设备与模型文件组成

ncnn是腾讯开源的轻量级神经网络推理框架，主要用于移动端和嵌入式设备。它提供纯C++推理接口，能够在CPU上运行，也可以在构建并启用Vulkan后使用受支持的GPU。

它的大致使用范围包括Android设备、树莓派及普通ARM Linux板卡，以及缺少可用NPU工具链而改用CPU或Vulkan GPU推理的嵌入式系统；在RK3588上，ncnn可以作为CPU或Vulkan GPU方案，瑞芯微NPU仍由RKNN调用。

ncnn常用模型由两个文件组成：

- `.ncnn.param`保存网络层、连接关系和层参数。
- `.ncnn.bin`保存模型权重。

程序部署时两个文件需要一起携带。只加载`.param`只能得到结构信息，缺少`.bin`中的权重后无法完成正常推理。

### 5.2 使用pnnx将ONNX转换为ncnn模型

pnnx（PyTorch Neural Network Exchange）是ncnn项目当前使用的模型转换工具。对于已经导出的ONNX，可以直接执行：

```bash
# 安装pnnx后，命令行会提供同名转换程序。
python3 -m pip install pnnx

# pnnx读取ONNX并生成ncnn模型文件。
pnnx yolo11n.onnx
```

成功后，当前目录会产生类似下面的文件：

```text
yolo11n.ncnn.param
yolo11n.ncnn.bin
```

转换产生的具体文件名以终端输出为准。如果ONNX带有动态形状，pnnx可能需要通过`inputshape`等参数取得明确的样例形状，具体写法应以当前pnnx版本帮助信息和模型输入为准。

如果手中仍有原始PyTorch模型，ncnn官方当前更推荐通过pnnx直接从PyTorch或TorchScript进入ncnn格式，可以减少ONNX中间算子带来的兼容问题。已经只有ONNX时，继续使用`pnnx model.onnx`即可。相关路线与当前工具说明见[ncnn官方PyTorch与ONNX转换指南](https://github.com/tencent/ncnn/wiki/use-ncnn-with-pytorch-or-onnx)。

### 5.3 使用ncnn C++接口加载模型并执行推理

ncnn C++程序包含`net.h`并链接ncnn库。`ncnn::Net`保存加载后的网络，`ncnn::Extractor`表示从这张网络创建的一次推理提取器，`ncnn::Mat`保存输入或输出数据。

下面代码只展示ncnn核心调用。`input_tensor`应当由程序提前按照模型要求完成尺寸调整、通道顺序转换、归一化和数据排布；输入输出名称也必须以转换后的ncnn模型为准。

```cpp
#include <net.h>

#include <iostream>

int run_ncnn(const ncnn::Mat& input_tensor)
{
    ncnn::Net network;

    // 如果目标程序已经正确构建Vulkan版ncnn，并且设备支持Vulkan计算，
    // 可以在加载模型前启用该选项。仅使用CPU时保持false。
    network.opt.use_vulkan_compute = false;

    // load_param()读取网络结构。返回非0表示路径、格式或内容存在问题，
    // 此时网络尚未完整加载，调用方不应继续执行推理。
    if (network.load_param("yolo11n.ncnn.param") != 0) {
        std::cerr << "load ncnn param failed\n";
        return -1;
    }

    // load_model()读取与param匹配的权重。param和bin必须来自同一次转换。
    if (network.load_model("yolo11n.ncnn.bin") != 0) {
        std::cerr << "load ncnn weights failed\n";
        return -1;
    }

    // Extractor保存本次推理的输入和中间状态。
    // 多次推理可以为每次输入重新创建Extractor，已加载的network继续复用。
    ncnn::Extractor extractor = network.create_extractor();

    // "in0"只是常见示例名称。这里必须改成转换后模型的真实输入名称。
    // input_tensor的宽、高、通道数和数值处理也必须与该入口一致。
    if (extractor.input("in0", input_tensor) != 0) {
        std::cerr << "set ncnn input failed\n";
        return -1;
    }

    ncnn::Mat output_tensor;

    // extract()执行到指定输出节点并把结果写入output_tensor。
    // "out0"同样需要替换为转换后模型的真实输出名称。
    if (extractor.extract("out0", output_tensor) != 0) {
        std::cerr << "extract ncnn output failed\n";
        return -1;
    }

    std::cout << "output dims=" << output_tensor.dims
              << ", w=" << output_tensor.w
              << ", h=" << output_tensor.h
              << ", c=" << output_tensor.c << '\n';
    return 0;
}
```

程序先加载结构和权重，然后为当前输入创建`Extractor`。`input()`把输入交给模型入口，`extract()`触发必要计算并取得指定出口。ncnn不会根据原ONNX文件自动替这段程序完成图像预处理，输入名称、尺寸、通道顺序和数值范围都要由应用程序与转换后的模型保持一致。

## 6 OpenVINO直接运行和转换ONNX模型的方法

### 6.1 OpenVINO支持的目标设备与设备插件

OpenVINO是Intel提供的模型优化与推理工具链，主要面向受支持的Intel CPU、Intel集成或独立GPU以及Intel NPU。它通过设备插件把统一模型交给具体硬件编译和执行。

常用设备名称包括：

- `CPU`：使用OpenVINO CPU插件。
- `GPU`：使用系统中受支持的Intel GPU插件。
- `NPU`：使用受支持的Intel NPU插件。
- `AUTO`：由OpenVINO根据当前可用设备选择执行设备。

设备名称只表达希望使用的插件。目标系统还必须安装匹配的驱动和OpenVINO Runtime，并且模型中的算子需要被该设备插件支持。可以通过`ov.Core().available_devices`查看当前Runtime实际识别到的设备。

### 6.2 直接加载ONNX与预先转换为IR的区别

OpenVINO支持两种入口。

第一种方式直接把ONNX交给`compile_model()`：

```python
import openvino as ov

core = ov.Core()

# OpenVINO读取ONNX，并在本次程序启动过程中为CPU编译模型。
compiled_model = core.compile_model("yolo11n.onnx", "CPU")
```

第二种方式在部署前使用OpenVINO模型转换器`ovc`生成中间表示（Intermediate Representation，IR）：

```bash
# 生成yolo11n.xml和与之配套的yolo11n.bin。
ovc yolo11n.onnx --output_model yolo11n.xml
```

IR由两个文件组成：

- `.xml`保存OpenVINO模型结构和算子属性。
- `.bin`保存模型常量与权重。

转换为IR后，推理程序把模型路径改为`yolo11n.xml`：

```python
import openvino as ov

core = ov.Core()

# Runtime读取IR后仍会针对CPU插件编译模型。
compiled_model = core.compile_model("yolo11n.xml", "CPU")
```

两种方式最终都会得到`CompiledModel`。直接读取ONNX更方便，适合先验证模型；预先转换IR可以提前完成模型前端转换，适合希望降低模型首次读取开销或固定部署输入格式的项目。IR加载后仍需要针对`CPU`、`GPU`或`NPU`完成设备编译。

OpenVINO当前对ONNX直接读取与IR转换的官方说明见[Converting an ONNX Model](https://docs.openvino.ai/nightly/openvino-workflow/model-preparation/convert-model-onnx.html)。

### 6.3 使用OpenVINO Runtime编译模型并执行推理

`CompiledModel`提供模型编译后的输入输出端口。`create_infer_request()`创建一次推理请求，`infer()`接收输入并返回由输出端口索引的结果。

下面代码假设`input_data`已经是符合模型要求的NumPy数组。对于常见固定输入YOLO模型，它可能是形状`[1, 3, 640, 640]`、类型`float32`的NCHW数据；最终必须以`input_port.shape`和`input_port.element_type`为准。

```python
import numpy as np
import openvino as ov


def run_openvino(input_data: np.ndarray) -> np.ndarray:
    """加载ONNX，在Intel CPU上执行一次推理，并返回第0个原始输出。"""
    core = ov.Core()

    # compile_model()负责读取ONNX、优化内部计算图并为CPU插件编译模型。
    # 如果模型算子或输入形状不被支持，异常会在这里出现，程序不应继续推理。
    compiled_model = core.compile_model("yolo11n.onnx", "CPU")

    input_port = compiled_model.input(0)
    output_port = compiled_model.output(0)

    # 推理前核对应用程序真正提交的数据，避免模型可以运行但输入含义错误。
    print("model input shape:", input_port.shape)
    print("application input shape:", input_data.shape)
    print("application input dtype:", input_data.dtype)

    infer_request = compiled_model.create_infer_request()

    # 字典键使用模型的输入端口，值为该端口对应的NumPy数组。
    # infer()同步执行；返回时result已经包含本次推理产生的输出。
    result = infer_request.infer({input_port: input_data})

    # output_port明确指定读取第0个图输出，返回的仍是模型原始Tensor。
    # YOLO框解析、置信度筛选和NMS属于后处理，不在本节展开。
    return result[output_port]
```

如果使用IR，只需要把`compile_model()`的模型路径改为`yolo11n.xml`，后续查询输入、创建请求和取得输出的流程不变。C++接口具有相同对象关系：`ov::Core`编译模型，`ov::CompiledModel`创建`ov::InferRequest`，推理请求设置输入Tensor后执行`infer()`。

## 7 三类框架从模型文件到原始输出的调用关系

三类框架的具体API不同，但模型文件必须交给与它匹配的Runtime：

| 模型文件 | 负责加载的框架 | 初始化阶段 | 单次推理阶段 |
| --- | --- | --- | --- |
| `.onnx` | ONNX Runtime | 创建`InferenceSession` | `run()` |
| TensorRT `.engine`或`.plan` | TensorRT Runtime | 反序列化Engine并创建Execution Context | 绑定GPU地址并调用`enqueueV3()` |
| ncnn `.param`与`.bin` | ncnn | `Net::load_param()`与`load_model()` | `Extractor::input()`与`extract()` |
| OpenVINO `.onnx`或IR | OpenVINO Runtime | `Core::compile_model()` | `InferRequest::infer()` |
| `.rknn` | RKNN Runtime | `rknn_init()` | 输入、`rknn_run()`与输出 |

应用程序的共同主线可以固定为：

```text
初始化Runtime并加载模型
    ↓
查询输入输出数量、名称、形状和数据类型
    ↓
把业务数据转换为模型要求的输入Tensor
    ↓
提交推理
    ↓
取得模型原始输出Tensor
    ↓
交给业务后处理
```

框架只负责自己模型入口与出口之间的计算。图像解码、缩放、颜色转换、归一化以及YOLO检测框解析是否包含在模型内部，要根据实际计算图判断。更换推理框架时，模型输入的shape、dtype、layout和数值范围仍然需要逐项确认。

## 8 其他厂商设备的ONNX部署路线判断方法

遇到新的NPU、DSP或其他专用加速器时，可以沿用前面的两条部署路径，不需要先记忆大量厂商API。先查看厂商提供的模型转换工具、板端Runtime和官方模型示例，再回答下面几个问题：

1. **Runtime是否直接读取ONNX**：如果可以，继续确认它是在启动时编译，还是只支持一个受限的ONNX算子子集。
2. **是否要求离线转换**：记录转换器输入的ONNX版本、目标芯片参数以及生成文件后缀。
3. **转换在哪里进行**：有些工具在x86 Linux主机上运行，有些编译过程要求目标GPU或特定驱动参与。
4. **转换结果由谁加载**：找到板端Runtime的头文件、动态库、初始化接口和推理接口，不能把厂商模型交给ONNX Runtime直接读取。
5. **转换产物绑定哪些环境**：查清它是否与芯片型号、Runtime版本、驱动版本或操作系统架构绑定。
6. **输入输出是否发生变化**：转换器可能调整布局、数据类型、输出数量或量化参数，板端程序应以转换后模型的查询结果为准。
7. **量化由哪个阶段完成**：部分工具读取浮点ONNX并在厂商编译器中校准量化，部分工具接收已经量化的ONNX；两者需要的校准数据和模型格式不同。

例如，一块新板卡的官方资料如果同时提供“模型转换工具”和“板端Runtime”，其基本关系通常为：

```text
训练框架导出ONNX
    ↓ PC端厂商转换工具
生成目标芯片模型
    ↓ 板端应用链接厂商Runtime
加载模型、提交输入并取得输出
```

如果官方只提供ONNX Runtime执行提供器，程序则可以继续加载`.onnx`，由该执行提供器接管支持的计算节点。最终应优先采用芯片厂商明确维护的工具链和支持矩阵，因为算子覆盖、驱动关系及模型兼容范围都会随软件版本变化。
