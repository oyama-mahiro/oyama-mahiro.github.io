# 阶段2-7 编码基础

视频编码器接收连续的原始视频帧，输出由编码数据包组成的压缩码流。编码器压缩视频的基本方法是：先预测当前图像内容，只编码预测结果与原始图像之间的差异，再通过量化降低这些差异的表示精度。实际工程还要同时控制画质、平均码率、瞬时峰值和编码延迟。

本阶段主要讨论 H.264/AVC 和 H.265/HEVC。H.264 的英文全称是 Advanced Video Coding，H.265 的英文全称是 High Efficiency Video Coding。二者的具体块结构和码流语法存在差异，但“预测、残差、变换、量化、熵编码、内部重建”的主流程相通。

## 1 原始视频帧与编码数据包的区别

原始视频帧（raw frame）保存一幅图像的像素采样值。例如，阶段2-1介绍的 1920×1080、8位 YUV420P 图像在不考虑行对齐时占用：

```text
1920 × 1080 × 1.5 = 3,110,400字节
```

以每秒30帧计算，原始视频的数据量约为：

```text
3,110,400 × 30 × 8 = 746,496,000 bit/s，约746.5 Mbit/s
```

编码数据包（encoded packet）保存压缩后的码流数据，包括预测方式、参考信息、量化后的残差以及解码所需的语法元素。编码后若平均码率为 4 Mbit/s，每秒只需要传输约 0.5 MB 数据，远小于原始视频。

帧与包不能按编号机械地一一对应：

- 编码器可能暂存多帧，完成帧类型选择或 B 帧重排后才输出数据包。
- 一张编码图像可以由多个条带（slice）组成，并分布在多个包中。
- 容器或网络协议还可能把一份编码数据继续拆分或重新组合。
- 某些包只携带 SPS、PPS、VPS 或补充增强信息，不代表一张可显示图像。

因此，应用程序需要分别维护原始帧和编码包的元数据。原始帧重点关注像素格式、宽高、平面地址和 stride；编码包重点关注数据长度、关键帧标记、时间戳和码流格式。时间戳及显示、解码顺序将在阶段2-8集中说明。

## 2 H.264与H.265编码器的内部工作流程

编码器压缩视频时，真正要解决的问题是：**怎样用尽量少的信息，让解码器重建出与原始图像足够接近的结果。**

如果直接把每个像素写入码流，数据量几乎没有减少。编码器先根据已经重建的图像内容生成一份预测，只记录预测方式和预测没有覆盖的差异。随后，编码器主动舍弃一部分人眼不敏感的差异精度，再把剩余信息写成紧凑的二进制码流。

整个过程存在两条相互连接的路径：

```text
原始图像块
→ 生成若干候选预测块并选择一种预测方式
→ 原始块减去预测块，得到残差
→ 对残差进行变换和量化
→ 得到量化系数
   ├─ 熵编码预测信息和量化系数 → 组成NAL单元 → 输出码流
   └─ 反量化和反变换 → 加回预测块 → 得到重建块 → 保存为参考
```

解码器只执行右侧信息能够确定的操作：读取预测方式、重新生成预测块、解码量化系数、反量化、反变换，再把重建残差加回预测块。编码器内部的候选搜索和模式比较不会写入码流，解码器也不需要重新搜索。

下面用一组连续的简化数据解释每一步的输入、作用、实现方法和输出。示例使用2×2小块便于手算；H.264/H.265实际使用标准规定的块尺寸、整数变换、预测模式和语法。

### 2.1 图像分块与帧内、帧间预测

#### 为什么要先分块

编码器拿到的是一张包含全部真实像素的完整图像。它需要分别预测平坦区域、纹理边缘和不同运动区域，因此先把整张图像划分为较大的基本处理块，再决定这些大块是否继续拆成较小的块。每个较小块可以独立选择预测方法，从而让预测结果更接近该局部区域的真实像素。

H.264中的关系可以先理解为：

```text
完整图像
→ 划分成16×16亮度像素的宏块
→ 宏块可以继续划分
→ 得到实际执行预测的较小块
```

宏块（macroblock）是H.264组织编码数据的基本大块。一个宏块不代表最终只能进行一次预测。例如，一个16×16宏块可以整体采用16×16帧内预测，也可以拆成多个4×4或8×8亮度块，让每个小块分别选择预测模式。帧间预测时还可以采用16×16、16×8、8×16、8×8及更小的分区描述不同局部运动。

H.265把对应的大块称为编码树单元（Coding Tree Unit，CTU），再使用树形划分得到更小的编码单元、预测单元和变换单元。术语和划分方式虽然不同，但层级关系相同：

```text
大块负责组织和递归划分
→ 较小的预测块负责生成预测像素
→ 变换块负责处理预测后得到的残差
```

大块适合内容平坦或运动一致的区域，因为要记录的块边界和模式信息较少。小块能更贴合边缘或局部运动，预测通常更准确，但每个小块都需要额外记录划分、模式或运动信息。编码器会把“大块直接预测”和“继续拆成小块分别预测”都作为候选，最后根据编码代价作出选择。

#### 帧内预测怎样生成预测块

帧内预测（intra prediction）只在当前帧内部取参考像素。编码器实际拥有待编码块的真实值，但在生成预测块时会在逻辑上屏蔽这些真实值，也就是禁止预测器读取它们。预测器只能读取解码器届时同样拥有的像素，通常是当前块上方、左侧和左上方已经编码并重建的边缘像素。

这里使用的是相邻块边缘上的一排或一列参考像素，不是分析周围整块包含什么物体或纹理。假设当前要预测中间的2×2块：

```text
                上方已重建像素
                    100  101
                       ↓
左侧已重建像素 102 → [ ?    ? ]
                 103 → [ ?    ? ]
                        当前块真实值暂时不参与预测
```

编码器按照标准允许的模式，把这些边缘参考像素复制、求平均或沿某个角度延伸到问号区域，从而产生多个候选预测块。例如：

```text
垂直模式：复制上方像素       水平模式：复制左侧像素

100  101                       102  102
100  101                       103  103

DC模式：使用相邻参考像素的平均值

102  102
102  102
```

角度模式会沿左上到右下、右上到左下等方向选取或插值参考像素，适合预测具有方向性的边缘。Planar模式会根据上方和左侧参考像素生成平滑变化的预测面，适合渐变区域。

帧内模式数量还与标准和预测块大小有关：

- H.264的4×4亮度块有9种模式，8×8亮度块也有9种模式，包括DC、垂直、水平和6种斜向模式。
- H.264的16×16亮度块有4种模式：垂直、水平、DC和平面预测。
- H.265的亮度帧内预测共有35种模式：Planar、DC和33种角度模式，水平与垂直包含在角度模式中。

编码器通常会先快速计算多个允许模式的预测误差，淘汰明显不合适的候选，再对剩余候选执行更完整的编码测试。标准规定可用模式和码流表示方法，没有要求每种编码器必须用相同的搜索顺序或把全部候选完整编码一遍。

#### 帧内预测怎样选择最终模式

编码器知道当前块的真实像素，因此可以把每个候选预测块与真实块进行比较。假设当前真实块为：

```text
104  105
106  103
```

编码器会分别测试垂直、水平、DC和允许的角度模式。每种模式都会产生一个候选预测块，候选预测块与真实块相减后得到候选残差。预测越接近真实值，候选残差通常越小。

编码器还要计算预测模式和残差需要占用多少比特。只比较像素误差容易偏向复杂模式，因为复杂模式可能预测得更准确，但描述模式和残差也可能需要更多比特。常用的综合判断是率失真代价：

```text
J = D + λ × R
```

- `D`是使用该模式编码并重建后产生的失真，例如原始块与重建块的平方误差。
- `R`是该模式预计占用的比特数，包括块划分、预测模式、运动信息和残差系数。
- `λ`是码率与失真之间的权重，编码器会结合QP等条件确定它。
- `J`是候选模式的总代价，编码器选择代价较小的模式。

例如：

```text
垂直模式：D = 10，R = 20 bit
水平模式：D = 14，R = 12 bit

假设λ = 1：
垂直模式J = 10 + 1×20 = 30
水平模式J = 14 + 1×12 = 26
```

垂直模式的预测误差更小，水平模式的总代价更低，因此编码器选择水平模式。最终只有选中的模式和对应残差进入码流，其他候选只在编码器内部用于比较。

#### 帧间预测怎样生成和选择预测块

帧间预测（inter prediction）仍然要预测当前帧中的一个真实块，并把候选预测块与真实块比较。它与帧内预测的主要区别是候选预测块的来源：帧内预测使用当前帧的相邻重建像素；帧间预测从一张或多张已经重建的参考帧中取得同样大小的候选区域。

假设当前待编码块左上角位于坐标`(100, 50)`，编码器可以先检查上一参考帧中的相同位置，再检查该位置周围的其他位置：

```text
当前帧待编码块的位置：(100, 50)

上一参考帧中的候选区域：
(100, 50)  相同位置，运动矢量为(0, 0)
( 96, 50)  左移4个像素，运动矢量为(-4, 0)
(104, 52)  右移4个像素并下移2个像素，运动矢量为(4, 2)
……
```

相同位置本身会参与比较。编码器也可以保存多张参考帧，例如第9帧、第8帧和第6帧，然后在每张参考帧的搜索范围内寻找候选区域。P帧通常从时间上较早的一张或多张参考帧取候选；B帧还可以从两个时间方向的参考帧取候选，并组合两个预测结果。

帧间预测没有套用前面所说的水平、垂直、DC等帧内模式。它比较的候选组合主要包括：

```text
选择哪一张参考帧
+ 选择参考帧中的哪个位置
+ 使用哪种块划分
+ P帧使用单向预测，或B帧使用单向、双向预测
```

对每个候选组合，编码器同样生成预测块、与当前真实块相减得到残差，再计算率失真代价`J = D + λ × R`。其中`R`还要计入参考帧编号、运动矢量和块划分所需的比特。编码器最终选择代价最低的组合，并把参考帧编号、运动信息、块划分和残差写入码流。

解码器不需要重新搜索。它读取参考帧编号和运动矢量后，从自己的参考帧缓冲区取出相同区域，便能生成与编码器一致的预测块。

经过这一步，编码器得到两个输出：一份能够被解码器复现的预测方式，以及该方式生成的预测块。下一步只处理预测块仍未覆盖的像素差异。

### 2.2 预测残差、变换与量化

#### 残差块是怎样形成的

编码器在2.1节选出最终预测块后，将当前真实块与预测块逐像素相减，得到残差块：

$$
R=C-P
$$

其中，$C$是当前真实块，$P$是预测块，$R$是残差块。反过来可以写成：

$$
C=P+R
$$

假设当前真实块和选中的预测块为：

$$
C=\begin{bmatrix}
104 & 105\\
106 & 103
\end{bmatrix},\qquad
P=\begin{bmatrix}
100 & 101\\
102 & 103
\end{bmatrix}
$$

逐个位置相减：

$$
R=C-P=
\begin{bmatrix}
104-100 & 105-101\\
106-102 & 103-103
\end{bmatrix}
=
\begin{bmatrix}
4 & 4\\
4 & 0
\end{bmatrix}
$$

残差块保存预测没有表达出来的像素差异。编码器不再重复发送整个真实块，而是发送“如何生成预测块”的信息，以及经过压缩的残差。解码器先生成相同的预测块，再加上解码得到的残差，便能重建当前块。

如果预测非常准确，残差中的数值会很小，并且会出现大量零值。此时需要编码的信息较少。预测仍有误差时，编码器接下来要进一步整理和压缩这个残差块。

#### 为什么要把残差变换成频率系数

残差矩阵中的每个元素原本对应一个像素位置。例如`R[0,0]=4`只说明左上角位置相差4。相邻位置的残差经常很接近，这些数值之间存在重复关系。如果直接逐个编码，编码器没有充分利用这种相关性。

变换会把“每个位置分别相差多少”改写成“这个残差块包含多少种变化模式”。变换后的系数矩阵通常按下面的方式解释：

- 左上区域是低频系数，表示整块共同变化或缓慢变化的强度。
- 越向右，越强调水平方向上更快的变化。
- 越向下，越强调垂直方向上更快的变化。
- 右下区域同时表示水平和垂直方向上的快速变化。

这里的“频率”表示数值在块内随位置变化得有多快，不表示每秒变化多少次。一个残差块中的数值几乎相同时，它主要由低频成分组成；相邻位置正负快速交替时，它包含较强的高频成分。

变换本身只更换描述方式。在不执行量化且计算精度足够时，逆变换可以恢复原残差。它对压缩有用，是因为自然图像经过预测后，残差通常仍具有局部相关性，变换能够把分散在多个位置的共同变化集中到少量低频系数中。其他系数会变小，后续量化便能把其中许多值归零。

例如，一个完全相同的残差块：

$$
R=\begin{bmatrix}
4 & 4\\
4 & 4
\end{bmatrix}
$$

经过后面介绍的简化变换会得到：

$$
T=\begin{bmatrix}
16 & 0\\
0 & 0
\end{bmatrix}
$$

原来四个位置都有非零值，变换后只剩一个非零系数。这就是变换为量化和熵编码创造的有利形式。

#### 系数矩阵中的每个值是怎样得到的

为了便于手算，先使用四个2×2基础算子分析残差块。这些是教学用的简化算子，不是H.264/H.265标准中的实际变换矩阵。

整体共同变化算子为：

$$
B_{00}=\begin{bmatrix}
1 & 1\\
1 & 1
\end{bmatrix}
$$

左右变化、上下变化和对角交错变化算子分别为：

$$
B_{01}=\begin{bmatrix}
1 & -1\\
1 & -1
\end{bmatrix},\qquad
B_{10}=\begin{bmatrix}
1 & 1\\
-1 & -1
\end{bmatrix},\qquad
B_{11}=\begin{bmatrix}
1 & -1\\
-1 & 1
\end{bmatrix}
$$

每个算子都与残差矩阵对应位置相乘，再把四个乘积相加，得到一个系数。对于：

$$
R=\begin{bmatrix}
4 & 4\\
4 & 0
\end{bmatrix}
$$

四个系数分别为：

$$
\begin{aligned}
T_{00}&=4\times1+4\times1+4\times1+0\times1=12\\
T_{01}&=4\times1+4\times(-1)+4\times1+0\times(-1)=4\\
T_{10}&=4\times1+4\times1+4\times(-1)+0\times(-1)=4\\
T_{11}&=4\times1+4\times(-1)+4\times(-1)+0\times1=-4
\end{aligned}
$$

把四个结果放回对应位置，就得到系数矩阵：

$$
T=\begin{bmatrix}
12 & 4\\
4 & -4
\end{bmatrix}
$$

$T_{00}=12$说明该残差块主要含有整体共同变化。其余三个系数表示左右、上下和对角交错变化的强度。系数的绝对值越大，代表对应变化模式越强；正负号表示该模式的方向关系。

#### 为什么可以写成H乘以R再乘以H的转置

上面的四个二维算子都能拆成两个一维向量的外积。先定义两条一维规则：

$$
h_0=\begin{bmatrix}1&1\end{bmatrix},\qquad
h_1=\begin{bmatrix}1&-1\end{bmatrix}
$$

$h_0$将两个相邻值相加，用来提取共同部分；$h_1$将两个相邻值相减，用来提取差异部分。

将它们两两组合：

$$
\begin{aligned}
B_{00}&=h_0^T h_0,& B_{01}&=h_0^T h_1,\\
B_{10}&=h_1^T h_0,& B_{11}&=h_1^T h_1
\end{aligned}
$$

例如：

$$
h_0^T h_1=
\begin{bmatrix}1\\1\end{bmatrix}
\begin{bmatrix}1&-1\end{bmatrix}
=
\begin{bmatrix}
1&-1\\
1&-1
\end{bmatrix}
=B_{01}
$$

把`h0`和`h1`作为矩阵`H`的两行：

$$
H=\begin{bmatrix}
1&1\\
1&-1
\end{bmatrix}
$$

矩阵乘法：

$$
T=HRH^T
$$

会自动枚举`H`的所有行组合：

$$
T=HRH^T=
\begin{bmatrix}
h_0Rh_0^T & h_0Rh_1^T\\
h_1Rh_0^T & h_1Rh_1^T
\end{bmatrix}
$$

四个位置依次对应$B_{00}$、$B_{01}$、$B_{10}$和$B_{11}$。

因此，$HRH^T$没有省略四个算子。它先用$H$沿一个方向处理残差，再用$H^T$沿另一个方向处理结果，把四个二维算子的计算合并到一次矩阵表达中。

这种二维算子能够拆成“一个竖直方向的一维向量 × 一个水平方向的一维向量”的性质，称为**可分离结构**。只有当一组二维算子都能由同一组一维规则两两组合出来时，才可以使用这种形式。任意一组彼此无关的二维算子无法直接合并成同一个$HRH^T$。

把前面的残差代入：

$$
H=\begin{bmatrix}
1&1\\
1&-1
\end{bmatrix},\qquad
R=\begin{bmatrix}
4&4\\
4&0
\end{bmatrix}
$$

$$
T=HRH^T=\begin{bmatrix}
12&4\\
4&-4
\end{bmatrix}
$$

它与四个二维算子分别计算得到的结果完全相同。

#### 离散余弦变换与编码中的整数变换

##### DCT解决什么问题

一组离散数据最直接的表示方法，是记录每个位置的数值。例如：

$$
x=\begin{bmatrix}4&4&4&0\end{bmatrix}
$$

这种表示告诉我们每个位置是多少，却没有直接说明这些数值包含多少“整体相同”、多少“缓慢变化”和多少“快速变化”。离散余弦变换（Discrete Cosine Transform，DCT）把按位置记录的数据改写成按变化模式记录的数据：

$$
\text{位置数值}\quad\xrightarrow{\mathrm{DCT}}\quad\text{不同频率模式的系数}
$$

DCT不会直接减少数据。输入有$N$个数，输出仍有$N$个系数；未量化时可以通过逆变换恢复原数据。它对压缩有用，是因为图像和预测残差中的相邻数值通常比较接近。经过DCT后，共同变化往往集中到少量低频系数，其余系数变得较小，后续量化便可以把许多小系数归零。

任意可逆变换都能把数据换一种形式表示，但随机选择的变换不一定能集中图像信息。DCT采用从低频到高频的余弦模式，这些模式与图像局部平滑、相邻值相关的特点比较匹配，所以通常能够产生少量大系数和大量小系数。

##### DCT与傅里叶变换的关系

傅里叶变换的基本思想是用不同频率的波形组合表示信号。离散傅里叶变换（Discrete Fourier Transform，DFT）处理离散输入，使用复指数作为基础模式，结果通常包含复数，并通过幅度和相位描述各个频率。

DCT采用相同的频率分解思想，但只使用余弦模式，输出为实数。DCT-II还可以理解为：先把有限长度输入在边界处做偶对称延拓，再对延拓后的数据进行DFT，最后取得对应的余弦部分。偶对称延拓可以减小块边界处的突变，因此DCT通常比直接对原始图像块做DFT更容易把能量集中到低频系数。

两者的关系可以概括为：

- DFT使用正弦和余弦共同描述频率，还保留相位信息。
- DCT只使用余弦模式，结果为实数。
- 图像块压缩关心能否把主要信息集中到少数系数，DCT在这方面通常很有效。

##### 一维DCT怎样计算

图像编码中通常讨论第二型离散余弦变换（DCT-II）。对于$N$个输入值$x[0],x[1],\ldots,x[N-1]$，第$k$个系数为：

$$
X[k]=\alpha(k)\sum_{n=0}^{N-1}
x[n]\cos\left[\frac{\pi}{N}\left(n+\frac{1}{2}\right)k\right]
$$

其中：

$$
\alpha(k)=
\begin{cases}
\sqrt{\dfrac{1}{N}}, & k=0,\\[6pt]
\sqrt{\dfrac{2}{N}}, & k>0
\end{cases}
$$

$n$表示输入位置，$k$表示频率模式编号，二者都从0取到$N-1$。计算顺序如下：

1. 固定一个模式编号$k$。
2. 用余弦公式计算该模式在各输入位置上的权重。
3. 每个输入$x[n]$乘以对应权重。
4. 将所有乘积相加，再乘归一化系数$\alpha(k)$，得到$X[k]$。
5. 依次计算$k=0$到$N-1$，得到全部$N$个系数。

$k=0$时所有位置的权重相同，得到DC系数，表示整组数据的共同部分。$k$越大，权重正负变化越快，对应更高频率的AC系数。

##### 一维DCT计算示例

继续使用：

$$
x=\begin{bmatrix}4&4&4&0\end{bmatrix},\qquad N=4
$$

把$k=0,1,2,3$代入公式，得到4组余弦权重。将它们按行排列，可以写成DCT变换矩阵：

$$
C\approx
\begin{bmatrix}
0.5000 & 0.5000 & 0.5000 & 0.5000\\
0.6533 & 0.2706 & -0.2706 & -0.6533\\
0.5000 & -0.5000 & -0.5000 & 0.5000\\
0.2706 & -0.6533 & 0.6533 & -0.2706
\end{bmatrix}
$$

用$C$乘输入列向量：

$$
X=Cx^T
\approx
\begin{bmatrix}
6\\
2.6131\\
-2\\
1.0824
\end{bmatrix}
$$

例如，第0行计算：

$$
X[0]=4\times0.5+4\times0.5+4\times0.5+0\times0.5=6
$$

第1行计算：

$$
X[1]\approx
4\times0.6533+4\times0.2706
+4\times(-0.2706)+0\times(-0.6533)
=2.6131
$$

其余两行用同样方法得到$X[2]=-2$和$X[3]\approx1.0824$。

##### 怎样看和使用变换矩阵与结果

需要区分$C$和$X$：

- $C$是固定的余弦权重矩阵。行表示频率模式，列表示输入位置。$C[k,n]$表示计算第$k$个系数时，第$n$个输入要乘的权重。
- $X$是当前输入经过DCT后得到的频率系数。$X[0]$是DC系数，后面的元素依次表示更高频率模式的强度。

在本例中，$X[0]=6$最大，说明数据主要由共同变化组成；其余系数的绝对值较小，说明快速变化较弱。编码器接下来量化的是$X$，矩阵$C$由输入长度和DCT定义决定，可以重复使用。

采用上述正交归一化后，未量化的系数可以通过逆变换恢复输入：

$$
x^T=C^TX
$$

这相当于用每个系数乘对应的余弦模式，再把所有模式相加。量化会修改或删除部分系数，因此解码器实际恢复的是近似值。

##### 二维DCT的大致过程

图像残差是二维矩阵。二维DCT先沿水平方向对每一行做一维DCT，再沿垂直方向对每一列做一维DCT：

$$
T=CRC^T
$$

结果矩阵$T$的左上角表示水平和垂直方向都变化缓慢的低频部分；向右表示水平方向频率升高；向下表示垂直方向频率升高；右下区域表示两个方向都变化较快。

DCT可以分两次计算，是因为二维余弦模式具有可分离结构。H.264/H.265实际采用标准规定的整数变换和缩放规则，没有直接执行上述浮点DCT；它们借鉴了DCT的频率分解、能量集中和可分离计算思想，以保证编解码结果一致并便于硬件实现。

#### 量化怎样把较小的系数归零

得到系数矩阵后，编码器通过量化降低每个系数的表示精度。简化形式是：

$$
Q[u,v]=\operatorname{round}\left(\frac{T[u,v]}{Q_{\text{step}}[u,v]}\right)
$$

`T[u,v]`是变换系数，`Qstep[u,v]`是该位置使用的量化步长。H.264/H.265中的QP是量化参数，它用于确定量化步长和相关缩放规则。编码器先由QP推导量化尺度，再按标准规定的整数缩放与取整公式处理各位置的系数。

为了展示效果，先假设所有位置都使用量化步长5：

$$
T=\begin{bmatrix}
12&4\\
4&-4
\end{bmatrix}
\quad\xrightarrow{\ Q_{\text{step}}=5\ }\quad
Q=\operatorname{round}\left(\frac{T}{5}\right)
=\begin{bmatrix}
2&1\\
1&-1
\end{bmatrix}
$$

若另一个系数的值为2：

$$
\operatorname{round}\left(\frac{2}{5}\right)=0
$$

这个系数便被归零。按照四舍五入的简化规则，绝对值小于量化步长一半的系数会归零；实际标准使用整数缩放和规定的舍入方法，边界应以对应公式为准。

量化步长越大，更多小系数会变成零，剩余系数的数值范围也会缩小。熵编码器只需集中表示少量非零系数和零值分布，因此码流变小。代价是被取整舍弃的系数精度无法通过反量化恢复，重建残差和原始残差会产生差异，这就是有损压缩。

完整过程可以归纳为：

```text
当前真实块减去预测块
→ 得到按像素位置排列的残差块
→ 使用可分离变换改写成频率系数矩阵
→ 将共同变化集中到少量低频系数
→ 根据QP确定量化步长并对系数取整
→ 大量较小系数变成零
→ 熵编码用较少比特表示量化结果
```

量化后的整数矩阵`Q`会进入两条后续路径：熵编码器把它写入码流；编码器内部的重建路径对它执行反量化和反变换，模拟解码器能够恢复出的残差。

### 2.3 熵编码与编码数据输出

量化结束后，编码器已经确定解码当前块所需的信息，主要包括：

- 当前块如何划分，以及选择了哪种预测模式。
- 帧间预测使用的参考图像和运动信息，或帧内预测使用的方向模式。
- 当前块使用的QP或由上级语法推导QP所需的差值。
- 哪些变换系数非零、非零系数的数值和符号。

直接给每个字段分配固定长度会浪费空间。视频中存在大量重复规律，例如“残差全零”“扫描末尾连续为零”“相邻块使用相似预测模式”都很常见。熵编码根据这些规律给高概率符号使用较短表示，给低概率符号使用较长表示。

#### 量化系数怎样变成待编码符号

二维量化系数先按标准规定的顺序扫描成一维序列。扫描通常从低频区域走向高频区域，使量化产生的连续零值集中到序列尾部。以简化矩阵为例：

```text
量化系数：         一种示意扫描结果：
2   1              [2, 1, 1, -1]
1  -1
```

如果量化结果是`[6, 1; 0, 0]`，扫描序列会包含连续零。编码器可以表达非零系数数量、最后一个非零位置、各系数幅值和符号，无需为尾部每个零分别写入完整数值。实际字段和扫描顺序由编码标准、块大小及预测方式确定。

#### CAVLC和CABAC怎样减少比特数

H.264可使用上下文自适应可变长编码（Context-Adaptive Variable-Length Coding，CAVLC）或上下文自适应二进制算术编码（Context-Adaptive Binary Arithmetic Coding，CABAC）；H.265主要使用CABAC。

CAVLC根据周围块的非零系数情况选择不同的可变长码表。常见的小数值和短模式使用较短码字，罕见的大数值使用较长码字。

CABAC的实现可以分成三个概念步骤：

1. **二值化**：把预测模式、系数幅值等语法元素转换成一串二进制判断，称为bin。
2. **上下文建模**：根据当前语法位置和邻近块的已编码状态，为某些bin选择概率模型。例如相邻块都没有非零系数时，当前块“无非零系数”的概率也可能较高。
3. **二进制算术编码**：按照概率不断缩小数值区间。高概率结果消耗的平均比特更少，最终区间被输出成字节序列。

熵编码只改变无损表示方法。量化矩阵已经确定后，熵编码器和熵解码器能够恢复出完全相同的量化系数、预测模式和运动信息。画质损失发生在前面的量化阶段。

#### 编码结果怎样组成NAL单元

网络抽象层单元（Network Abstraction Layer Unit，NAL unit）是H.264/H.265码流的基本组织单位。熵编码后的slice数据、参数集和辅助信息不会混成一段无法区分的字节，而是分别装入不同类型的NAL单元。

一个NAL单元可以先理解为：

```text
NAL头部 + NAL负载
```

- **NAL头部**说明该NAL属于什么类型、是否可作为参考，以及H.265中的层级和时间子层等信息。
- **NAL负载**保存该类型对应的实际语法，例如图像slice、SPS、PPS或SEI。

##### H.264的NAL头部

H.264的基本NAL头部占1字节：

```text
bit 7        bit 6～5       bit 4～0
forbidden    nal_ref_idc    nal_unit_type
zero_bit
```

- `forbidden_zero_bit`占1位，合法码流中必须为0。
- `nal_ref_idc`占2位，表示该NAL中的图像数据是否会影响参考图像。值为0时，该NAL不用于后续参考；值越高表示参考重要性等级越高。参数集等重要NAL也会使用非零值。
- `nal_unit_type`占5位，决定NAL负载中保存的内容。

H.264常见的`nal_unit_type`如下：

| 类型值 | NAL负载承载的内容 |
|---|---|
| 1 | 非IDR图像的slice数据，可能属于普通I、P或B图像 |
| 5 | IDR图像的slice数据 |
| 6 | 补充增强信息（Supplemental Enhancement Information，SEI） |
| 7 | 序列参数集SPS |
| 8 | 图像参数集PPS |
| 9 | 访问单元分隔符AUD，用于辅助标记一张编码图像的边界 |

NAL类型1只表明负载是非IDR slice，不能单凭NAL头部判断它是I、P还是B。具体帧类型需要继续解析负载中的slice header及其`slice_type`。

##### H.265的NAL头部

H.265的NAL头部占2字节，主要字段包括：

```text
forbidden_zero_bit  1位
nal_unit_type       6位
nuh_layer_id        6位
nuh_temporal_id_plus1 3位
```

- `nal_unit_type`同样说明负载类型，但H.265使用6位，能够区分更多普通图像和随机访问图像类型。
- `nuh_layer_id`标识该NAL所属的编码层；普通单层视频通常为0。
- `nuh_temporal_id_plus1`标识时间子层，其值必须大于0，实际时间层编号等于该值减1。

H.265常见类型包括：

| 类型值 | NAL负载承载的内容 |
|---|---|
| 0～9 | 普通非随机访问图像的slice数据，具体类型还需解析slice header |
| 16～18 | BLA类随机访问图像的slice数据 |
| 19～20 | IDR图像的slice数据 |
| 21 | CRA图像的slice数据 |
| 32 | 视频参数集VPS |
| 33 | 序列参数集SPS |
| 34 | 图像参数集PPS |
| 35 | 访问单元分隔符AUD |
| 39、40 | 前缀SEI和后缀SEI |

##### NAL负载怎样保存和传输

NAL头部后的负载首先按照编码标准组织为原始字节序列负载（Raw Byte Sequence Payload，RBSP）。为避免负载中的字节与Annex B起始码混淆，编码器会按规则插入防竞争字节，形成实际放入NAL中的字节序列。

编码器输出NAL单元后，下一层根据使用场景继续处理：

```text
编码器输出NAL单元
├─ 保存为Annex B裸码流：在NAL前添加起始码
├─ 写入MP4等容器：记录NAL长度，并把部分参数集放入容器配置
└─ 通过RTP等协议发送：按网络负载限制聚合或分片
```

因此，“编码包”已经是封装器或发送接口看到的数据单位；预测块、残差矩阵和变换系数只存在于编码器内部，不会以原始矩阵形式直接发送。

### 2.4 编码器内部重建、环路滤波与参考帧同步

解码器收到预测信息和量化系数后，只能重建出一张接近原始图像的**重建图像**。它无法取得摄像头输入的原始图像，因为量化已经舍弃了一部分系数精度。

帧间预测要求编码器和解码器使用内容相同的参考帧。为此，编码器除了输出码流，还会在内部执行一次与解码器相同的重建过程：

```text
编码器                                  解码器

拥有原始图像                            接收编码码流
产生预测、残差、量化系数                  读取预测信息和量化系数
         ↓                                      ↓
反量化、反变换、加回预测块                 反量化、反变换、加回预测块
         ↓                                      ↓
得到重建图像C'                           得到内容相同的重建图像C'
         ↓                                      ↓
保存C'作为后续帧间预测的参考帧             保存C'作为后续解码的参考帧
```

编码器内部没有调用接收端的外部解码器。它只是在自己的编码流程中保留了一条本地重建路径，执行与解码器等价的计算。

#### 解码器为什么只能得到重建图像

继续使用2.2节的简化数据。量化前的变换系数为：

$$
T=\begin{bmatrix}
12&4\\
4&-4
\end{bmatrix}
$$

使用简化量化步长5后，量化系数为：

$$
Q=\begin{bmatrix}
2&1\\
1&-1
\end{bmatrix}
$$

解码器从码流中恢复的是$Q$，无法知道量化前精确的$12、4、4、-4$。反量化只能得到：

$$
T'=\begin{bmatrix}
10&5\\
5&-5
\end{bmatrix}
$$

对$T'$执行反变换并取整，得到重建残差：

$$
R'=\begin{bmatrix}
4&4\\
4&-1
\end{bmatrix}
$$

再把重建残差加回预测块：

$$
P=\begin{bmatrix}
100&101\\
102&103
\end{bmatrix},\qquad
C'=P+R'=
\begin{bmatrix}
104&105\\
106&102
\end{bmatrix}
$$

原始块右下角是103，重建结果是102。这个1级误差来自量化。解码器最终拥有的是$C'$，没有原始块$C$。

#### 编码器为什么也要重建同一张图像

假设下一帧需要引用当前帧：

- 编码器若引用原始值103，会以103生成下一帧的预测块。
- 解码器手中只有重建值102，只能以102生成下一帧的预测块。

双方预测块相差1。编码器计算并发送的下一帧残差是以自己的预测块为基础，解码器却把该残差加到另一个预测块上，重建结果便会继续偏离。

因此，编码器舍弃原始帧作为后续预测的直接参考，改用自己内部重建出的$C'$。编码器和解码器各自在本地保存内容相同的$C'$，下一帧就能从相同像素生成相同的预测块。

#### 环路滤波与参考帧缓冲区

分块预测和分块量化可能使相邻块边界两侧出现不连续。H.264的去块滤波器会根据边界强度、像素差和QP等条件平滑符合要求的边界。H.265还可以使用样点自适应补偿（Sample Adaptive Offset，SAO），根据像素类别添加小偏移，降低量化造成的系统性误差。

环路滤波属于重建闭环的一部分。编码器和解码器必须对重建图像执行相同的标准滤波，再将滤波结果保存到解码图像缓冲区（Decoded Picture Buffer，DPB）：

```text
重建图像
→ 环路滤波
→ 写入编码器自己的DPB
→ 写入解码器自己的DPB
→ 双方后续都从内容相同的参考帧中生成预测块
```

两边的DPB位于不同设备或不同进程中，并不共享同一块内存。码流语法、确定性的反量化、反变换和滤波规则保证它们保存的参考内容一致。图像不再需要作为参考时，编码器和解码器再分别从自己的DPB中移除它。
## 3 H.264与H.265的编码结构及工程差异

H.265通过更灵活的块划分、更多预测模式和改进的编码工具，通常能在相近主观画质下减少码率。实际节省比例没有统一常数，必须以相同输入、分辨率、帧率和质量目标进行实测。画面内容、编码预设、硬件实现和低延迟限制都会改变结果。

工程选型主要检查以下条件：

- 采集或推理芯片是否具有对应的硬件编码器，以及支持哪些 profile、level、像素格式和最大分辨率。
- 接收端、浏览器、播放器和硬件解码器是否支持该编码格式。
- 编码速度、功耗、端到端延迟和内存占用是否满足设备限制。
- 容器与传输协议怎样保存参数集、时间戳和随机访问点。
- 产品发布地区和使用方式涉及的专利许可条件。

H.264目前具有更广泛的兼容性；H.265适合带宽或存储压力较高、收发两端均可控的系统。嵌入式项目应先查询芯片厂商编码接口实际返回的能力，不能仅根据标准名称判断支持情况。

## 4 I帧、P帧、B帧与参考关系

I、P、B描述一张编码图像允许采用的预测关系。它们影响压缩率、参考依赖、编码缓存和错误传播。

### 4.1 I帧、P帧与B帧的预测方式

- **I帧（Intra-coded Picture）**的图像块使用帧内预测，不从其他图像取得预测像素。按照是否具有IDR刷新语义，可以先把I帧理解为IDR帧和普通非IDR I帧。两者的当前图像都能依靠帧内预测完成重建，区别主要出现在当前图像之后的参考关系。
- **P帧（Predictive-coded Picture）**允许使用先前已经解码的参考图像，也可以包含帧内编码块。P帧不等于“整张图像都采用帧间预测”。
- **B帧（Bi-predictive-coded Picture）**允许使用前后两个方向的参考图像进行预测。B帧通常能提高压缩效率，但编码器需要等待后续参考图像，解码器也要按照参考依赖调整解码顺序，最后恢复显示顺序。

普通非IDR I帧自身不会引用前面的帧，但它不会清空解码图像缓冲区中的旧参考帧。后续P/B帧仍可能跨过这张I帧，继续引用I帧之前的旧参考帧，也可以引用这张I帧。IDR帧会在这里增加参考关系刷新的限制，具体见4.2节。

“当前图像使用什么预测方式”和“后续图像可以引用哪些参考帧”是两个维度。部分编码结构还允许B图像成为参考图像。分析实际依赖关系时，应读取码流或编码器配置，不能仅看I、P、B字母推断完整参考链。

### 4.2 IDR帧、I帧与关键帧的区别

即时解码刷新图像（Instantaneous Decoder Refresh，IDR）是H.264/H.265中具有明确参考刷新语义的帧内编码图像。可以将它理解为具有“切断旧参考链”作用的特殊I帧。

普通非IDR I帧与IDR帧的关系可以表示为：

```text
普通非IDR I帧：

P0 → P1 → I2 → P3
      └────────→ P3仍可能引用I2之前的P0或P1

IDR帧：

P0 → P1    IDR2 → P3 → P4
旧参考链     ↑       新参考链
             在IDR处切断
```

解码器遇到IDR帧后，会按照IDR语义刷新旧参考状态。IDR之后的图像不能再引用IDR之前的旧参考图像。因此，只要解码器先取得正确的SPS/PPS并从IDR开始，就不需要解码IDR之前的图像来建立后续参考链。

普通非IDR I帧只保证当前图像不需要其他图像提供预测像素。它不会强制后续P/B帧放弃I帧之前的旧参考图像，所以从普通I帧中途开始解码，未必能够正确重建紧随其后的所有图像。

这个区别发生在2.4节介绍的参考帧缓冲与参考关系管理阶段：

```text
当前图像完成重建和环路滤波
→ 更新DPB中的参考图像
→ 决定后续图像允许引用哪些参考帧
  ├─ 普通非IDR I帧：旧参考关系可以继续保留
  └─ IDR帧：切断IDR之前的旧参考关系
```

关键帧（key frame）是工具、容器和应用常用的宽泛标记，通常表示适合开始解码的位置。具体是否具有IDR刷新语义，还需要结合编码标准、NAL类型和码流结构确认。

## 5 图像组（Group of Pictures，GOP）与编码延迟

图像组（Group of Pictures，GOP）描述一段编码图像的帧类型安排和参考结构。一个简化的闭合 GOP 可以表示为：

```text
IDR  B  B  P  B  B  P  B  B  P  ...  下一张IDR
└──────────── 一个GOP ────────────┘
```

### 5.1 GOP长度、参考结构与随机访问

GOP长度通常表示相邻关键刷新点之间的图像数量。FFmpeg的通用编码选项`-g`设置最大 GOP 大小；对`libx264`而言，它映射到最大关键帧间隔`keyint`。例如30 fps视频使用`-g 60`，最大间隔对应2秒。场景切换检测和最小关键帧间隔等设置可能使实际关键帧位置发生变化，因此应使用`ffprobe`检查输出结果。[FFmpeg编码器文档](https://ffmpeg.org/ffmpeg-codecs.html)

较长 GOP 减少高开销 I/IDR 图像出现的频率，通常有利于降低平均码率。代价包括随机访问间隔变长、丢包错误可能传播更久，以及播放端跳转到目标位置时需要从更早的随机访问点开始解码。

闭合 GOP 内的图像不引用 GOP 边界之外的图像，边界更适合独立切片和随机访问。开放 GOP 允许边界附近的图像跨 GOP 使用参考，可能提高压缩效率，但切片、拼接和随机访问需要同时处理跨边界依赖。

### 5.2 B帧重排、编码缓存与延迟

假设显示顺序为：

```text
I0  B1  B2  P3
```

B1和B2若要引用P3，编码器必须先取得并编码P3，再完成B1和B2。因此编码器需要缓存后续图像，解码器也需要按依赖顺序解码后重新排列显示。B帧数量、前视分析深度和参考结构越复杂，通常需要更多缓存和等待时间。

低延迟视频常减少或关闭B帧，并缩短前视分析。这样会牺牲部分压缩效率。具体延迟仍取决于采集缓冲、编码器、封装、网络抖动缓冲和显示队列，不能只用是否存在B帧判断端到端延迟。

### 5.3 参考链对丢包和错误恢复的影响

一个参考图像的数据损坏后，引用它的后续图像可能继续使用错误的重建内容，画面错误便沿参考链传播。解码器收到新的 IDR 后可以丢弃旧参考关系，从完整图像重新建立状态。

GOP越长并不意味着错误一定持续到整个GOP结束，实际结果还受丢失的NAL单元、错误隐藏策略、参考关系和传输层重传影响。工程排查应同时记录丢包位置、关键帧位置和解码器错误日志。

### 5.4 帧内刷新如何分散I/IDR帧的码率峰值

帧内刷新（Intra Refresh）让编码器在连续多张图像中分别选择一部分区域进行帧内编码，经过一个刷新周期后覆盖整幅画面。循环帧内刷新（Cyclic Intra Refresh，CIR）是常见实现，例如让帧内编码区域按列或按行逐步移动。

```text
第1张P图像：区域A使用帧内编码，其余区域继续预测
第2张P图像：区域B使用帧内编码，其余区域继续预测
第3张P图像：区域C使用帧内编码，其余区域继续预测
……
完成一次整幅图像刷新
```

这些输出通常仍是包含帧内编码块的P图像。编码器没有把一张I帧的字节切成多份。帧内刷新能把集中在周期性IDR上的编码开销分散到多张图像，降低瞬时码率峰值，并逐步替换可能受损的参考内容。

它的主要限制是随机接入：新接收端无法像收到完整IDR那样立即获得整幅可独立恢复的图像，可能要等待完整刷新周期并遵守编码器规定的恢复点。实时通信可以平时使用帧内刷新，在新客户端加入或严重丢包时另外请求IDR。

FFmpeg的`libx264`封装提供`-intra-refresh 1`，含义是使用周期性帧内刷新代替IDR；硬件编码器的支持方式和约束不同，使用前应运行`ffmpeg -h encoder=<编码器名称>`查询当前构建。[FFmpeg编码器文档](https://ffmpeg.org/ffmpeg-codecs.html)

## 6 编码参数集SPS、PPS与VPS

参数集保存一段码流中会被多张图像重复使用的解码配置。编码器给参数集分配编号，图像语法通过编号引用对应配置，避免每张图像重复携带全部参数。

### 6.1 SPS、PPS与VPS分别保存的信息

SPS、PPS和VPS保存的是可被多张图像重复使用的解码配置。它们不保存某张图像的完整像素，也不保存该图像全部残差；图像slice只需引用参数集编号，就可以复用其中的规则。

#### H.264的SPS内部主要有什么

序列参数集（Sequence Parameter Set，SPS）描述一段编码序列的整体结构。常见字段可以按用途分成以下几类。

**1. 参数集身份与编码能力**

- `seq_parameter_set_id`：当前SPS的编号。PPS通过这个编号引用它。
- `profile_idc`及约束标志：说明码流使用Baseline、Main、High等哪类编码工具集合。
- `level_idc`：说明该码流需要的解码能力等级，约束最大图像尺寸、宏块处理速率、码率和参考帧缓冲需求等。

Profile回答“使用了哪些编码工具”，Level回答“解码这些内容至少需要多大的处理和缓冲能力”。

**2. 像素格式和位深**

- `chroma_format_idc`：说明色度采样结构，例如常见的4:2:0。
- `bit_depth_luma_minus8`和`bit_depth_chroma_minus8`：分别说明亮度与色度位深。字段保存的是实际位深减8，例如值为2代表10 bit。
- `separate_colour_plane_flag`：在特定色度格式下说明三个颜色平面是否分别编码。

这些字段决定解码器怎样解释重建样点的数量、范围和颜色平面结构。

**3. 编码图像尺寸与显示裁剪**

- `pic_width_in_mbs_minus1`：每行宏块数量减1。
- `pic_height_in_map_units_minus1`：图像高度对应的map unit数量减1。
- `frame_mbs_only_flag`：说明序列采用逐帧编码，还是允许场编码结构。
- `frame_cropping_flag`及四个裁剪偏移：从编码图像边缘裁掉不属于最终显示区域的样点。

H.264的SPS通常先描述按宏块对齐的编码尺寸，再通过裁剪字段得到显示尺寸。例如1920×1080的亮度高度不是16的整数倍，编码高度可能按1088组织，再裁掉底部多出的8行。实际裁剪单位还与色度格式和帧、场结构有关，解析器必须按标准换算，不能直接把裁剪偏移当作像素数。

**4. 帧编号、图像顺序与参考帧能力**

- `log2_max_frame_num_minus4`：决定`frame_num`字段使用多少位。
- `pic_order_cnt_type`及其相关字段：规定图像顺序计数（Picture Order Count，POC）怎样计算，为显示顺序重排提供依据。
- `max_num_ref_frames`：解码图像缓冲区需要支持的最大参考帧数量。
- `gaps_in_frame_num_value_allowed_flag`：说明帧编号出现间断时是否允许按规定处理。

这些字段为解码器维护DPB、识别参考图像和恢复显示顺序提供基础。PTS、DTS与时间基将在阶段2-8单独说明。

**5. 视频可用性信息VUI**

SPS可以携带视频可用性信息（Video Usability Information，VUI），常见内容包括：

- 像素宽高比或样点宽高比。
- 视频信号类型、色彩原色、传递特性和矩阵系数。
- 全范围或有限范围标志。
- 时序信息，例如`num_units_in_tick`和`time_scale`。
- HRD缓冲模型与码率相关参数。

VUI主要补充视频如何正确显示和按什么时序、颜色含义解释。VUI缺失不一定导致像素无法解码，但播放器可能只能依赖容器信息或默认值解释帧率、宽高比和颜色。

#### H.264的PPS内部主要有什么

图像参数集（Picture Parameter Set，PPS）描述一组图像或slice共同采用的图像级编码规则。常见字段包括：

**1. PPS身份以及它引用哪个SPS**

- `pic_parameter_set_id`：当前PPS的编号，slice header通过它选择PPS。
- `seq_parameter_set_id`：该PPS所依赖的SPS编号。

引用链为：

```text
slice header中的pic_parameter_set_id
→ 找到PPS
→ PPS中的seq_parameter_set_id
→ 找到SPS
```

**2. 熵编码和slice组织方式**

- `entropy_coding_mode_flag`：值为0时使用CAVLC，值为1时使用CABAC。Baseline Profile通常不允许CABAC。
- `num_slice_groups_minus1`及相关字段：说明是否使用灵活宏块排序（Flexible Macroblock Ordering，FMO）把图像宏块组织成多个slice group。
- `num_ref_idx_l0_default_active_minus1`和`num_ref_idx_l1_default_active_minus1`：给出参考列表L0、L1默认启用的参考索引数量；slice header可以覆盖默认值。

**3. 量化初始值与色度量化偏移**

- `pic_init_qp_minus26`：给出图像级初始亮度QP相对26的偏移。slice还可以通过`slice_qp_delta`继续调整。
- `pic_init_qs_minus26`：与SP/SI slice相关的初始量化参数。
- `chroma_qp_index_offset`及可选的第二色度偏移：控制色度QP相对亮度QP的映射偏移。

因此，某个块最终使用的QP不只由PPS中的一个字段决定，还可能叠加slice和宏块、编码单元级调整。

**4. 加权预测和去块滤波控制**

- `weighted_pred_flag`：说明P slice是否允许显式加权预测。
- `weighted_bipred_idc`：说明B slice采用关闭、显式或隐式加权双向预测。
- `deblocking_filter_control_present_flag`：说明slice header中是否携带去块滤波控制参数。
- `constrained_intra_pred_flag`：限制帧内预测的参考来源，只允许使用满足条件的帧内编码邻块。
- `redundant_pic_cnt_present_flag`：说明slice header中是否出现冗余图像计数字段。

这些标志决定解码器是否应该在后续slice header中读取对应字段，以及怎样执行预测或滤波。

#### H.265中的VPS、SPS和PPS怎样分工

H.265仍然使用SPS和PPS，但字段会根据HEVC的CTU、短期和长期参考图像集、SAO、tile等机制重新组织。其大致分工为：

- **VPS**：描述更高层的视频结构，包括最大子层数量、时间嵌套、profile-tier-level，以及多层码流中的层级关系。普通单层码流也会携带VPS。
- **SPS**：描述序列的图像尺寸、色度格式、位深、CTU与变换块范围、参考图像集、POC、SAO及VUI等序列级信息。
- **PPS**：描述图像级规则，例如初始QP、tile、熵编码同步（WPP）、去块滤波、加权预测和slice header扩展等。

解码器必须先取得被slice引用的有效参数集。参数集缺失、编号错误，或分辨率改变后仍使用旧参数，都会使解码器无法按正确的尺寸、位深和语法解析后续图像。

### 6.2 参数集的引用关系、传输时机与缺失故障

H.264中的简化引用链为：

```text
Slice Header中的pic_parameter_set_id
→ 找到对应PPS
→ PPS中的seq_parameter_set_id
→ 找到对应SPS
→ 使用两组参数解析和重建当前图像
```

H.265还会由SPS继续引用VPS。参数集缺失或编号不匹配时，解码器无法建立正确配置，常见症状包括`non-existing PPS referenced`、解码失败、黑屏或等待下一组有效参数。

参数集可以在编码码流内部传输，也可以由容器保存在码流外的解码器额外数据（extradata）中。FFmpeg官方文档将前者称为in-band，后者称为out-of-band；MP4常把H.264/H.265参数集保存在容器配置中，Annex B裸码流和部分实时传输通常会在码流内发送。[FFmpeg码流过滤器文档](https://ffmpeg.org/ffmpeg-bitstream-filters.html#extract_005fextradata)

修改分辨率、profile或其他会影响解码配置的参数时，编码器需要产生新的参数集，并保证接收端在引用新参数的图像之前取得它们。网络发送端还应考虑SPS/PPS丢包：只发送一次会让中途加入或当时丢包的接收端长期无法解码。

### 6.3 I帧、GOP与SPS/PPS参数集的关系

I/IDR图像、GOP和参数集分别承担图像编码、参考结构组织和解码配置三种职责：

```text
SPS/PPS：说明后续图像应该怎样解析
IDR：提供完整帧内编码图像并刷新旧参考关系
GOP：组织IDR或I图像之后的一组I/P/B图像及参考关系
```

SPS/PPS可以被多张图像和多个GOP重复引用，不固定属于某张I帧，也没有“每个GOP必须生成一套新SPS/PPS”的规则。工程码流经常形成`SPS → PPS → IDR → P/B...`的排列，是因为新接收端同时需要参数集和随机访问图像才能从中途开始解码。

编码器或复用器可以在每个IDR前重复现有SPS/PPS，提高中途加入和丢包后的恢复机会。参数没有变化时，这种重复不代表产生了新的配置；参数发生变化时，应先传输新参数集，再发送引用它的图像。参数集究竟保存在容器extradata还是重复插入码流，需要根据封装与传输协议确定。

有些编码器默认只在码流开始时输出一次SPS/PPS：

```text
SPS → PPS → IDR → P/B……→ IDR → P/B……
```

实时接收端若从第二个IDR附近中途加入，手中没有开头的SPS/PPS，就可能无法初始化解码器或解析图像。此时可以开启编码器的重复头部（repeat headers）功能，让每个IDR前都携带当前SPS/PPS：

```text
SPS → PPS → IDR → P/B……→ SPS → PPS → IDR → P/B……
```

这样接收端取得`SPS/PPS + IDR`后即可从该随机访问点开始解码。具体配置名称和参数集是编码器自动插入，还是由应用程序取得codec header后自行插入，需要查看所用硬件编码器或SDK接口。

## 7 量化参数（Quantization Parameter，QP）与压缩质量

量化参数（Quantization Parameter，QP）控制量化步长。QP升高会增大量化步长，更多变换系数被舍弃，编码数据通常减少，重建误差增大；QP降低会保留更多系数精度，数据量通常增加。

### 7.1 QP如何影响量化步长、画质与码率

H.264中，亮度量化步长随QP每增加6大约扩大一倍。可以写成相对关系：

```text
Qstep(QP + 6) ≈ 2 × Qstep(QP)
```

这条关系描述量化器的步长，不表示文件大小必然减半。最终数据量还取决于预测效果、画面内容、帧类型、熵编码结果和码率控制策略。

`libx264`中的`-qp`选择恒定QP模式，适合观察量化参数对结果的直接影响。`-crf`选择恒定质量目标模式，编码器会根据内容和帧的重要性调整实际QP；CRF数值越低，目标质量越高，文件通常越大。二者是不同的码率控制方式，实验时不要把CRF值称为每帧固定QP。[FFmpeg编码器文档](https://ffmpeg.org/ffmpeg-codecs.html)

### 7.2 画面复杂度对相同QP编码结果的影响

相同QP不会得到相同码率。静止背景、平坦颜色和可预测运动通常产生较少的非零残差系数；随机噪声、树叶、水面、细密纹理和快速运动会产生更多难以预测的残差。即使每个系数使用相同量化强度，后一类画面仍需编码更多非零系数和预测信息。

摄像头弱光噪声尤其容易消耗码率。降噪可以减少随机高频成分，但过强降噪也会损失真实细节。工程上应使用实际摄像头、照明和运动场景测试，不能只用静态测试图确定最终码率。

## 8 码率控制、CBR、VBR与VBV缓冲模型

码率控制器根据目标码率、画面复杂度和缓冲状态调整QP或其他编码决策。它要解决的问题是：有限带宽和缓存能承受多少数据，以及这些比特应该如何分配给不同图像。

### 8.1 平均码率、瞬时码率与文件大小

一段视频的平均码率可以由总编码数据量和时长计算：

```text
平均码率(bit/s) = 编码数据总字节数 × 8 ÷ 视频时长(s)
```

例如60秒纯视频数据占用30 MB，按十进制单位计算：

```text
30,000,000 × 8 ÷ 60 = 4,000,000 bit/s = 4 Mbit/s
```

瞬时码率必须先规定统计窗口。若按1秒窗口统计，就把每个连续1秒内的包大小相加后乘8；若按100毫秒统计，再把窗口中的比特数除以0.1秒。窗口越短，越容易看到I/IDR图像造成的尖峰。只报告“瞬时码率”而不说明窗口长度，数值无法可靠比较。

容器文件还包含音频、索引和封装开销，所以用整个文件大小计算出的总码率可能高于视频流本身的平均码率。`ffprobe -show_packets`可以读取每个视频包的大小和时间位置，用于构造固定窗口统计。

### 8.2 CBR与VBR的控制目标和适用场景

恒定码率（Constant Bit Rate，CBR）让编码器围绕固定输出速率工作。简单画面可以降低QP保留更多质量，复杂画面可能提高QP以避免超过带宽和缓冲限制。CBR仍会产生大小不同的编码包；“恒定”描述缓冲模型和时间窗口内的速率目标。

可变码率（Variable Bit Rate，VBR）允许简单片段使用较少比特、复杂片段使用较多比特。它通常更容易维持稳定视觉质量，适合存储和可变带宽场景。链路有硬上限时，还要配合最大码率和VBV缓冲限制。

CRF属于以质量为主要目标的可变码率方式；两遍编码属于以整个文件的平均码率或目标大小为主要目标的离线方式。实时摄像头编码无法等待完整视频完成第一遍分析，通常使用单遍码率控制。

### 8.3 VBV缓冲区如何限制瞬时码率

视频缓冲验证器（Video Buffering Verifier，VBV）是标准和编码器使用的虚拟缓冲模型。可以把编码器输出理解为向缓冲区写入数据，把固定带宽链路理解为按指定速率从缓冲区取走数据：

```text
编码图像产生比特 → 写入VBV缓冲区 → 链路按maxrate约束取出比特
```

FFmpeg的`-maxrate`设置最大码率约束，`-bufsize`设置码率控制缓冲区大小，二者单位都是bit。官方文档明确说明`maxrate`需要与`bufsize`配合。[FFmpeg通用编解码选项](https://ffmpeg.org/ffmpeg-codecs.html#Codec-Options)

例如`-maxrate 2M -bufsize 2M`表示最大速率目标为2 Mbit/s，缓冲容量为2 Mbit，即按最大取出速率计算约1秒的数据。它不保证任意短窗口都低于2 Mbit/s；编码器允许在缓冲区容量范围内产生局部波动。缓冲区过小或目标码率过低时，复杂画面需要提高QP，画质会在压力最大的片段下降。

### 8.4 编码器根据画面复杂度调整QP的基本流程

实时码率控制可以用下面的简化流程理解：

```text
分析当前图像复杂度和帧类型
→ 根据目标码率与VBV占用分配本帧比特预算
→ 选择初始QP并编码
→ 统计实际产生的比特数
→ 更新复杂度模型和VBV状态
→ 调整后续图像的QP
```

实时编码器的常见做法是：当前帧编码完成后，统计它实际产生的比特数并更新VBV状态；若本帧超出预算，就提高后续帧的QP，使后续帧压缩得更强。它通常不会因为本帧已经超出预算，就立即提高QP并把整帧重新编码一次，因为重编码会增加计算量和延迟。

I/IDR图像通常需要更多比特。若它使VBV占用快速上升，编码器会提高后续图像的QP，让缓冲区回到安全范围。部分编码器也支持在当前帧内部调整后续块的QP，或在严格帧大小限制下重新编码当前帧；具体行为由软硬件编码器实现决定。前视分析还可以提前发现复杂片段并重新分配比特，但会增加缓存和编码延迟。

## 9 FFmpeg与ffprobe编码参数对照实验

以下实验依赖带`libx264`的FFmpeg和`ffprobe`。先运行：

```bash
ffmpeg -hide_banner -h encoder=libx264
```

输出中应包含`libx264`、支持的像素格式，以及`crf`、`qp`、`intra-refresh`等选项。命令以Linux shell为主；Windows PowerShell可以把行末反斜杠改为反引号，或写成单行命令。

先生成10秒、30 fps的公共输入。`testsrc2`提供运动测试图，`noise`叠加随时间变化的噪声，使不同码率控制方式的差异更明显：

```bash
ffmpeg -hide_banner -y \
  -f lavfi -i "testsrc2=size=1280x720:rate=30:duration=10" \
  -vf "noise=alls=8:allf=t" \
  -pix_fmt yuv420p -c:v ffv1 source.mkv
```

FFV1是无损视频编码器，这里只用于保存可重复输入，避免多组实验使用不同源帧。

### 9.1 GOP长度、帧内刷新与I、P、B帧分布实验

生成最大GOP分别为30和120的两段H.264视频。`-sc_threshold 0`关闭场景切换引发的额外关键帧，`-keyint_min`与`-g`设为相同值，使测试图上的关键帧间隔更容易观察：

```bash
ffmpeg -hide_banner -y -i source.mkv \
  -c:v libx264 -preset medium -crf 23 \
  -g 30 -keyint_min 30 -sc_threshold 0 -bf 2 \
  gop30.mp4

ffmpeg -hide_banner -y -i source.mkv \
  -c:v libx264 -preset medium -crf 23 \
  -g 120 -keyint_min 120 -sc_threshold 0 -bf 2 \
  gop120.mp4
```

查看每张解码图像的时间、关键帧标记和帧类型：

```bash
ffprobe -v error -select_streams v:0 \
  -show_entries frame=best_effort_timestamp_time,key_frame,pict_type,pkt_size \
  -of csv=p=0 gop30.mp4

ffprobe -v error -select_streams v:0 \
  -show_entries frame=best_effort_timestamp_time,key_frame,pict_type,pkt_size \
  -of csv=p=0 gop120.mp4
```

`gop30.mp4`应约每30帧出现一次关键帧，`gop120.mp4`约每120帧出现一次。具体包大小由测试内容和编码决策决定，关键帧通常形成较高峰值。再用下面的命令比较文件中的视频流平均码率与总大小：

```bash
ffprobe -v error -select_streams v:0 \
  -show_entries stream=codec_name,profile,avg_frame_rate,bit_rate,nb_frames \
  -show_entries format=duration,size,bit_rate \
  -of default=noprint_wrappers=1 gop30.mp4
```

帧内刷新实验使用相同输入，并关闭B帧以减少低延迟结构中的重排因素：

```bash
ffmpeg -hide_banner -y -i source.mkv \
  -c:v libx264 -preset medium -crf 23 \
  -g 120 -keyint_min 120 -sc_threshold 0 -bf 0 \
  -intra-refresh 1 \
  intra_refresh.h264
```

`ffprobe`可以查看包大小和关键帧标记，却不能直接展示每张图像内部哪些块使用了帧内编码。证明刷新区域的移动需要编码器调试输出或支持宏块、CTU类型显示的码流分析器。这个实验主要观察周期性大包是否减少，以及输出是否仍能被解码：

```bash
ffprobe -v error -select_streams v:0 \
  -show_entries packet=pts_time,size,flags \
  -of csv=p=0 intra_refresh.h264

ffmpeg -v error -i intra_refresh.h264 -f null -
```

要观察SPS/PPS与图像NAL单元，可以给FFmpeg的H.264解析器开启调试日志：

```bash
ffmpeg -loglevel debug -debug bitstream \
  -i intra_refresh.h264 -f null - 2>&1 \
  | grep -E "nal_unit_type|SPS|PPS|IDR"
```

不同FFmpeg版本的调试文本可能变化。若日志不显示完整NAL类型，应使用专用H.264码流分析工具。MP4中的参数集可能位于容器extradata，分析Annex B裸流更容易观察码流内NAL单元。

### 9.2 固定QP、CBR、VBR与VBV对照实验

固定QP实验只改变`-qp`：

```bash
ffmpeg -hide_banner -y -i source.mkv \
  -c:v libx264 -preset medium -qp 20 \
  -g 60 -keyint_min 60 -sc_threshold 0 \
  qp20.mp4

ffmpeg -hide_banner -y -i source.mkv \
  -c:v libx264 -preset medium -qp 32 \
  -g 60 -keyint_min 60 -sc_threshold 0 \
  qp32.mp4
```

QP32的量化步长是QP20的约4倍，因为两者相差12，即两个“QP增加6、步长约翻倍”的区间。预期结果是`qp32.mp4`更小，细节损失和块状、模糊伪影更明显；文件大小不会严格缩小到四分之一。

使用CRF观察以质量为主要目标的VBR：

```bash
ffmpeg -hide_banner -y -i source.mkv \
  -c:v libx264 -preset medium -crf 23 \
  -g 60 -keyint_min 60 -sc_threshold 0 \
  crf23.mp4
```

使用目标平均码率、最大码率和VBV缓冲约束生成受限VBR：

```bash
ffmpeg -hide_banner -y -i source.mkv \
  -c:v libx264 -preset medium \
  -b:v 2M -maxrate 3M -bufsize 6M \
  -g 60 -keyint_min 60 -sc_threshold 0 \
  vbr_vbv.mp4
```

使用相等的目标、最小和最大码率，并启用x264的CBR HRD信号生成CBR测试流。官方文档说明`nal-hrd=cbr`不允许用于MP4，因此这里输出MPEG-TS：

```bash
ffmpeg -hide_banner -y -i source.mkv \
  -c:v libx264 -preset medium \
  -b:v 2M -minrate 2M -maxrate 2M -bufsize 2M \
  -x264-params "nal-hrd=cbr:force-cfr=1" \
  -g 60 -keyint_min 60 -sc_threshold 0 \
  cbr.ts
```

分别查看总大小和平均码率：

```bash
for file in qp20.mp4 qp32.mp4 crf23.mp4 vbr_vbv.mp4 cbr.ts; do
  echo "===== $file ====="
  ffprobe -v error \
    -show_entries format=duration,size,bit_rate \
    -of default=noprint_wrappers=1 "$file"
done
```

再导出逐包时间和大小：

```bash
ffprobe -v error -select_streams v:0 \
  -show_entries packet=pts_time,duration_time,size,flags \
  -of csv=p=0 vbr_vbv.mp4 > vbr_packets.csv

ffprobe -v error -select_streams v:0 \
  -show_entries packet=pts_time,duration_time,size,flags \
  -of csv=p=0 cbr.ts > cbr_packets.csv
```

逐包大小不等于瞬时码率。要比较波动，应按相同时间窗口汇总`size`字段，例如每1秒累加包字节数再乘8。测试结果应结合编码器日志中的实际参数解释；硬件编码器可能只支持CBR、VBR、CQP等模式的一部分，并可能把请求映射到最接近的硬件模式。
