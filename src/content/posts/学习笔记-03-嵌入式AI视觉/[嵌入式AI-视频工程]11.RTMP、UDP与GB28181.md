# 阶段2-11 RTMP、UDP与GB28181

本节要解决的实际问题是：同一段H.264视频，通过RTMP、直接UDP和GB28181发送时，发送端分别增加了哪些协议层，接收端又要按什么顺序拆开。

三条主链如下：

```text
RTMP：编码数据 → RTMP Message → RTMP Chunk → TCP → IP

UDP：应用数据 → 可选的自定义头或RTP头 → UDP → IP

GB28181：SIP完成注册和点播协商
         编码数据 → PES → MPEG-PS → RTP → UDP或TCP → IP
```

阶段2-10已经完整解释RTP头、分片、UDP重排序和RTCP。本节只引用这些结论，重点说明RTMP、UDP方案边界和GB28181的信令—媒体协作。

---

## 1 RTMP、裸UDP、自定义UDP、RTP与GB28181的协议层次

### 1.1 音视频编码、媒体包装、会话控制和网络传输的分层

一条视频网络链至少可以分为四层：

| 层级 | 解决的问题 | 典型对象 |
|---|---|---|
| 压缩编码层 | 如何减少图像数据量 | H.264 NAL、H.265 NAL、AAC帧 |
| 媒体包装层 | 如何表示消息、分片、时间和多路媒体 | RTMP Message/Chunk、RTP、MPEG-PS |
| 会话控制层 | 如何注册、鉴权、发起和结束会话 | RTMP Command、SIP、SDP |
|网络传输层 | 字节或数据报如何经过网络 | TCP、UDP、IP |

H.264只定义视频压缩语法。它不会决定服务器地址、UDP端口、重传策略或设备注册流程。发送程序还要按照目标协议增加上层结构。

### 1.2 RTMP、RTP、SIP、MPEG-PS、UDP与TCP的职责对应关系

- 实时消息协议（Real-Time Messaging Protocol，RTMP）同时定义命令、音频、视频、数据消息以及Chunk多路复用方式，常运行在TCP上。
- 实时传输协议（Real-time Transport Protocol，RTP）给实时媒体增加序列号、时间戳、SSRC和Payload Type，通常运行在UDP上，也可以由TCP承载。
- 会话初始协议（Session Initiation Protocol，SIP）负责注册、定位、建立和结束会话。它通过消息体携带SDP等描述，不承载持续视频图像。[RFC 3261定义了SIP的REGISTER、INVITE、ACK和BYE等基础方法](https://www.rfc-editor.org/info/rfc3261/)。
- MPEG节目流（MPEG Program Stream，MPEG-PS）把视频、音频等基本流包装成带时间信息的PES和PS结构。
- UDP保留数据报边界，不保证送达和顺序。
- TCP提供可靠、有序的字节流，不保留应用消息边界。

### 1.3 RTMP直播链与GB28181监控联网链的完整路径对照

RTMP推流的控制消息和媒体消息复用在一条RTMP连接中：

```text
推流端建立TCP
  → RTMP握手
  → connect连接服务器应用
  → createStream创建逻辑媒体流
  → publish发布流名
  → 连续发送Metadata、Audio Message和Video Message
```

GB28181把设备管理和媒体传输分开：

```text
设备通过SIP REGISTER注册到平台
  → 平台通过MESSAGE查询目录
  → 平台通过INVITE携带SDP发起点播
  → 设备回复200 OK，平台发送ACK
  → 设备按照SDP指定的IP、端口和传输方式发送RTP媒体
  → 一方发送BYE结束会话
```

因此，RTMP连接成功后仍需完成RTMP命令状态机；GB28181设备注册成功后仍需另外建立媒体会话。

## 2 RTMP连接建立过程：TCP、握手与控制命令

### 2.1 连接建立阶段与数据发送阶段分别使用什么

RTMP的工作过程可以明确拆成两段：先建立连接和逻辑媒体流，再在这条逻辑媒体流上持续发送数据。

```text
连接建立阶段
TCP连接
  → C0/C1/C2、S0/S1/S2握手
  → connect命令
  → createStream命令
  → publish或play命令
  → 得到可推流或可拉流的NetStream

数据发送阶段
编码后的音频/视频、元数据或控制信息
  → 形成对应类型的RTMP Message
  → 一个Message切成一个或多个RTMP Chunk
  → Chunk字节写入已经建立的TCP连接
```

这里有一个容易混淆的地方：`connect`、`createStream`、`publish`和`play`是命令的名字，实际发送时不会只向网络写入这几个英文单词。发送端先用AMF编码命令名和参数，将编码结果作为Command Message的Payload，再把Command Message切成Chunk，最后交给TCP。

```text
命令名和参数
  → AMF二进制数据
  → Command Message
  → 一个或多个Chunk
  → TCP字节流
```

因此，连接建立阶段和数据发送阶段共用`Message → Chunk → TCP`这套传输机制。区别在于：握手包直接放入TCP字节流；握手之后的命令、音频、视频、元数据和控制信息都通过RTMP Message与Chunk发送。

传统RTMP URL常写成：

```text
rtmp://server:1935/app/stream
```

- `server:1935`确定TCP服务地址，1935是RTMP常用端口；
- `app`用于`connect`，标识服务器应用实例；
- `stream`用于`publish`或`play`，标识发布或请求的媒体流。

### 2.2 C0、C1、S0和S1的实际结构

TCP连接建立后，客户端和服务器先进行RTMP握手。C表示Client，S表示Server，数字表示该方向上的握手块序号。C0、C1、C2和S0、S1、S2都是字段名称，不是网络中只发送字母`C0`或`S1`。

在RTMP简单握手中，`C0`和`S0`各占1字节：

```text
C0或S0：protocol version（1字节）
```

传统RTMP版本值为`0x03`。因此抓包中C0通常就是一个字节`03`，S0通常也回应`03`。

`C1`和`S1`各占1536字节：

```text
偏移       长度       字段
0          4字节      time：发送方时间戳
4          4字节      zero：简单握手中填写0
8          1528字节   random：发送方产生的随机数据
总计       1536字节
```

四字节时间字段使用网络字节序。它表示握手使用的毫秒计时值，主要用于握手回应和往返信息，不是音视频PTS。随机数据让对端可以在后续回应中证明自己确实收到了这一块数据。

部分实现还支持带摘要校验的复杂握手。它仍使用相同的C0/C1/C2、S0/S1/S2名称和总体尺寸，但1536字节内部会放入摘要相关字段。本文后续用最容易观察和实现的简单握手说明数据关系。

### 2.3 C2和S2怎样回应对方，以及完整收发顺序

`C2`和`S2`也各占1536字节。简单握手中的结构如下：

```text
C2：
偏移       长度       内容
0          4字节      复制S1.time
4          4字节      客户端收到S1时的时间值
8          1528字节   复制S1.random

S2：
偏移       长度       内容
0          4字节      复制C1.time
4          4字节      服务器收到C1时的时间值
8          1528字节   复制C1.random
```

典型收发顺序是：

```text
客户端                                      服务器
建立TCP连接
C0(1字节) + C1(1536字节)  ---------------->
                           <---------------- S0(1字节) + S1(1536字节) + S2(1536字节)
C2(1536字节)              ---------------->
握手完成，开始交换RTMP Chunk
```

从依赖关系看，服务器收到C0后才能确定版本，收到C1后才能生成回应C1的S2；客户端收到S1后才能生成回应S1的C2。双向发送可以由实现交错调度，所以抓包中的TCP分段组合可能不同，但逻辑依赖不变。

这些握手块直接写入TCP，没有RTMP Message Header和Chunk Header。一次`send()`也不保证对应一个TCP段；接收端应按协议规定累计读满1字节或1536字节，不能按一次`recv()`判断握手块边界。[RTMP规范给出了握手尺寸、字段和依赖顺序](https://rtmp.veriskope.com/docs/spec/)。

### 2.4 connect、createStream、publish和play实际编码成什么

握手完成后才进入RTMP Message阶段。命令由动作消息格式（Action Message Format，AMF）编码。以常见AMF0为例，一个字符串的二进制格式为：

```text
02 | 字符串长度（2字节，大端序） | UTF-8字符串内容
```

因此，命令名`connect`不会被单独发送成七个裸字符，它的AMF0编码以如下字节开始：

```text
02 00 07 63 6F 6E 6E 65 63 74
│  │     └──────── connect的UTF-8字节
│  └────────────── 字符串长度7
└───────────────── AMF0 String类型标记
```

每个命令的Payload由一串有顺序的AMF值组成：

| 命令 | Command Message Payload中的主要AMF值 | 作用 |
|---|---|---|
| `connect` | 命令名、Transaction ID、包含`app`和`tcUrl`等字段的命令对象 | 建立到服务器应用的NetConnection |
| `createStream` | 命令名、Transaction ID、Null | 请求服务器创建NetStream |
| `publish` | 命令名、Transaction ID、Null、流名、发布类型 | 在指定NetStream上发布媒体 |
| `play` | 命令名、Transaction ID、Null、流名及可选播放参数 | 在指定NetStream上请求媒体 |

Transaction ID用于把请求和`_result`或`_error`响应对应起来。`connect`通常使用非零Transaction ID，服务器用相同ID回应；`publish`和`play`的执行结果通常通过`onStatus`通知。

### 2.5 AMF命令怎样成为Message，再怎样成为Chunk

AMF编码完成后，发送端把整段AMF二进制数据作为Command Message Payload。Command Message属于RTMP Message的一种：AMF0 Command Message的Message Type ID通常为20，AMF3 Command Message的Message Type ID为17。

```text
connect及其参数
  → AMF0编码得到一段Payload
  → 指定Message Type ID = 20、时间戳、Payload长度和Message Stream ID
  → 得到一条逻辑上的Command Message
  → 按当前Chunk Size切成Chunk
  → 写入TCP
```

RTMP Message的逻辑结构是：

```text
RTMP Message
├─ Timestamp：这条Message的时间信息
├─ Message Length：Payload总长度
├─ Message Type ID：Payload应按命令、音频、视频等哪种类型解释
├─ Message Stream ID：属于哪条NetStream
└─ Message Payload：本例中就是AMF命令及其参数
```

需要精确理解“Message头”：线上并不存在一份完整Message先带独立头发送、随后再二次套Chunk头的重复结构。Message的时间戳、长度、类型和Message Stream ID由这条Message第一个Chunk的Message Header携带；后续Chunk通过CSID和压缩头继承这些信息。第三章会展开Chunk的逐字节结构。

`connect`和`createStream`属于连接级命令，通常使用Message Stream ID 0。服务器处理`createStream`后，通过`_result`返回一个NetStream使用的Message Stream ID，例如1；后续`publish`、`play`以及该流的音视频Message使用这个ID。

### 2.6 推流连接和拉流连接分别怎样建立

推流端的连接建立顺序为：

```text
TCP连接
  → C0/C1/C2、S0/S1/S2握手
  → connect Command Message（Message Stream ID 0）
  ← _result：应用连接成功
  → createStream Command Message（Message Stream ID 0）
  ← _result：返回Message Stream ID，例如1
  → publish Command Message（Message Stream ID 1，携带streamName）
  ← onStatus：NetStream.Publish.Start
  → 进入音视频数据发送阶段
```

拉流端的连接建立顺序为：

```text
TCP连接
  → C0/C1/C2、S0/S1/S2握手
  → connect Command Message（Message Stream ID 0）
  ← _result：应用连接成功
  → createStream Command Message（Message Stream ID 0）
  ← _result：返回Message Stream ID，例如1
  → play Command Message（Message Stream ID 1，携带streamName）
  ← User Control：StreamBegin
  ← onStatus：NetStream.Play.Start
  ← 进入音视频数据接收阶段
```

服务器还可能在这些命令之间发送Window Acknowledgement Size、Set Peer Bandwidth和Set Chunk Size等控制Message。只有收到发布或播放成功状态，应用才能确认逻辑媒体流已经可用；TCP连接成功和RTMP握手成功都早于这个状态。

## 3 RTMP数据发送过程：Message生成、Chunk切分与TCP传输

### 3.1 数据发送阶段使用哪些Message

逻辑媒体流建立后，连续数据仍然使用RTMP Message。Message Type ID决定Payload的具体解释方式：

| Message类别 | 常见Type ID | 主要内容 |
|---|---:|---|
| Audio Message | 8 | AAC等音频格式字段和编码音频数据 |
| Video Message | 9 | 帧类型、视频编码格式字段和编码视频数据 |
| Data Message | 18（AMF0）或15（AMF3） | 分辨率、帧率、编码器等元数据 |
| Command Message | 20（AMF0）或17（AMF3） | 命令、响应和状态通知 |
| Protocol Control Message | 1、2、3、5、6等 | Chunk大小、确认、确认窗口和带宽控制 |
| User Control Message | 4 | Stream Begin、Ping Request和Ping Response等事件 |

推流时，客户端主要向服务器发送Data、Audio和Video Message；拉流时，服务器主要向客户端发送这三类Message。Command、Protocol Control和User Control Message可以在媒体传输期间穿插出现，用于状态变化、保活和流量控制。

### 3.2 编码后的一帧怎样形成Audio或Video Message

以传统H.264 over RTMP为例，发送端通常把一个访问单元（Access Unit，AU）中的NAL单元写入一个Video Message Payload，并在前面加入RTMP视频载荷字段：

```text
H.264访问单元中的NAL单元
  → 按AVC格式写成“长度字段 + NAL数据”
  → 前面加入Frame Type、Codec ID、AVC Packet Type、Composition Time
  → 形成Video Message Payload
  → 配置时间戳、Payload长度、Type ID=9、Message Stream ID
  → 形成一条逻辑Video Message
```

传统H.264 RTMP Video Message的时间戳通常对应解码时间，Composition Time表示显示时间与解码时间之差，接收端据此恢复PTS与DTS关系。AAC音频也会先加入RTMP音频格式字段，再形成Audio Message Payload；元数据通常经过AMF编码后形成Data Message Payload。

### 3.3 RTMP Message的字段如何落到第一个Chunk中

一条RTMP Message在逻辑上包含Timestamp、Message Length、Message Type ID、Message Stream ID和Payload。发送时，第一个Chunk用Chunk Message Header携带这些Message字段，随后才放入第一段Payload数据。

| Message字段 | 作用 | `fmt=0`的Chunk Message Header中所占长度 |
|---|---|---:|
| Timestamp | Message时间戳 | 3字节，必要时另加4字节Extended Timestamp |
| Message Length | 整个Message Payload长度 | 3字节 |
| Message Type ID | Payload类型 | 1字节 |
| Message Stream ID | 所属NetStream | 4字节，线上使用小端序 |
| Message Payload | 命令、音频、视频或数据 | 分散在一个或多个Chunk Data中 |

Command Message和Video Message使用完全相同的Message外层字段。两者的不同主要体现在Message Type ID和Payload内容：前者的Payload通常是AMF命令，后者的Payload是RTMP视频字段与编码视频数据。

### 3.4 一条Message怎样切成多个Chunk

RTMP规范中的正式名称是Chunk，可理解为“RTMP数据块”。发送端按当前发送方向的Chunk Size切分Message Payload。规范初始Chunk Size为128字节，通信双方可以各自通过Set Chunk Size Message修改自己随后发送的Chunk Data上限。

假设一条Video Message Payload为1000字节，Chunk Size为128字节：

```text
第1个Chunk：Chunk Header + Payload[0..127]       128字节
第2个Chunk：压缩Chunk Header + Payload[128..255] 128字节
……
第8个Chunk：压缩Chunk Header + Payload[896..999] 104字节
```

因此它需要8个Chunk。Chunk Size限制的是每个Chunk承载的Message Payload字节数，不包含Chunk Header本身。同一Message的各段使用同一CSID；在它们之间可以插入其他CSID上的音频或控制Chunk，使一个大Video Message不会长期阻塞其他RTMP Message。

### 3.5 每个Chunk里面是什么结构

每个Chunk由Chunk Header和Chunk Data组成：

```text
RTMP Chunk
├─ Basic Header：1～3字节
│  ├─ fmt：2 bit，决定后面的Message Header格式
│  └─ CSID：Chunk Stream ID，基础值或扩展值
├─ Message Header：0、3、7或11字节
├─ Extended Timestamp：条件存在，4字节
└─ Chunk Data：本Chunk携带的一段Message Payload
```

Basic Header中的CSID标识Chunk所属的逻辑Chunk通道。接收端按CSID分别保存上一次头部状态和正在重组的Message。Message Stream ID则标识`createStream`创建的NetStream：CSID解决“这一块应沿用哪组Chunk解析状态”，Message Stream ID解决“完整Message属于哪条发布或播放流”。

`fmt`决定Message Header携带多少新信息：

| fmt | Message Header长度 | 本次携带或继承的信息 |
|---:|---:|---|
| 0 | 11字节 | 完整时间戳、Message长度、类型和Message Stream ID |
| 1 | 7字节 | 时间戳差、Message长度和类型；继承Message Stream ID |
| 2 | 3字节 | 仅给出时间戳差；继承长度、类型和Message Stream ID |
| 3 | 0字节 | 继承当前CSID此前建立的头部状态，也常用于同一Message的后续Chunk |

当3字节时间戳字段写成`0xFFFFFF`时，Chunk Header后增加4字节Extended Timestamp，真正的时间戳或时间戳差放在其中。解析器必须按每个CSID独立保存历史字段，否则`fmt=1/2/3`无法恢复完整Message信息。

### 3.6 连接命令和媒体数据共用怎样的包装链

下表把“连接建立用了什么”和“数据发送用了什么”放在同一条包装链上比较：

| 要发送的内容 | Payload怎样产生 | RTMP Message类型 | 是否切成Chunk | 最终承载 |
|---|---|---|---|---|
| C0/C1/C2、S0/S1/S2 | 按握手固定结构填写 | 不使用Message | 不使用Chunk | TCP字节流 |
| `connect`、`createStream` | 命令名和参数经过AMF编码 | Command Message | 是 | TCP字节流 |
| `publish`、`play` | 命令名、流名等参数经过AMF编码 | Command Message | 是 | TCP字节流 |
| 视频帧 | 加入RTMP视频载荷字段 | Video Message | 是 | TCP字节流 |
| 音频帧 | 加入RTMP音频载荷字段 | Audio Message | 是 | TCP字节流 |
| 元数据 | 元数据对象经过AMF编码 | Data Message | 是 | TCP字节流 |
| Chunk大小、确认窗口等 | 按对应控制格式填写 | Protocol Control Message | 是 | TCP字节流 |

可以把整条关系记成两句：握手块直接走TCP；握手结束后，所有RTMP命令和业务数据都先成为Message，再成为Chunk，最后进入TCP。

### 3.7 接收端怎样从TCP字节流恢复Message

```text
TCP recv取得若干字节
  → 放入累积缓冲区
  → 读取Basic Header，取得fmt与CSID
  → 根据fmt和该CSID历史状态读取Message Header
  → 必要时读取Extended Timestamp
  → 按当前接收Chunk Size取得Chunk Data
  → 追加到“该CSID当前Message”的重组缓冲区
  → 累计Payload字节达到Message Length时输出完整Message
  → 根据Message Type ID交给命令、音频、视频、数据或控制解析器
```

一次`recv()`可能只得到半个Chunk Header，也可能同时得到多条Chunk。TCP只提供有序字节流，接收端必须按RTMP字段推进解析，不能用TCP读取次数判断Chunk或Message边界。

### 3.8 RTMP Chunk、TCP分段与IP分片的区别

- RTMP Chunk由RTMP发送程序按Chunk Size主动切分，具有RTMP Chunk Header；
- TCP分段由操作系统TCP协议栈根据最大报文段长度（Maximum Segment Size，MSS）、拥塞窗口和发送状态产生；
- IP分片由IP层在数据报超过链路MTU且允许分片时产生。

一条RTMP Chunk可能跨越多个TCP段，一个TCP段也可能包含多条RTMP Chunk。接收端TCP栈先恢复有序字节流，RTMP解析器随后恢复Chunk和Message。

## 4 RTMP缓冲、TCP重传与直播延迟

### 4.1 发送缓存、服务器转发队列和播放器缓存的延迟累积

RTMP端到端延迟由多段等待相加：

\[
T_{total}=T_{encode}+T_{sender}+T_{network}+T_{server}+T_{receiver}+T_{decode}+T_{playout}
\]

推流端可能积压编码帧和TCP发送缓冲；服务器可能为每个订阅者维护转发队列；拉流端可能缓存RTMP Message、解码帧和待显示帧。任何一段持续增长，画面都会逐渐落后于实时事件。

### 4.2 TCP丢包重传与队头阻塞对后续音视频消息的影响

一个TCP段丢失后，TCP接收端等待重传并保持有序交付。后续TCP段即使已经到达，也要等缺口补齐后才能交给RTMP解析器。

因此，RTMP层可能观察到一段时间没有新Chunk，重传完成后大量Chunk集中到达。RTP over UDP会把丢包直接暴露为序列号缺口；RTMP over TCP更常表现为瞬时停顿和延迟跳增。

### 4.3 Chunk大小对消息交错、传输开销和延迟的影响

Chunk Size较小时，大Video Message会更快让出RTMP应用层发送机会，音频和控制Message可以插入；代价是Chunk Header数量和解析次数增加。

Chunk Size较大时，头部开销和CPU处理次数减少；低带宽连接中，一次连续写入的大Chunk会让其他Message等待更久。Set Chunk Size只改变RTMP切块上限，不直接改变TCP MSS或IP MTU。

### 4.4 TCP可靠传输无法保证固定低延迟的原因

可靠表示TCP会重传缺失字节并按序交付。固定低延迟还要求发送队列受控、网络吞吐不低于媒体码率、服务器不过度缓存、播放器及时丢弃过期数据。

如果实时编码产生4 Mbit/s，而某段时间TCP实际只能发送2 Mbit/s，每秒会新增约2 Mbit待发送数据。即使没有永久丢包，队列仍会持续增长，直播延迟也会持续增加。

### 4.5 RTMP延迟增长、卡顿和断流的分层排查

按以下顺序记录运行数据：

```text
编码层：最新编码帧PTS与墙上时间的差
推流层：待发送RTMP Message数量和字节数
TCP层：发送缓冲、重传、往返时间（Round-Trip Time，RTT）和实际吞吐
服务器：输入时间戳与向订阅者发送时间
拉流层：最后收到的RTMP时间戳与当前播放时间
解码显示：待解码和待显示帧数量
```

连接仍然存在但延迟持续增长时，优先寻找不断增长的队列；连接直接断开时，再检查TCP I/O错误、服务器状态响应、心跳和超时。

## 5 裸UDP、自定义UDP与RTP over UDP的区别

### 5.1 UDP提供的数据报边界和不提供的媒体能力

UDP每次发送一个数据报，接收端一次成功的`recvfrom()`取得一个数据报；接收缓冲区容量小于数据报时，多出的部分会被截断，下一次读取无法补回。

UDP头只包含源端口、目标端口、长度和校验和。它没有视频编码类型、帧号、分片号、媒体时间戳和关键帧标记。应用把视频放入UDP后，必须自行规定接收端如何解释Payload。

### 5.2 裸UDP直接承载编码数据的发送与接收条件

裸UDP表示应用直接把已有字节交给UDP：

```text
H.264 Annex B字节 → UDP Payload → UDP → IP
```

这种方案只有在双方预先约定以下条件时才能工作：

- Payload固定为H.264 Annex B或其他明确格式；
- 一个数据报承载一个NAL、一个访问单元或任意字节片段；
- 数据报超过路径MTU时如何拆分；
- 收到数据后如何恢复边界；
- 丢失一包后从哪个位置重新同步；
- 时间戳由哪里提供。

若发送端把5000字节NAL直接交给UDP，而路径MTU只能承载约1500字节IP包，IP层可能进行分片。任一IP Fragment丢失，整个UDP数据报都无法交付应用。实时视频应在应用层主动把数据控制在路径MTU以内。

### 5.3 自定义UDP头中的类型、序号、时间戳和分片字段

自定义UDP协议通常在Payload前增加私有头：

```text
+--------+------+--------+----------+---------+-----------+-------------+
| Magic  | 版本 | 流类型 | 序列号   | 帧号    | 分片号/数 | 时间戳      |
+--------+------+--------+----------+---------+-----------+-------------+
| Payload长度   | 可选校验字段      | Payload……                         |
+-------------------------------+--------------------------------------+
```

- Magic和版本用于识别协议及兼容升级；
- 流类型区分视频、音频和控制数据；
- 序列号检测数据报丢失、乱序和重复；
- 帧号把多个分片归入同一帧；
- 分片号和总数确定重组是否完整；
- 时间戳确定采集或播放时间；
- Payload长度用于校验实际数据边界。

这些字段的字节序、位宽、回绕、超时和异常包策略都必须形成双方共同规范。只定义结构体而不定义状态机，仍会在丢包、重启和版本变化时产生歧义。

### 5.4 RTP over UDP增加的标准包头和媒体Payload格式

RTP over UDP采用标准RTP头和具体媒体Payload规范：

```text
H.264 NAL
  → 单NAL、聚合或FU-A Payload
  → RTP Header（PT、Sequence、Timestamp、SSRC）
  → UDP Header
  → IP Header
```

RTP解决序号、媒体时间、发送源和Payload格式标识；H.264/H.265等Payload规范解决NAL如何进入单包、聚合包和分片包。RTCP还可以报告丢包、抖动和同步映射。

RTP不会自动选择服务器、鉴权或建立点播会话。RTSP、SIP或应用配置负责告诉双方媒体地址、端口、Payload Type和编码参数。

### 5.5 大NAL单元在三种UDP方案中的分片方式

| 方案 | 大NAL的处理者 | 分片识别方式 |
|---|---|---|
| 裸UDP | 若应用不主动拆分，可能由IP层分片 | 应用看不到独立媒体分片字段 |
| 自定义UDP | 私有协议发送模块 | 帧号、分片号、总片数等私有字段 |
| RTP over UDP | RTP Payload打包模块 | H.264 FU-A或H.265 FU中的开始、结束和类型字段 |

接收端必须使用与发送端相同的重组规则。RTP FU解析器无法直接重组某个私有UDP头，自定义协议解析器也无法仅靠分片号还原FU-A中的NAL头。

### 5.6 丢包、乱序、重复包和超时处理责任的区别

裸UDP没有协议级序列号，应用只能依赖外部边界或编码启始码尝试恢复；它通常无法准确指出哪一个数据报丢失。

自定义UDP由应用依据自己的序列号和帧号处理，发送端、接收端、抓包工具和测试程序都要实现同一份规则。

RTP over UDP使用RTP Sequence Number检测缺口和重排，使用Payload分片字段判断NAL完整性。阶段2-10第8节已经解释重排序窗口和超时丢弃。RTP基础协议可以检测丢包，恢复动作仍取决于重传扩展或应用策略。

### 5.7 UDP数据报、RTP包、媒体分片与IP分片的边界

常见映射是一只UDP数据报承载一只RTP包：

```text
一个IP包
  └─一个UDP数据报
      └─一个RTP包
          └─一段媒体Payload
```

若RTP包超过路径MTU，IP层仍可能把它拆成多个IP Fragment。应用接收RTP包之前，IP层必须先完成IP Fragment重组。因此，发送端应让“IP头 + UDP头 + RTP头 + Payload”不超过实际路径MTU。

## 6 GB28181设备、平台、SIP信令与RTP媒体的分工

### 6.1 GB/T 28181-2022的适用范围和系统角色

GB/T 28181规定公共安全视频监控联网系统中的信息传输、交换和控制要求。当前现行版本为GB/T 28181-2022，2022年12月30日发布，2023年7月1日实施。[国家标准信息公共服务平台列出了标准状态与实施日期](https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=8BBC2475624A6C31DC34A28052B3923D)。

学习实现时常见三类角色：

- 设备：网络摄像机、网络视频录像机（Network Video Recorder，NVR）或编码设备，向平台注册并提供视频通道；
- 下级平台：汇聚本域设备，也可以作为级联节点向上级平台注册；
- 上级平台：查询下级资源、发起实时点播、录像查询和控制。

同一个系统组件可能同时承担SIP客户端、SIP服务器、RTP发送端和RTP接收端中的多个角色。

### 6.2 设备、下级平台与上级平台的连接关系

```text
摄像机/NVR ──REGISTER、MESSAGE、NOTIFY──> 下级平台
摄像机/NVR <──────INVITE、BYE────────── 下级平台
摄像机/NVR ─────────RTP媒体────────────> 媒体接收端

下级平台 ───────REGISTER、目录响应─────> 上级平台
下级平台 <────────INVITE、BYE────────── 上级平台
下级平台或设备 ───────RTP媒体──────────> 上级指定接收端
```

级联时，信令可以经过平台转发，媒体也可以由下级平台转发或按协商路径发送。排查必须分别记录SIP目的地址和SDP中的媒体目的地址。

### 6.3 SIP设备标识、域标识与通道标识

GB28181使用标准编码标识平台、设备和通道，工程中常见20位设备或通道编码，例如：

```text
平台ID：34020000002000000001
设备ID：34020000001320000001
通道ID：34020000001320000002
域ID：  3402000000
```

这些示例只用于观察长度和层级，实际值必须由部署平台分配。SIP URI通常组合为：

```text
sip:设备或平台ID@域ID
```

平台以ID定位逻辑资源，以IP和端口定位当前网络端点。设备重新联网后IP可以变化，逻辑ID应保持平台配置的一致性。

### 6.4 SIP负责注册和会话控制，RTP负责媒体传输

SIP消息负责：

- REGISTER注册与鉴权；
- MESSAGE承载心跳、目录和设备信息XML；
- INVITE携带SDP建立媒体会话；
- ACK确认INVITE成功响应；
- BYE结束已建立会话。

RTP负责把实际视频或音频送到SDP指定的媒体地址。SIP 200 OK只表明对应事务成功；若SDP IP、端口、网络路由或媒体发送状态错误，接收端仍然没有视频。

### 6.5 信令路径与媒体路径独立产生的网络问题

典型故障如下：

```text
设备到平台5060端口的SIP可达
  → REGISTER成功
  → INVITE与200 OK成功
  → SDP要求设备向另一台媒体服务器的端口发送RTP
  → 设备无法访问该媒体IP，或防火墙阻止UDP
  → 平台显示点播成功但始终没有画面
```

诊断时需要分别抓取SIP服务器和媒体服务器的流量。只查看SIP日志无法证明RTP已经发出或到达。

## 7 GB28181注册、心跳和设备目录交互流程

### 7.1 从设备注册到平台取得通道目录的完整流程

这一流程由设备和平台共同完成。设备先证明自己的身份并告诉平台“后续SIP消息应发到哪里”，注册成功后持续报告在线状态；平台需要通道列表时，再向已经注册的设备发起目录查询。

```text
第1步 设备 → 平台：第一次REGISTER注册请求
      设备提供自己的逻辑ID、SIP联系地址和希望保持注册的时长。
      这一次没有Authorization身份认证信息头，因为设备还没有拿到平台生成的nonce等鉴权参数。

第2步 设备 ← 平台：401 Unauthorized鉴权挑战
      401在首次注册中表示“请按我给出的参数证明身份”。
      平台在WWW-Authenticate身份认证挑战头中给出realm（认证域）、
      nonce（平台生成的一次性随机挑战值）和摘要算法等参数。

第3步 设备 → 平台：第二次REGISTER注册请求
      设备使用平台在第2步给出的参数和本地密码计算摘要，
      将结果放进Authorization头。平台验证成功后返回200 OK并保存注册绑定。

第4步 设备 → 平台：周期性Keepalive MESSAGE
      设备通过XML消息体报告自己仍然在线，平台返回200 OK并更新最后活跃时间。
      注册有效期将结束前，设备还要重新发送REGISTER续期。

第5步 设备 ← 平台：Catalog Query MESSAGE
      平台通过XML消息体请求设备目录。设备先返回200 OK，表示查询消息已经收到。

第6步 设备 → 平台：Catalog Response MESSAGE
      设备用新的MESSAGE返回通道列表，沿用第5步查询中的SN。
      平台每收到一条目录响应都返回200 OK，并累计目录项直到完整。
```

这里的`REGISTER`和`MESSAGE`都是SIP请求方法。`REGISTER`用于建立或更新“设备ID应该联系哪个SIP地址”的注册绑定；`MESSAGE`用于携带Keepalive、Catalog等GB28181业务XML。`401 Unauthorized`和`200 OK`是SIP响应：前者在首次注册中发起身份认证，后者确认对应SIP请求已经处理成功。

接收端在解析这些命令前，要先从网络数据中切出一条完整SIP消息。SIP消息的长度不固定，接收端依靠行结束标记、头部结束标记和`Content-Length`确定边界：

```text
消息起始位置
  → 读取到第一个\r\n：得到请求行或响应状态行
  → 继续逐行读取SIP头，每个头仍以\r\n结束
  → 读取到\r\n\r\n：确定整个SIP头已经结束
  → 解析Content-Length
  → 再读取Content-Length指定的消息体字节数
  → 得到一条完整SIP消息
  → 紧接着的下一个字节是下一条SIP消息的起点
```

单个`\r\n`只表示当前一行结束，下一行通常是`Via`、`From`等SIP头，不代表出现了下一条命令。连续的`\r\n\r\n`表示SIP头结束；如果`Content-Length: 0`，这条消息到这里结束；如果`Content-Length: 183`，接收端还必须继续取得183字节消息体，这183字节内部即使出现`\r\n`也不能提前结束。

通过UDP接收时，一次`recvfrom()`返回一个完整UDP数据报的Payload，UDP保留数据报边界，因此不存在TCP意义上的粘包。接收端从这个Payload的第一个字节开始解析一条SIP消息。IP层发生分片时，操作系统先完成IP重组，成功后才把完整UDP数据报交给SIP程序；缺少任一IP分片时，整个数据报无法交付。

通过TCP接收时，程序必须维护累积缓冲区。第一次消息从连接字节流的起点开始；以后每条消息的起点都由上一条消息的`\r\n\r\n + Content-Length`计算得到。例如一次`recv()`同时取得两条消息，解析器先取出第一条，把缓冲区剩余字节留作第二条；如果只收到半条，就继续读取，直到头部和指定长度的消息体全部到齐。

完整消息切出后，解析器才检查第一行。第一行以`REGISTER`、`MESSAGE`或`INVITE`等方法名开头时，它是一条SIP请求；以`SIP/2.0`开头时，它是一条401、200等SIP响应。方法名通过第一行第一个空格前的字段获得，解析器不会在整个缓冲区中到处搜索这些字母。

这六步的依赖关系为：第2步给出第3步计算身份摘要所需的参数；第3步成功后平台才有可靠的设备联系地址；第4步维持在线状态；第5步使用这个联系地址发送查询；第6步使用第5步的查询序号返回业务结果。[GB/T 28181—2022规定了基本注册的REGISTER、401、携带Authorization的REGISTER和200 OK流程](https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=8BBC2475624A6C31DC34A28052B3923D)。

### 7.2 第1步：第一次REGISTER提供设备身份、联系地址和注册有效期

设备启动、网络恢复或者当前注册尚未建立时，设备中的SIP代理向平台的SIP服务器发送第一次`REGISTER`。这一请求解决两个问题：声明要注册的设备身份；告诉平台以后应把SIP请求发送到设备的哪个IP和端口。

一条简化的首次注册请求如下：

```text
REGISTER sip:34020000002000000001@3402000000 SIP/2.0
Via: SIP/2.0/UDP 192.168.1.20:5060;branch=z9hG4bK-register-001
From: <sip:34020000001320000001@3402000000>;tag=device-tag-01
To: <sip:34020000001320000001@3402000000>
Call-ID: register-call-001@192.168.1.20
CSeq: 1 REGISTER
Contact: <sip:34020000001320000001@192.168.1.20:5060>
Expires: 3600
Content-Length: 0
```

这些头字段都服务于当前注册操作：

- 请求行中的URI指出负责接收注册的SIP服务器。服务器ID、域和地址来自设备的上级平台配置；
- `Via`写入设备发送SIP消息所用的传输方式、IP和端口。`branch`由设备为本次请求生成，平台用它匹配本次请求与响应；
- `From`和`To`中的SIP URI写入正在注册的设备国标ID及所属域。`From tag`由设备生成，用来区分端点产生的消息关系；
- `Call-ID`由设备生成，用来关联这一系列注册消息。后续鉴权REGISTER通常沿用它；
- `CSeq`由“递增序号 + 请求方法”组成。第二次REGISTER应提高序号，例如从`1 REGISTER`变为`2 REGISTER`；
- `Contact`给出平台后续联系设备时使用的SIP URI，其中的IP和端口应当是平台实际能够到达的地址；
- `Expires`的单位是秒，表示设备希望这条注册绑定保持多久。示例中的3600表示一小时，实际值由设备配置和平台策略共同决定；
- `Content-Length: 0`表示这条REGISTER没有消息体。

首次REGISTER不含`Authorization`头。Authorization是“身份认证信息”头，其中需要填写平台提供的`realm`和`nonce`。设备发送第1步时还没有收到这两个值，所以先发出不带Authorization的REGISTER，让平台通过第2步返回计算参数。

### 7.3 第2步：401响应通过WWW-Authenticate给出身份认证参数

平台收到首次REGISTER后，发现其中没有身份认证信息，便返回`401 Unauthorized`。在这个固定流程中，401的直接含义是“请使用下面的参数计算身份摘要后再次注册”，设备此时不应把它当成最终注册失败。

```text
SIP/2.0 401 Unauthorized
Via: SIP/2.0/UDP 192.168.1.20:5060;branch=z9hG4bK-register-001
From: <sip:34020000001320000001@3402000000>;tag=device-tag-01
To: <sip:34020000001320000001@3402000000>;tag=server-tag-01
Call-ID: register-call-001@192.168.1.20
CSeq: 1 REGISTER
WWW-Authenticate: Digest realm="3402000000", nonce="server-nonce-value", algorithm=MD5
Content-Length: 0
```

设备从响应中取得：

- `realm`：平台划定的认证域，由平台在`WWW-Authenticate`中给出；
- `nonce`：平台为本次认证生成的随机挑战值。平台保存或能够验证这个值，设备必须原样用于摘要计算；
- `algorithm`：平台要求使用的摘要算法，示例为MD5；
- 原请求的`Via`、`Call-ID`和`CSeq`：设备据此确认这条401回应的是第1步REGISTER。

`WWW-Authenticate`是平台发给设备的挑战参数，`Authorization`是设备在下一次请求中提交的计算结果。两者方向相反，并且通过`realm`和`nonce`衔接第2步与第3步。

### 7.4 第3步：第二次REGISTER用Authorization证明身份并建立注册绑定

设备收到401后，读取`realm`、`nonce`和`algorithm`，再从本地配置读取设备ID与注册密码。常见的无`qop` MD5摘要计算为：

\[
HA1=MD5(设备ID:realm:密码)
\]

\[
HA2=MD5(REGISTER:注册请求URI)
\]

\[
response=MD5(HA1:nonce:HA2)
\]

其中，冒号也是参与计算的ASCII字符。注册请求URI必须与Authorization中的`uri`一致；任何设备ID、realm、密码、nonce、请求方法或URI不一致，都会得到不同的`response`。如果平台的挑战中给出了`qop`，设备必须按照该挑战对应的摘要格式增加`cnonce`、`nc`和`qop`字段，不能继续套用上面的无`qop`公式。

设备随后发送第二次REGISTER：

```text
REGISTER sip:34020000002000000001@3402000000 SIP/2.0
Via: SIP/2.0/UDP 192.168.1.20:5060;branch=z9hG4bK-register-002
From: <sip:34020000001320000001@3402000000>;tag=device-tag-01
To: <sip:34020000001320000001@3402000000>
Call-ID: register-call-001@192.168.1.20
CSeq: 2 REGISTER
Contact: <sip:34020000001320000001@192.168.1.20:5060>
Authorization: Digest username="34020000001320000001",
               realm="3402000000",
               nonce="server-nonce-value",
               uri="sip:34020000002000000001@3402000000",
               response="计算得到的32位十六进制摘要",
               algorithm=MD5
Expires: 3600
Content-Length: 0
```

第二次REGISTER继续使用同一个`Call-ID`，提高`CSeq`，并为新的SIP事务生成新的`Via branch`。平台使用自己保存的设备密码和相同参数重新计算摘要；结果与`response`一致时，平台返回`200 OK`。

收到200 OK后发生的状态变化是：平台把设备逻辑ID映射到`Contact`中的SIP地址，并记录注册到期时间；设备记录注册已经成功以及下一次续期时间。平台之后发送Catalog Query等请求时，就能使用这条注册绑定找到设备。密码错误、realm或nonce抄错、URI不一致时，平台会再次返回401或拒绝注册，应优先逐字段比较第二次REGISTER的Authorization与第一次401中的挑战参数。

### 7.5 第4步：Keepalive MESSAGE报告在线状态，REGISTER负责注册续期

注册成功后，设备周期性发送SIP `MESSAGE`，并在消息体中放入GB28181的Keepalive XML。可扩展标记语言（Extensible Markup Language，XML）在这里用于表示命令类型、业务序号和设备ID。

```text
MESSAGE sip:34020000002000000001@3402000000 SIP/2.0
Via: SIP/2.0/UDP 192.168.1.20:5060;branch=z9hG4bK-keepalive-001
From: <sip:34020000001320000001@3402000000>;tag=device-tag-01
To: <sip:34020000002000000001@3402000000>
Call-ID: keepalive-call-001@192.168.1.20
CSeq: 1 MESSAGE
Content-Type: Application/MANSCDP+xml
Content-Length: 经过实际编码后的XML字节数

<?xml version="1.0" encoding="GB18030"?>
<Notify>
    <CmdType>Keepalive</CmdType>
    <SN>1</SN>
    <DeviceID>34020000001320000001</DeviceID>
    <Status>OK</Status>
</Notify>
```

这一消息中的对应关系为：

- SIP请求行、`Via`、`From`、`To`、`Call-ID`和`CSeq`负责把MESSAGE送到平台并匹配它的200 OK；
- `Content-Type`告诉平台消息体使用MANSCDP XML格式；
- `Content-Length`必须填写空行之后XML内容的实际字节数。字符编码会影响字节数，所以应当先完成编码，再计算长度；
- `CmdType=Keepalive`告诉GB28181业务解析器这是心跳；
- `SN`是设备生成的业务序号，用于区分业务消息；
- `DeviceID`指出谁在报告在线；`Status=OK`表示设备工作状态正常。

平台解析成功后返回SIP 200 OK，并更新该设备的最后活跃时间。这个200确认当前Keepalive MESSAGE已经被平台接收。设备是否在线由平台根据连续心跳与超时策略判断。

Keepalive维护业务在线状态，REGISTER续期维护注册绑定。设备应在`Expires`到期前重新发送REGISTER；只发心跳却不续期，平台仍可能删除设备ID到Contact地址的注册绑定。心跳周期、连续超时次数和续期提前量应读取设备与平台配置，运行时以双方实际配置和响应为准。

### 7.6 第5步：Catalog Query MESSAGE携带平台的目录查询条件

平台需要取得设备及其通道列表时，根据第3步保存的注册绑定找到设备地址，并向设备发送Catalog Query MESSAGE：

```text
MESSAGE sip:34020000001320000001@192.168.1.20:5060 SIP/2.0
Via: SIP/2.0/UDP 192.168.1.10:5060;branch=z9hG4bK-catalog-query-001
From: <sip:34020000002000000001@3402000000>;tag=server-tag-02
To: <sip:34020000001320000001@3402000000>
Call-ID: catalog-query-001@192.168.1.10
CSeq: 1 MESSAGE
Content-Type: Application/MANSCDP+xml
Content-Length: 经过实际编码后的XML字节数

<?xml version="1.0" encoding="GB18030"?>
<Query>
    <CmdType>Catalog</CmdType>
    <SN>100</SN>
    <DeviceID>34020000001320000001</DeviceID>
</Query>
```

平台负责生成`SN=100`并保存“SN 100正在等待目录响应”的请求状态。`CmdType=Catalog`要求对端查询目录，`DeviceID`指出查询哪个设备或下级域。设备收到并接受该SIP请求后，先返回SIP 200 OK。

这个200 OK只完成第5步的SIP传递确认，消息中不携带完整目录。设备需要整理通道数据，再通过第6步的新MESSAGE主动发送Catalog Response。因此，平台收到查询请求的200 OK后仍要保留`SN=100`的等待状态。

### 7.7 第6步：Catalog Response MESSAGE沿用SN返回一条或多条目录结果

设备准备好目录后，向平台发送新的MESSAGE。它的XML根节点从`Query`变为`Response`，`CmdType`仍为Catalog，`SN`沿用第5步的100，使平台能够把结果交给正在等待的那次查询。

```text
MESSAGE sip:34020000002000000001@3402000000 SIP/2.0
Content-Type: Application/MANSCDP+xml
Content-Length: 经过实际编码后的XML字节数

<?xml version="1.0" encoding="GB18030"?>
<Response>
    <CmdType>Catalog</CmdType>
    <SN>100</SN>
    <DeviceID>34020000001320000001</DeviceID>
    <SumNum>2</SumNum>
    <DeviceList Num="2">
        <Item>
            <DeviceID>34020000001320000001</DeviceID>
            <Name>入口摄像机</Name>
            <Status>ON</Status>
        </Item>
        <Item>
            <DeviceID>34020000001320000002</DeviceID>
            <Name>出口摄像机</Name>
            <Status>ON</Status>
        </Item>
    </DeviceList>
</Response>
```

`SumNum`表示本次查询总共有多少个目录项，`DeviceList Num`表示当前这条Response实际携带多少项。示例中两者都为2，所以一条MESSAGE就能返回完整结果。如果`SumNum=100`而当前`Num=20`，平台只能确认收到了其中20项，还要继续接收相同SN的后续Catalog Response。

平台每收到一条Response MESSAGE，先返回SIP 200 OK，随后按照`SN`找到第5步建立的查询状态，以唯一`DeviceID`累计目录项。当已取得的唯一目录项数量达到`SumNum`时，本次查询完成。目录为空时应沿六步顺序定位：先确认注册绑定存在，再确认Catalog Query到达设备、设备返回了查询的200、设备发出了相同SN的Response、Content-Length与XML实际字节数一致，最后检查平台是否因XML解析失败或DeviceID冲突丢弃目录项。

## 8 GB28181实时点播和媒体停止流程

### 8.1 INVITE携带SDP发起实时视频点播

平台选择一个通道后，向该通道对应的SIP URI发送INVITE。INVITE头建立SIP事务和对话，消息体中的SDP提出媒体接收条件：

```text
平台 → 设备：INVITE + SDP Offer
设备 → 平台：100 Trying（可选）
设备 → 平台：200 OK + SDP Answer
平台 → 设备：ACK
设备 → SDP协商地址：RTP媒体
```

INVITE操作的是逻辑通道ID。设备内部负责把该通道映射到摄像头、编码器或录像资源。

### 8.2 SDP协商媒体接收IP、端口、传输方式和Payload Type

简化SDP示例：

```sdp
v=0
o=34020000002000000001 0 0 IN IP4 192.168.1.20
s=Play
c=IN IP4 192.168.1.20
t=0 0
m=video 30000 RTP/AVP 96
a=recvonly
a=rtpmap:96 PS/90000
y=0100000001
```

- `c=`给出媒体接收IP；
- `m=video 30000`给出接收端口；
- `RTP/AVP`表示RTP媒体配置；
- `96`是动态Payload Type；
- `a=rtpmap:96 PS/90000`把96映射为90000Hz的PS载荷；
- `a=recvonly`表示发起方只接收媒体；
- `y=`携带媒体流SSRC相关标识。

设备应依据最终协商结果发送，平台也应记录本次会话的Call-ID、标签、SSRC、Payload Type、媒体IP和端口。

### 8.3 200 OK与ACK完成SIP会话建立

设备接受INVITE后返回200 OK。平台必须发送ACK确认该最终响应，随后SIP对话进入已确认状态。

INVITE、200 OK和ACK通过Call-ID、From tag、To tag及CSeq关联。ACK确认的是INVITE最终响应，不需要对BYE的200 OK再发送ACK。[RFC 3261说明了INVITE/200/ACK三步建立会话以及BYE结束会话](https://www.rfc-editor.org/info/rfc3261/)。

设备可能在发送200 OK后立即开始RTP，也可能在收到ACK后开始。接收端应在发送INVITE前或至少在回复协商完成前准备好媒体Socket，防止开头的PS包和关键帧被操作系统丢弃。

### 8.4 设备或平台按照SDP结果发送RTP媒体

媒体发送端读取编码帧，将其复用为PS，再切成RTP Payload并发往SDP指定地址。媒体接收端依据本次会话保存的端口、SSRC和Payload Type把RTP交给对应通道。

SIP信令和RTP媒体可以由不同线程或进程处理，但它们必须共享同一份会话状态。收到未知SSRC或未知端口的RTP时，接收端不能随意绑定到最近一次INVITE，应根据协商记录或明确的兼容策略匹配。

### 8.5 BYE与200 OK结束会话并释放媒体资源

会话任一方都可以在已建立对话内发送BYE：

```text
平台 → 设备：BYE
设备 → 平台：200 OK
```

收到BYE后，设备停止对应媒体发送；平台停止等待该会话RTP，并释放端口、RTP重排队列、PS解复用器和解码器。资源释放必须按Call-ID与tag定位具体会话，防止关闭同一通道的另一条并发点播。

### 8.6 INVITE成功但没有RTP媒体的排查顺序

```text
1. 检查200 OK和ACK是否完成，Call-ID与tag是否一致
2. 检查SDP中的c=IP和m=端口是否为设备可达地址
3. 检查UDP/TCP传输方式是否被双方同时支持
4. 在设备出口抓包，确认RTP是否实际发出
5. 在媒体服务器入口抓包，确认网络和防火墙是否放行
6. 检查PT、SSRC与会话映射是否导致接收端主动丢包
7. 检查RTP Payload是否能解析为约定的PS格式
```

先证明媒体包到达，再检查PS和视频解码。这样可以避免把网络不可达误判为编码器错误。

## 9 GB28181中MPEG-PS over RTP的媒体包装与解析

### 9.1 H.264或H.265基本流进入PES和MPEG-PS的过程

发送端的包装方向为：

```text
编码器输出H.264/H.265访问单元
  → 为视频数据建立分组基本流（Packetized Elementary Stream，PES），写入stream_id及PTS/DTS
  → 将PES放入PS Pack
  → 按需要写Pack Header、System Header和Program Stream Map
  → 形成连续MPEG-PS字节流
```

PES保存该路基本流及时间戳；Program Stream Map描述PS中包含的视频、音频类型；Pack Header提供PS层时钟信息。阶段2-8第5节已解释PES、PTS和DTS，本节只增加PS到RTP的路径。

### 9.2 MPEG-PS数据进入RTP Payload并通过UDP或TCP发送

PS复用器产生的字节可能超过单个网络包容量。RTP打包器按路径MTU和协商方式切取PS字节，给每片增加RTP头：

```text
PS字节片段
  → RTP Header（PT、Sequence、Timestamp、SSRC）
  → UDP数据报
  → IP包
```

使用TCP媒体传输时，仍需额外的长度边界或标准规定的封装方式从TCP字节流提取完整RTP包。TCP的`recv()`边界不能直接作为RTP包边界。

### 9.3 RTP序列号、时间戳与MPEG-PS内部时间信息的分工

- RTP Sequence Number按RTP包递增，用于网络排序和丢包检测；
- RTP Timestamp使用协商的90000Hz媒体时钟，关联一组媒体数据的发送时间；
- PES PTS表示编码帧计划显示时间；
- PES DTS表示需要提前解码的时间；
- PS中的系统时钟字段支持解复用和时钟恢复。

接收端先利用RTP序列号恢复PS字节顺序，再由PS解复用器读取PES时间戳。RTP Timestamp不能直接替代PES PTS/DTS，因为它们服务于不同层级。

### 9.4 接收端从RTP重排到PS解复用和视频解码的完整顺序

```text
UDP或TCP收到网络数据
  → 提取完整RTP包
  → 校验PT、SSRC和长度
  → 按RTP Sequence Number重排并处理缺口
  → 去掉RTP头，按序连接PS Payload
  → PS解复用器识别000001BA等起始结构
  → 解析Program Stream Map确定编码类型
  → 从PES中取出视频基本流和PTS/DTS
  → H.264/H.265解析器恢复NAL与访问单元
  → 解码器输出图像
```

每层只消费自己的头。RTP层不能跳过PS直接寻找所有NAL启始码，否则丢失PS轨道映射和PES时间信息。

### 9.5 RTP丢包对PS、PES、NAL和解码图像的逐层影响

一个RTP包丢失会在PS字节流中制造缺口。缺口可能落在：

- PS或PES头：当前包长度、流类型或时间戳无法可靠解析；
- Program Stream Map：后续轨道类型识别受到影响，直到新的有效映射到来；
- NAL数据：当前NAL残缺；
- 关键帧或参考帧：错误可能传播到后续预测帧。

接收端应在RTP层记录序列号缺口，在PS层寻找下一个可信起始结构重新同步，并把受损访问单元标记或丢弃。单纯连接缺口两侧字节可能产生伪起始码和错误长度。

## 10 RTMP、UDP方案与GB28181的选择和故障定位

### 10.1 RTMP直播推拉流与GB28181设备联网的使用边界

RTMP适合以流名向媒体服务器发布和订阅直播。它包含握手、命令、音视频Message与TCP多路复用，但不提供GB28181的设备目录、国标编码、级联和监控控制体系。

GB28181适合监控设备和平台联网。它先通过SIP管理设备与通道，再为每次点播建立独立媒体会话。只需要直播分发时使用RTMP较直接；需要设备注册、目录、级联和按通道点播时，GB28181提供完整业务规范。

### 10.2 裸UDP、自定义UDP和RTP over UDP的工程选择条件

| 方案 | 适用条件 | 主要代价 |
|---|---|---|
| 裸UDP | 封闭实验、固定小消息、双方完全受控 | 缺少序号、时间和标准分片，扩展困难 |
| 自定义UDP | 标准协议无法表达特定硬件或业务字段 | 必须维护规范、兼容性、抓包工具和异常状态机 |
| RTP over UDP | 实时音视频及跨实现互通 | 需要实现对应Payload格式、重排、时钟和会话协商 |

已有RTP Payload规范能够满足需求时，优先复用标准。私有协议只应增加确实无法由现有协议表达的业务能力。

### 10.3 控制通道成功但媒体通道失败的判断方法

RTMP中，TCP和`connect`成功后还要确认`createStream`及`publish/play`状态，随后确认Audio/Video Message实际流动。

GB28181中，REGISTER成功只表示设备登记；INVITE成功只表示媒体参数协商完成。必须继续检查媒体发送端是否产生RTP、网络是否送达、接收端是否接受PT/SSRC以及PS是否可解复用。

### 10.4 TCP可靠性、UDP实时性和应用缓冲的实际关系

TCP通过重传和有序交付保护完整字节流，丢包时可能产生队头阻塞。UDP允许后续数据报越过缺失数据继续到达，应用需要自行处理损坏和超时。

UDP协议本身也不保证低延迟。应用若配置500ms重排序等待和2秒播放缓存，端到端仍会增加对应等待。TCP应用若严格限制队列并在过载时丢弃过期视频，也可以控制延迟增长。实时性取决于传输行为和所有应用缓冲的共同结果。

### 10.5 从网络连接、协议会话、媒体拆包到解码显示的排查顺序

```text
网络层
  检查TCP是否连接、UDP是否到达、端口与防火墙是否正确

会话层
  RTMP检查握手、connect、createStream、publish/play状态
  GB28181检查REGISTER、MESSAGE、INVITE、ACK与BYE状态

传输层
  RTMP检查Chunk边界、Message长度和时间戳
  RTP检查PT、SSRC、Sequence、Timestamp和丢包
```
