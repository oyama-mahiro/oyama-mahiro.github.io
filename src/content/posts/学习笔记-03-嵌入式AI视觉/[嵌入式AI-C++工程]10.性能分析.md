# 阶段1-10 性能分析

性能分析不是看到程序慢就立刻改代码，而是先把“慢”转换成可以重复测量的问题，再用系统和程序内部的证据判断时间花在哪里。本阶段建立一条最基本的分析链路：确定指标、固定测试条件、建立基线、判断瓶颈、修改一个因素，然后在相同条件下复测。

本阶段不追求掌握所有性能工具。完成后，应当能够使用平均值、P50、P95和P99描述延迟，使用`top`或`htop`观察系统状态，使用`perf stat`观察程序整体行为，使用`perf record`和`perf report`定位CPU热点，并把这些结果整理成可以复现的测试报告。

## 1 性能分析到底要测什么

### 1.1 延迟、吞吐量和资源占用

性能不是单一数字。嵌入式视觉程序中最常见的指标包括：

- **延迟（latency）**：一个输入从进入系统到得到结果经历的时间，常用毫秒表示。
- **吞吐量（throughput）**：单位时间完成的任务数，例如每秒处理帧数（FPS）。
- **CPU利用率**：一段时间内CPU处于执行状态的比例。
- **内存占用**：程序实际驻留在物理内存中的数据量，以及是否持续增长。
- **队列深度**：某个时刻积压在队列中的任务数量。
- **丢弃数量**：实时系统为了避免延迟无限增加而丢弃的任务数量。

这些指标可能向不同方向变化。例如，将工作拆给更多线程后，吞吐量可能增加，但锁竞争和调度可能使P99延迟变差；摄像头始终以30 FPS输入，而处理线程只能完成20 FPS时，短时间内显示的处理吞吐量仍可能接近20 FPS，但队列会不断积压，端到端延迟越来越大。

因此不能只报告“平均耗时10 ms”或者“CPU占用80%”。至少要说明测量对象、输入规模、线程数以及这一数字描述的是单阶段耗时、端到端延迟还是吞吐量。

### 1.2 先确定问题再选择指标

性能分析前先把问题写成可以验证的形式：

| 原始描述 | 可以验证的问题 | 主要指标 |
|---|---|---|
| 程序很慢 | 单帧从输入到输出是否超过50 ms | 端到端P95、P99延迟 |
| 视频越来越卡 | 处理速度是否长期低于输入速度 | 输入/输出FPS、队列深度、队列等待时间 |
| CPU很高 | 哪些线程和函数消耗CPU时间 | 每线程CPU、`perf`热点 |
| 偶尔卡一下 | 少量请求是否远慢于大部分请求 | P95、P99、最大值及对应日志 |
| 优化有没有效果 | 相同条件下目标指标是否稳定改善 | 优化前后多次测量结果 |

一个合格的问题还应包含边界。例如，“在设备A上，使用模型B、1920×1080视频和两个推理线程连续运行5分钟，端到端P95小于50 ms，并且不丢帧”。目标越具体，后面越容易选择工具和判断结果。

## 2 一次处理的时间花在哪里

### 2.1 实际经过时间与CPU执行时间

**墙上时间（wall-clock time）**是现实世界实际经过的时间。程序执行计算、等待磁盘、等待锁或者被操作系统暂停时，墙上时间都继续增加。

**CPU时间（CPU time）**是CPU真正为进程或线程执行指令的累计时间，通常分为：

- 用户态CPU时间：执行应用程序和用户态库代码的时间。
- 内核态CPU时间：代表该进程执行系统调用、驱动和其他内核代码的时间。

Linux可以用`time`做一次粗略观察：

```bash
# real是墙上时间，user和sys分别是用户态、内核态CPU时间。
/usr/bin/time -v ./vision_app
```

如果单线程程序运行10秒，其中8秒等待I/O，那么墙上时间可能接近10秒，CPU时间却明显少于10秒。多线程程序则相反：四个线程各使用1秒CPU并且并行执行，墙上时间可能接近1秒，而累计CPU时间接近4秒。因此多线程程序的CPU时间可以大于墙上时间。

### 2.2 I/O等待、锁等待和队列等待

只知道墙上时间大于CPU时间还不能确定原因，需要继续区分等待发生在哪里：

- **I/O等待**：线程等待磁盘、网络、摄像头或设备返回数据。
- **锁等待**：线程准备执行，但获取互斥锁时被其他线程阻塞。
- **队列等待**：任务已经进入流水线，但正在等待上游生产空间或下游处理。
- **调度等待**：线程已经可以运行，但CPU正在执行其他任务。

需要注意，`top`中的`wa`是CPU统计口径下的I/O等待比例，不等于“当前进程准确等待I/O的时间”。锁等待和队列等待也不会自动出现在`perf`的CPU热点列表中，因为休眠线程没有持续执行指令。

因此要组合证据：系统CPU状态说明机器整体是否繁忙，`perf`说明CPU时间主要消耗在哪些函数，程序内部的队列和计时指标则说明任务在哪里等待。

### 2.3 端到端耗时与各阶段耗时

端到端延迟应从任务进入系统开始，到最终结果对外可用时结束。对于一个简化的视觉流水线，可以拆成：

```text
端到端延迟
= 输入等待
+ 解码或采集
+ 队列等待
+ 图像预处理
+ 模型推理
+ 后处理
+ 输出等待
```

只测`infer()`调用不能代表整个程序延迟。模型推理只有10 ms，但任务在推理队列中等待了80 ms时，用户感受到的延迟至少接近90 ms。

阶段1-6第5节已经介绍队列深度、等待时间和丢弃数量。本阶段应把这些队列指标与各处理阶段耗时放在同一份报告中，才能判断延迟来自执行还是积压。

## 3 如何正确记录和比较耗时

### 3.1 使用steady_clock测量持续时间

`std::chrono::steady_clock`是C++标准库中的单调时钟。单调时钟不会因为用户修改系统时间或网络校时而向后跳，适合测量一段操作持续了多久。它定义在`<chrono>`头文件中。

基本计时写法如下：

```cpp
#include <chrono>

using SteadyClock = std::chrono::steady_clock;

// 记录待测操作开始前的单调时间点。
const auto start_time = SteadyClock::now();

run_preprocess();

// 结束时间必须使用同一种时钟，二者相减得到持续时间。
const auto end_time = SteadyClock::now();
const double elapsed_ms =
    std::chrono::duration<double, std::milli>(end_time - start_time).count();
```

`duration<double, std::milli>`表示以毫秒为单位、使用`double`保存的时间段，`count()`返回其中的数值。这里得到的是调用线程看到的墙上耗时，其中可能同时包含执行和等待；它不是CPU时间。

不要在每一帧的关键路径中同步打印大量日志。终端输出、格式化和文件写入也会产生耗时。更稳妥的做法是先把数值写入预分配的内存结构，测试结束后统一计算和输出。

### 3.2 预热、正式采样与重复测试

程序刚启动时经常会执行只发生一次的工作，例如：

- 装载动态库和模型文件；
- 分配内存并建立缓存；
- 首次创建线程；
- 推理引擎进行图优化或初始化设备；
- CPU频率从低功耗状态逐步升高。

如果目标是测量稳定运行性能，应将测试分成两个阶段：

1. **预热阶段**：运行固定次数，但不计入正式统计。
2. **正式采样阶段**：记录每个样本，并保证测试持续时间足够长。

预热次数不能机械固定为30次。模型初始化很重时可按时间预热；设备温度持续上升时还要观察长期运行是否发生降频。正式测试也不要只运行一次，建议用多次独立运行观察结果波动。

### 3.3 固定影响测试结果的条件

优化前后至少固定并记录：

- 硬件型号、CPU架构、内存和加速器型号；
- 操作系统、内核、编译器、依赖库和程序版本；
- CMake构建类型与编译选项；
- 模型、输入分辨率、编码格式和数据集；
- 线程数、队列容量、批大小和并发量；
- 预热方式、样本数、测试时长和重复次数；
- CPU调频器、频率上下限、温度和后台负载。

性能测试通常使用接近发布配置的优化构建，而不是`Debug`构建。为了让`perf`仍能看到函数名和调用栈，可以使用`RelWithDebInfo`并保留栈帧：

```bash
# RelWithDebInfo通常同时启用优化并保留调试符号。
cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build -j
```

如果项目使用GCC或Clang，可以为性能分析构建额外加入`-fno-omit-frame-pointer`。它有助于调用栈展开，但也可能轻微改变最终性能，因此报告中必须记录该选项，并确保前后测试使用相同构建方式。

### 3.4 查看和控制CPU频率

Linux的CPU频率缩放子系统称为**CPUFreq（CPU Frequency Scaling）**。它通常由三部分协作：调频驱动与硬件通信，调频器（governor）决定采用怎样的频率策略，`sysfs`向用户空间暴露当前策略和限制。

先安装并查看`cpupower`信息：

```bash
# Ubuntu中工具版本通常应与当前内核匹配。
sudo apt install linux-tools-common linux-tools-$(uname -r)

# 查看驱动、硬件频率范围、当前策略、可用调频器等信息。
cpupower frequency-info

# 每秒刷新一次内核报告的当前频率；该值不一定等于硬件瞬时真实频率。
watch -n 1 'grep . /sys/devices/system/cpu/cpufreq/policy*/scaling_cur_freq'
```

多核CPU不一定每个核心独立调频。内核使用`policy0`、`policy1`等**调频策略对象**管理一组共享频率策略的CPU，尤其在大小核或多个CPU簇的嵌入式平台上，不能只检查`cpu0`：

```bash
# related_cpus显示同属一个调频策略的CPU。
grep . /sys/devices/system/cpu/cpufreq/policy*/related_cpus

# 查看每个策略当前使用的驱动和调频器。
grep . /sys/devices/system/cpu/cpufreq/policy*/scaling_driver
grep . /sys/devices/system/cpu/cpufreq/policy*/scaling_governor

# 查看每个策略允许设置的调频器，以及当前频率上下限，单位通常为kHz。
grep . /sys/devices/system/cpu/cpufreq/policy*/scaling_available_governors
grep . /sys/devices/system/cpu/cpufreq/policy*/scaling_min_freq
grep . /sys/devices/system/cpu/cpufreq/policy*/scaling_max_freq
```

为了减少短测试中动态调频造成的波动，可以临时选择`performance`调频器：

```bash
# performance请求在当前策略上限范围内使用较高性能状态。
# 修改系统调频策略需要管理员权限。
sudo cpupower frequency-set -g performance
```

`performance`不等于“CPU永远精确固定在最高标称频率”。实际频率仍可能受硬件控制、睿频、功耗限制和温度保护影响。如果确实要限制测试频率，可以设置策略允许的最低和最高频率：

```bash
# 把允许范围限制为1.8 GHz；硬件和驱动不支持时会失败或取邻近值。
sudo cpupower frequency-set -d 1.8GHz -u 1.8GHz
```

另一种方法是切换到`userspace`调频器后用`-f`请求具体频率，但并非所有驱动和平台都提供该调频器：

```bash
# 只有scaling_available_governors中存在userspace时才能这样使用。
sudo cpupower frequency-set -g userspace
sudo cpupower frequency-set -f 1.8GHz
```

修改前必须记录原来的调频器、最小频率和最大频率，测试结束后恢复原策略。设置通常不是永久配置，也可能被电源管理服务重新覆盖。不要为了得到好看的数字禁用温度保护；如果长时间运行后频率下降，应把温度或功耗限制作为测试结果的一部分，而不是强行绕过保护机制。

内核文档还特别说明，`scaling_cur_freq`在很多平台上表示驱动最近请求的频率，不一定是硬件此刻真正运行的精确频率。因此它适合记录调频状态和趋势，不应被当作高精度测量仪器。详细字段含义参见[Linux内核CPUFreq文档](https://docs.kernel.org/admin-guide/pm/cpufreq.html)，`cpupower`选项参见[Ubuntu cpupower frequency-info手册](https://manpages.ubuntu.com/manpages/noble/man1/cpupower-frequency-info.1.html)和[frequency-set手册](https://manpages.ubuntu.com/manpages/noble/man1/cpupower-frequency-set.1.html)。

## 4 平均值为什么不够

### 4.1 P50、P95和P99表示什么

平均值把所有样本相加后除以样本数量。它能描述整体水平，却可能隐藏少量特别慢的请求。例如有100帧，其中99帧耗时10 ms，1帧耗时1000 ms，平均值只有19.9 ms，但用户仍会明显感受到一次接近1秒的卡顿。

**百分位数（percentile）**表示有多少比例的样本不超过某个值：

- P50：约50%的样本不超过该值，常用来描述典型情况。
- P95：约95%的样本不超过该值，开始反映较慢的一部分请求。
- P99：约99%的样本不超过该值，常用来观察尾部延迟。

分位数不是“最慢的那一次”。如果需要排查偶发严重卡顿，还应记录最大值、发生时间、输入编号和对应系统日志。

### 4.2 如何计算延迟分位数

下面采用容易理解的**最近秩（nearest-rank）**方法：将样本从小到大排序，P95取排序后第`ceil(0.95 × N)`个样本。不同统计库可能使用插值等其他算法，样本较少时结果会不同，因此报告应保持同一种计算方法。

```cpp
#include <algorithm>
#include <cmath>
#include <numeric>
#include <stdexcept>
#include <vector>

// 输入是同一指标的一组毫秒样本；函数复制并排序，不改变调用方原数据。
// percentile应位于[0, 100]，返回最近秩定义下的百分位数。
double calculate_percentile_ms(std::vector<double> samples_ms,
                               double percentile)
{
    if (samples_ms.empty()) {
        // 没有样本时不存在百分位数，交给调用方决定如何报告失败。
        throw std::invalid_argument("samples_ms must not be empty");
    }
    if (percentile < 0.0 || percentile > 100.0) {
        throw std::invalid_argument("percentile must be in [0, 100]");
    }

    std::sort(samples_ms.begin(), samples_ms.end());

    // 最近秩公式得到的是从1开始的位置，转换为vector从0开始的下标。
    const std::size_t rank = static_cast<std::size_t>(
        std::ceil((percentile / 100.0) * samples_ms.size()));
    const std::size_t index = rank == 0 ? 0 : rank - 1;
    return samples_ms[index];
}

// 输入单位是毫秒，返回值也保持毫秒。
double calculate_average_ms(const std::vector<double>& samples_ms)
{
    if (samples_ms.empty()) {
        throw std::invalid_argument("samples_ms must not be empty");
    }
    const double total_ms =
        std::accumulate(samples_ms.begin(), samples_ms.end(), 0.0);
    return total_ms / static_cast<double>(samples_ms.size());
}
```

这段代码要求调用方先完成预热，再只把正式样本传入。输出报告时至少同时给出样本数、平均值、P50、P95和P99，避免单个数字失去上下文。

### 4.3 样本数量与测试稳定性

100个样本的P99基本落在最慢的一个样本附近，容易受到偶然噪声影响；样本数量越少，越不能精细描述高分位数。选择样本数时应考虑输入速率和测试持续时间，而不是机械追求一个固定数字。

判断结果是否稳定可以采用以下方法：

1. 每次测试使用相同输入和配置。
2. 独立执行多轮测试，而不是只重复统计同一批数据。
3. 同时查看每轮结果和整体分布。
4. 如果各轮差异明显，检查温度、CPU频率、后台任务和输入变化。

不能因为某一轮结果最好就把它当作优化结果。报告可以使用多轮中位数，也可以列出每轮P95，但必须提前确定规则并对优化前后保持一致。

## 5 使用top和htop观察系统状态

### 5.1 查看进程、线程和每个CPU核心

`top`和`htop`用于观察系统在一段时间内的运行状态。常用命令如下：

```bash
# 启动top后按1可展开每个逻辑CPU，按H可显示线程。
top

# 直接显示目标进程中的所有线程；PID替换为真实进程号。
top -H -p PID

# htop提供交互式列表和每核视图，通常需要单独安装。
htop
```

先看机器整体是否繁忙，再看目标进程，最后展开线程。某个线程持续接近一个逻辑CPU的上限，而其他核心较空，通常说明该阶段没有有效并行；所有相关线程都不高但任务延迟很大，则应检查I/O、锁和队列等待。

### 5.2 正确理解超过100%的CPU占用

Linux工具存在不同显示口径。在`top`常见的Irix模式中，一个线程占满一个逻辑CPU可显示为100%，四个线程同时占满四个逻辑CPU时，一个进程可能接近400%。切换显示模式或使用其他工具后，也可能把整台机器归一化为100%。

因此看到250%不能直接认为统计错误，它大致表示进程正在消耗约2.5个逻辑CPU的计算能力。报告中应写明CPU逻辑核数量和工具口径，不要只截图一个百分比。

### 5.3 查看用户态、内核态和I/O等待

`top`的CPU汇总行中常见字段包括：

- `us`：用户态执行时间比例。
- `sy`：内核态执行时间比例。
- `id`：空闲比例。
- `wa`：CPU统计口径下等待I/O完成的比例。

`us`很高时可以继续用`perf`找用户态热点；`sy`异常高时检查频繁系统调用、内存映射、网络或驱动交互；`wa`高时检查存储和设备I/O。但这些只是方向，不是根因证明。

内存列中，`VIRT`是进程可见的虚拟地址空间规模，包含尚未驻留、文件映射和共享库等区域；`RES`是当前驻留在物理内存中的部分。仅凭`VIRT`很大不能认定内存泄漏，应结合`RES`趋势、队列深度和阶段1-8的内存检查工具判断。

### 5.4 区分CPU利用率与系统负载

Linux负载平均值（load average）通常反映可运行任务以及部分不可中断等待任务的数量趋势，不是CPU使用百分比。四核机器负载为4可能表示CPU接近满载，也可能混有I/O等待任务；必须与每核CPU、`wa`和任务状态一起判断。

常见误判包括：

- CPU利用率低，所以程序一定没有性能问题；实际上线程可能长期等待锁。
- 负载高，所以CPU一定是瓶颈；实际上大量任务可能处于不可中断I/O等待。
- CPU利用率高，所以必须降低CPU；如果吞吐量达到目标且温度允许，高利用率可能只是资源被充分使用。

## 6 使用perf stat观察程序整体表现

### 6.1 perf stat的基本使用方法

`perf`是Linux性能分析工具集合。`perf stat`运行目标程序，并统计这次执行期间的时间和性能计数器。先确认工具可用：

```bash
# 显示perf版本；Ubuntu工具通常应与正在运行的内核匹配。
perf --version

# 查看当前设备支持的事件，嵌入式ARM与x86设备可能不同。
perf list

# 连续执行程序5次，输出每次统计及波动信息。
perf stat -r 5 -- ./build/vision_app
```

`--`用于分隔`perf`选项和目标程序命令。若程序需要参数，应继续写在可执行文件后面。默认事件已经足够进行第一轮观察，不必一开始收集几十种硬件事件。

### 6.2 时间、周期和指令数量

常见统计项包括：

- `task-clock`：任务占用CPU的累计时间。
- `cycles`：CPU周期数。
- `instructions`：退休指令数，即CPU已经完成的指令数量。
- `instructions per cycle`或IPC：平均每个周期完成的指令数。
- `context-switches`：上下文切换次数。
- `cpu-migrations`：任务在CPU之间迁移的次数。

可以明确请求常用事件：

```bash
# 事件是否可用取决于处理器和内核；失败时先用perf list检查。
perf stat -r 5 \
  -e task-clock,cycles,instructions,context-switches,cpu-migrations \
  -- ./build/vision_app
```

IPC低不一定说明代码差。访存等待、分支依赖、硬件架构和任务类型都会影响IPC；不同处理器之间也不能只靠IPC直接比较。正确做法是结合代码变化和其他事件解释。

### 6.3 分支预测和缓存事件

分支和缓存事件可帮助判断CPU为什么没有持续完成指令：

```bash
# 观察分支预测和缓存访问；部分平台不支持其中某些通用事件。
perf stat \
  -e branches,branch-misses,cache-references,cache-misses \
  -- ./build/vision_app
```

`branch-misses`表示预测错误的分支次数；`cache-misses`表示通用缓存未命中的统计，但不同处理器对该通用事件的映射可能不同。优化前后应在同一台设备、相同配置下比较，不要把不同CPU的原始计数直接放在一起下结论。

### 6.4 硬件事件与权限限制

`perf`可能遇到三类限制：

1. CPU性能监控单元不支持某个事件。
2. 系统的`perf_event_paranoid`安全策略限制普通用户采样。
3. 同时请求的事件超过硬件计数器数量，内核需要分时复用并缩放结果。

排查时先减少事件数量，再检查：

```bash
# 查看系统对普通用户使用perf的限制等级。
cat /proc/sys/kernel/perf_event_paranoid

# 查看事件是否由当前硬件支持。
perf list
```

不要为了方便长期关闭系统安全限制。在个人测试设备上确实需要调整时，也应理解影响、记录修改并在测试后恢复。`perf stat`输出出现较低的“计数运行比例”时，说明分时复用可能使结果误差增大，应减少同一轮采集的事件。

`perf stat`的命令和计数范围可参考[perf-stat Linux手册](https://www.man7.org/linux/man-pages/man1/perf-stat.1.html)。

## 7 使用perf定位耗时最多的函数

### 7.1 perf record如何进行采样

`perf record`进行**采样分析**：程序运行期间周期性记录CPU当时正在执行的位置，出现次数较多的位置通常消耗了较多CPU时间。它不是记录每一次函数调用的完整跟踪器，因此短函数可能一次也没有被采到，百分比也存在统计误差。

```bash
# -g请求同时记录调用栈，结果默认写入当前目录的perf.data。
perf record -g -- ./build/vision_app
```

采样本身会增加开销。先使用默认参数获得方向，只有确有需要时才调整采样频率或调用栈方式，并保证优化前后使用相同参数。

### 7.2 使用perf report查看热点

`perf report`读取`perf.data`并汇总样本：

```bash
# 打开交互式热点报告。
perf report

# 输出文本报告，适合保存到测试记录或在无交互终端中查看。
perf report --stdio
```

报告中的`Overhead`表示某个符号包含了多少采样比例，不等于该函数精确占用了同样比例的墙上时间。先观察采样主要落在哪个程序或动态库，再展开调用链确认该函数由谁调用。

### 7.3 调用栈、调试符号和帧指针

如果报告中大量出现十六进制地址、`[unknown]`或者调用栈断裂，应检查：

- 可执行程序和动态库是否保留与当前二进制匹配的调试符号；
- 是否使用了过度裁剪符号的发布文件；
- 编译器是否省略了栈帧指针；
- 目标平台是否支持当前调用栈展开方式。

对GCC或Clang项目，可使用优化加调试符号，并考虑`-fno-omit-frame-pointer`。也可以使用DWARF调用栈：

```bash
# DWARF方式记录更多栈信息，但文件大小和采样开销通常更高。
perf record --call-graph dwarf -- ./build/vision_app
```

不能为了让报告好看就改用`-O0`测正式性能，因为无优化构建的函数结构和耗时与发布版本差异很大。

### 7.4 编译优化和动态库带来的影响

优化编译可能把小函数内联到调用者、合并相同代码或者重新排列指令，因此源码中的函数边界不一定与报告完全一致。动态库也可能只显示库内符号；如果库已被`strip`且没有匹配符号文件，只能看到有限信息。

阶段1-9第8～9节已经介绍动态库、ELF和符号检查。性能分析时需要保存与被测版本完全匹配的可执行文件、动态库和符号文件，否则可能把地址解释成错误的函数。

`perf record`和`perf report`的完整选项分别参见[perf-record手册](https://www.man7.org/linux/man-pages/man1/perf-record.1.html)和[perf-report手册](https://www.man7.org/linux/man-pages/man1/perf-report.1.html)。

## 8 判断程序到底卡在哪里

### 8.1 CPU计算瓶颈

CPU计算瓶颈常见证据是：

- 一个或多个CPU核心长期繁忙；
- 目标线程大部分时间处于运行状态；
- `perf record`样本集中在少数计算函数；
- 减少输入规模或计算量后，延迟和CPU时间同步下降。

此时可以检查算法复杂度、不必要的内存复制、重复格式转换、没有生效的并行化以及缓存访问方式。仍应先定位热点再改代码，不能因为某个函数“看起来复杂”就认定它是瓶颈。

### 8.2 I/O等待瓶颈

I/O瓶颈可能表现为CPU不满、线程长期睡眠、`wa`升高或者读取接口耗时很长。需要进一步区分磁盘、网络、摄像头和其他设备，因为它们的验证工具不同。

可以临时使用已在内存中的固定输入进行对照：如果去掉实际读取后计算阶段稳定，而端到端延迟显著下降，说明I/O路径值得继续检查。但这只是对照实验，不能证明具体是驱动、介质、网络还是应用缓冲策略造成问题。

### 8.3 锁竞争和线程等待

锁竞争常见现象是增加线程后吞吐量没有提高，CPU也没有完全利用，线程却频繁等待同一临界区。首先检查阶段1-5介绍的锁范围：是否在持锁时执行推理、日志、文件I/O或大块复制。

CPU采样报告可能只显示持锁线程执行的代码，不会把睡眠等待者直接显示成热点。因此要结合线程状态、上下文切换和应用内部锁等待计时。不要看到`pthread_mutex_lock`就直接归因；它可能只是调用频繁，也可能确实发生长时间竞争，需要比较等待时长和调用次数。

### 8.4 队列积压和背压

队列瓶颈的证据链应包含：

1. 输入速率长期高于输出速率。
2. 队列深度持续上升或长期接近容量上限。
3. 队列等待时间使端到端延迟增加。
4. 阻塞、拒绝或丢弃策略开始频繁触发。

队列积压不是单纯的“队列代码慢”，真正瓶颈通常在下游消费者。要继续测量各消费者阶段，确定是预处理、推理、后处理还是输出跟不上。

## 9 建立可靠的优化流程

### 9.1 先测量并保存基线

**基线（baseline）**是修改前、在明确测试条件下取得的一组性能结果。基线至少应保存：

- 代码版本和构建配置；
- 硬件、内核、CPU调频信息和温度；
- 输入、线程、队列和模型参数；
- 平均值、P50、P95、P99、吞吐量和队列指标；
- `perf stat`命令与原始输出；
- `perf report`的主要热点。

原始数据应保留，不能只复制最终结论。将来统计方法变化时，原始样本仍可重新计算。

### 9.2 一次只修改一个因素

基线建立后，先提出带有证据的假设，例如：“`perf`显示预处理中的整帧深复制占用大量样本，因此去掉所有权上不需要的`cv::Mat::clone()`可能降低预处理延迟和缓存访问。”

一次同时改线程数、模型、图片尺寸和复制方式，即使性能变好也无法知道原因。最好一次只改变一个主要因素，并记录代码差异；相互依赖的修改必须一起完成时，也要明确它们构成同一个实验组。

### 9.3 使用相同条件重新测试

复测应复用基线的命令、输入和环境。特别检查：

- CPU调频器和频率限制是否一致；
- 设备是否因长时间运行而升温降频；
- 后台更新、日志压缩或其他程序是否干扰测试；
- 测量顺序是否总让其中一个版本处于更热或更冷的状态。

条件难以完全固定时，可以交替运行旧版本和新版本，而不是先连续测完旧版本再测新版本。报告中应诚实记录无法控制的因素。

### 9.4 同时检查性能与结果正确性

性能提高不能以结果错误为代价。去掉图像复制后，必须确认后续线程不会在原缓冲区被覆盖后继续访问；减少锁范围后，必须重新检查数据竞争；降低图像尺寸或替换模型则已经改变了任务定义，不能直接称为同条件代码优化。

最低验收包括：

- 测试输入全部处理完成或按设计丢弃；
- 输出数量、尺寸、类型和关键数值正确；
- 没有新增崩溃、Sanitizer错误和资源泄漏；
- 目标性能指标在多轮测试中稳定改善；
- 其他关键指标没有出现不可接受的退化。

## 10 在主项目中完成性能分析

### 10.1 增加各处理阶段的计时

主项目不需要重新实现一个性能测试程序。应在现有采集、预处理、推理和后处理路径中记录时间点。每个任务至少保存：

```cpp
#include <cstddef>
#include <cstdint>

struct FrameTiming {
    // frame_id用于把耗时、输出结果和异常日志对应到同一帧。
    std::uint64_t frame_id = 0;

    // 所有时间都使用毫秒；字段只记录正式测试阶段的样本。
    double queue_wait_ms = 0.0;
    double preprocess_ms = 0.0;
    double inference_ms = 0.0;
    double postprocess_ms = 0.0;
    double end_to_end_ms = 0.0;

    // 入队时的深度用于观察积压趋势，不等同于该帧等待的任务数。
    std::size_t queue_depth_on_push = 0;
};
```

该结构只定义数据含义，不规定流水线实现。时间点必须使用同一种单调时钟；端到端起点应放在输入真正进入系统的位置，而不是推理开始位置。跨线程传递任务时，要把任务的入队时间和最初输入时间一起传递，不能在消费者线程中重新创建起点。

### 10.2 统计分位数和队列指标

测试结束后生成CSV或Markdown报告。建议每帧原始记录包含：

```text
frame_id,queue_wait_ms,preprocess_ms,inference_ms,postprocess_ms,end_to_end_ms,queue_depth,dropped
```

汇总部分对每个耗时字段计算平均值、P50、P95和P99，并额外输出总帧数、成功帧数、丢弃帧数、测试持续时间、吞吐量、平均队列深度和最大队列深度。

丢弃帧不能从延迟统计中悄悄消失。实时策略允许丢帧时，应分别报告成功任务的延迟分布和丢弃比例，否则可以通过大量丢弃慢任务制造虚假的低延迟。

### 10.3 使用top和perf建立基线

推荐的基线顺序是：

1. 记录CPU型号、逻辑核、调频策略、频率限制和温度。
2. 固定输入、线程数、队列容量和预热方式。
3. 使用`top -H -p PID`观察线程是否均衡以及是否存在明显等待。
4. 使用`perf stat -r 5`记录整体计数。
5. 使用`perf record -g`采样一次有代表性的稳定运行区间。
6. 保存`perf report --stdio`结果和程序内部指标。

若主程序持续运行，可以让`perf stat`或`perf record`附加到进程：

```bash
# 附加到已运行进程，按Ctrl+C结束统计；PID替换为目标进程号。
perf stat -p PID

# 采样已运行进程的CPU热点，按Ctrl+C后生成perf.data。
perf record -g -p PID
```

附加前应确认PID正确，并记录采样开始和结束时间，以便与应用日志对齐。

### 10.4 定位并修改一个真实热点

从`perf report`样本占比高的函数开始，但必须回到源代码确认调用条件和数据规模。一个适合本阶段的真实优化是检查预处理路径中的不必要深复制：

```cpp
// clone()会复制完整像素缓冲区。只有后续必须独立拥有并修改数据时才需要它。
cv::Mat owned_frame = input_frame.clone();
preprocess(owned_frame);
```

如果生命周期分析证明`input_frame`在预处理完成前始终有效，而且预处理不会修改它，可以把接口改为只读引用并去掉复制。`cv::Mat`的浅拷贝、深拷贝和跨线程生命周期已经在阶段1-3第3～6节讲过，不能只为性能删除复制而忽略所有权。

修改后预期看到的不是所有指标都变好，而是与假设对应的指标发生变化，例如预处理CPU时间下降、相关复制函数样本减少、缓存访问减少或端到端分位数降低。

### 10.5 生成优化前后对比报告

报告可使用下面的结构：

| 项目 | 优化前 | 优化后 | 说明 |
|---|---:|---:|---|
| 平均端到端延迟 |  |  | ms |
| P50端到端延迟 |  |  | ms |
| P95端到端延迟 |  |  | ms |
| P99端到端延迟 |  |  | ms |
| 吞吐量 |  |  | FPS |
| 最大队列深度 |  |  | 个任务 |
| 丢弃比例 |  |  | % |
| task-clock |  |  | `perf stat`原始口径 |
| cycles / instructions |  |  | 同设备同事件比较 |
| 主要热点 |  |  | `perf report`函数与样本占比 |

表格前面写清硬件、频率策略、温度范围、输入、线程数、样本数和命令，表格后面说明修改内容、为什么预期它影响这些指标，以及正确性检查结果。不要只写“提升20%”而不提供原始条件和数值。
