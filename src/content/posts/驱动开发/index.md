# [驱动开发] Linux 驱动入门

把一颗器件接到 Linux 开发板上，先要回答四个问题：**硬件怎样连接，内核怎样知道它存在，哪个驱动负责它，应用从哪里使用它**。本文用“给 RK3588 底板增加一颗 I2C 实时时钟（RTC）”贯穿这条链，再说明串口、网口、摄像头等设备哪里相同、哪里不同。读完应能判断一项需求需要改设备树、内核配置、驱动代码，还是用户空间。

本文讨论使用设备树的嵌入式 Linux 板卡。示例中的控制器编号和引脚组只是演示位置；真正修改时，以当前板子的原理图、实际启动的设备树和正在编译的内核源码为准。

## 1 一颗器件进入系统，要经过哪几层

先看 RTC 的完整路径：

```text
原理图：RTC 的 SDA/SCL 接到 SoC 的某一路 I2C，还有电源和可能的中断
    ↓
设备树：启用该 I2C 控制器，在它下面描述 RTC 型号和地址
    ↓
驱动：控制器驱动发送 I2C 时序；RTC 芯片驱动理解时间寄存器
    ↓
RTC 子系统：向用户空间提供 /dev/rtcN 等标准接口
    ↓
应用：用 hwclock 或 RTC 接口读写时间
```

**控制器与外设是两个对象。** SoC 内的 I2C 控制器负责在 SDA/SCL 上收发数据；焊在板上的 RTC 才知道哪个寄存器保存秒、分钟和日期。控制器驱动正常，只能证明总线有机会工作；RTC 还要有正确的供电、地址、设备描述和芯片驱动。类似地，网口通常有 MAC 与 PHY，SPI 有控制器与外接闪存。

把一次“读取时间”拆开，就能看清两份驱动的边界。用户程序向 RTC 子系统请求时间；PCF8563 驱动决定先读哪几个寄存器、怎样把芯片保存的数值换算成年月日；I2C 核心把这次传输交给 RK3588 的 I2C 控制器驱动；控制器驱动操作 SoC 寄存器，在物理引脚上产生起始信号、地址和数据。传回的数据再沿反方向交给 RTC 驱动解释。**总线驱动理解“怎么传”，芯片驱动理解“传来的字节是什么意思”。**

这也解释了为什么仅有 `/dev/i2c-N` 还不够：它让用户程序直接发送 I2C 报文，却不会帮程序理解 RTC 的时间寄存器。反过来，芯片驱动源码已经编进内核，但控制器没启用或引脚接错，它也不可能从硬件读到时间。

设备树（Device Tree）是硬件描述，不是驱动源码。它告诉内核“这块板把什么器件接在什么位置，使用哪些引脚、供电和中断”。内核据此建立设备对象，再寻找能匹配的驱动。`compatible` 是匹配线索；写出一个没有驱动识别的字符串，不会自动生成驱动。[Linux 内核：设备树在 Linux 中的使用](https://docs.kernel.org/devicetree/usage-model.html)

驱动也不等于 `/dev` 文件。它可以向 RTC、IIO、V4L2、网络等子系统注册，最终由子系统提供应用接口。判断“驱动做好了”的终点是**应用通过相应接口完成真实操作**，不是 `dmesg` 打印一句 `probe success`。

可以把这四层看成一条逐步收窄的问题链：**物理层**回答“电和信号能不能到达”，**设备描述**回答“内核是否建立了正确的设备”，**驱动绑定**回答“有没有代码接管它”，**功能接口**回答“应用是否得到需要的结果”。后一层成功不能倒推前一层以外的所有细节正确：例如网口驱动绑定成功，PHY 链路仍可能不通；RTC 节点被建立，芯片也可能没有供电。

## 2 先判断需要改哪一层

拿到新硬件需求，先问它在哪一步断了。下表也是后续操作的地图。

| 已知现象或变化 | 优先查看和修改 |
| --- | --- |
| 同一块板换了系统镜像，原有器件消失 | 确认启动的 DTB、内核配置、模块是否与原镜像一致 |
| 底板换了引脚、地址、片选、复位脚或电源连接 | 原理图与板级设备树；必要时检查引脚复用和供电 |
| 硬件描述正确，但驱动未编译或未加载 | 内核配置、模块安装与加载 |
| 内核有控制器驱动，没有这颗芯片的驱动 | 搜索相应子系统和较新内核；确实没有时开发或移植芯片驱动 |
| 驱动已绑定，标准设备接口已出现，但开机不自动使用 | 用户程序、权限、服务和配置 |

还有一类设备会**自己枚举**：USB、PCIe 设备插入后由总线报告身份，通常不用把每个 U 盘或 USB 摄像头写成板级设备树子节点。设备树仍可能需要描述 USB 控制器、PHY、供电及接口接线。普通 I2C 设备则不会向控制器自动报出“这里有一颗某型号 RTC”；板子已知接了它，才在设备树中描述它。[Linux 内核：设备树与设备创建](https://docs.kernel.org/devicetree/usage-model.html)

“要不要自己写驱动”应放在最后判断。假设你换了一块底板，RTC 原来能读，现在 `/dev/rtc0` 消失：若运行中的设备树没有 `rtc@51`，先解决 DTB；若节点存在而 `/sys/bus/i2c/devices/` 中没有对应设备，先解决控制器、节点状态或总线创建；若设备存在却没有驱动链接，再核对 `compatible`、模块和探测错误；只有确认目标内核确实没有这颗芯片的实现，才进入新驱动开发。这样每一步都能用证据排除一类原因。

## 3 从原理图得到可用的硬件事实

以“新增一颗 I2C RTC”为例，先把原理图和芯片手册中的事实写成记录：

| 要确认的事实 | 为什么影响软件 | RTC 例子 |
| --- | --- | --- |
| 芯片准确型号 | 决定驱动和绑定文档 | PCF8563 |
| 供电与使能/复位 | 没上电时任何扫描都没有意义 | 电源是否一直存在，是否有使能脚 |
| 总线与 SoC 引脚 | 决定启用哪一路控制器、哪组 pinctrl | SDA/SCL 连到实际的两个 SoC 管脚 |
| 总线地址或片选 | 决定设备树子节点的 `reg` | PCF8563 的 7 位地址 `0x51`，仍按手册核对 |
| 额外连线 | 可能要求中断、时钟、GPIO、稳压器属性 | RTC 的中断脚是否真的接到 SoC |
| 期望的应用功能 | 决定最终验证接口 | 能从 RTC 读出时间，重启后再读到 |

这张记录把**硬件事实**和**软件配置**分开：原理图决定线接到了哪里；内核源码决定可引用的标签、属性名和驱动选项。不能因为一篇示例写了 `&i2c5`，就推断自己的板子也接在 I2C5。引脚复用（pinctrl）尤其容易误判：控制器驱动可以成功加载，但 SDA/SCL 被切到另一组脚，外部器件仍然毫无响应。

从原理图追线时，要顺着 RTC 的 SDA、SCL 网络找到 SoC 管脚，再到**当前内核**的 pinctrl 定义中找这两个管脚所在的复用组。RK3588 的同一个控制器可能有多组可选引脚；控制器编号相同，不代表任何一组引脚都能到达底板上的芯片。I2C 还需要上拉和合适的电压域。若电平转换器位于中间，要把它两侧的电源和使能脚一并核实。能在软件里看到控制器对象，并不能证明示波器上已有正确波形。

地址也来自硬件与手册，而非节点名字的猜测。某些 I2C 器件有地址选择脚，焊接电阻不同会改变低几位；`rtc@51` 中的 `51` 只是节点单元地址的写法，实际传输由 `reg = <0x51>` 指定。把手册中包含读写位的 8 位地址直接照搬为 `reg`，常会得到两倍于预期的错误地址。先确认手册给的是 7 位地址还是总线上的 8 位地址字节。

原理图上还要区分“真正带寄存器的器件”和“电平转换/收发器”。例如 CAN 收发器主要把控制器的逻辑信号变成总线电平，常见情况下由 CAN 控制器驱动提供 `can0`，不另写一个“CANH/CANL 驱动”。若用的是接在 SPI 上的独立 CAN 控制器，则它是 SPI 外设，需要自己的芯片驱动。先看**芯片与 SoC 之间实际连的是什么线**。

## 4 设备树、配置和驱动怎样接起来

### 4.1 描述板上真实存在的设备

SoC 公共 `.dtsi` 通常已有 I2C 控制器的寄存器地址、中断和时钟。板级 `.dts` 引用它，写出这块底板特有的连接。假设当前源码确实存在 `i2c5m2_xfer`，原理图证实 RTC 接在该组引脚且地址为 `0x51`，结构可能是：

```text
&i2c5 {
    pinctrl-names = "default";
    pinctrl-0 = <&i2c5m2_xfer>;
    status = "okay";

    rtc@51 {
        compatible = "nxp,pcf8563";
        reg = <0x51>;
    };
};
```

父节点表示**总线控制器**，`rtc@51` 表示这条总线上的**一颗芯片**。`reg` 是 I2C 的 7 位地址；在 SPI 子节点里，同一个属性通常表示片选编号，所以不能只记“`reg` 等于地址”。属性的准确要求以该设备在 `Documentation/devicetree/bindings/` 中的绑定文档为准。若实际连接了中断、电源或复位，也按绑定文档补齐；未连接的线不要凭空填写。

这里的 `&i2c5` 不是新建一个控制器，而是引用 SoC `.dtsi` 里已经声明的节点。公共 `.dtsi` 描述芯片内部固定的寄存器范围、中断和时钟；板级 `.dts` 描述底板有没有把这路控制器接出来、引脚复用到哪组、总线上挂了什么。把这些责任分开，同一 SoC 才能支持多块接线不同的板。`status = "okay"` 只让控制器参与设备创建，不能代替它的内核驱动、供电或外部接线。

`compatible = "nxp,pcf8563"` 说明这颗芯片遵循该驱动认识的编程模型。设备树绑定文档规定字符串与可用属性；驱动的匹配表决定它是否接管这个设备。实际板子若是兼容型号，应按其绑定文档选择字符串和备用兼容项，不能为了强行匹配就冒充另一颗寄存器布局不同的芯片。

还要确认启动时加载的是**新编译出的那份 DTB**。只改源文件、却让 U-Boot 继续加载旧 DTB，运行中的硬件描述不会变化。板上可先看 `/proc/device-tree` 或 `/sys/firmware/devicetree/base`，再核对启动配置和 DTB 路径。

### 4.2 让两份驱动存在，并完成匹配

内核必须具备两份能力：I2C 控制器驱动使总线工作，RTC 芯片驱动把寄存器变成时间。它们可能编进内核，也可能作为模块安装。启动所必需的驱动如果编成模块，必须能从 initramfs 等启动早期环境加载；仅放在尚未挂载的根分区里，无法帮助系统找到根分区。

在**自己正在编译的源码树**里，可以按顺序查，而不背配置符号：

```bash
# 从板级 DTS 引用的标签追到 SoC DTSI，核对控制器 compatible。
rg 'i2c5:|i2c5m2_xfer' arch/arm64/boot/dts/rockchip
# 用芯片型号找设备树绑定，再核对驱动是否识别该 compatible。
rg 'pcf8563' Documentation/devicetree/bindings drivers/rtc
# 查看对应驱动的 Makefile/Kconfig，确认实际配置项。
rg 'pcf8563|I2C_RK3X' drivers/rtc drivers/i2c
```

`rg` 只是阅读源码的工具，未安装时可用 `grep -R`。配置选项以**这棵内核的 Kconfig/Makefile**为准。控制器节点与控制器驱动匹配后，驱动注册 I2C 总线；内核再为子节点建立 I2C 设备，匹配 RTC 驱动并调用它的 `probe()`。`probe()` 是开始初始化的入口，成功返回后还要看驱动是否向 RTC 子系统注册了设备。[Linux 内核：I2C 设备驱动与设备创建](https://docs.kernel.org/i2c/writing-clients.html)

“设备出现但没绑定驱动”和“驱动曾经尝试探测却失败”也要区分。前者多见于没有匹配的驱动或模块未加载；后者可能是读不到芯片 ID、申请 GPIO/电源失败、总线传输超时。还有一种**延后探测**：驱动依赖的稳压器、时钟等尚未准备好，内核把探测留到稍后重试。此时既不能把 `compatible` 改成另一个随意的值，也不能仅凭启动早期没有 `driver` 链接就断定永久失败。查看完整 `dmesg` 和相关设备的依赖状态，才能找到断点。[Linux 内核：驱动模型与延后探测](https://docs.kernel.org/driver-api/driver-model/driver.html)

配置成 `y` 的驱动随 `Image` 进入内核；配置成 `m` 的驱动要有匹配这份内核的 `.ko`，并且启动后能够加载。普通 RTC 不一定是挂根所必需的，作为模块很常见；放根的存储控制器和根文件系统若也做成模块，就必须有能在挂根前加载它们的 initramfs。选择 `y` 或 `m` 要看**设备被需要的时间点**，不是简单地认为两者性能不同。

### 4.3 `probe` 成功与用户能使用之间还有一层

内核驱动通常把器件交给已有子系统，而不是每个芯片自造一个接口：

| 器件功能 | 常见内核子系统 | 用户通常看到什么 |
| --- | --- | --- |
| RTC | RTC | `/dev/rtcN`、`hwclock` |
| 温度/电压或惯性测量 | hwmon 或 IIO | `/sys/class/hwmon/`、`/sys/bus/iio/devices/`，部分设备有缓冲接口 |
| 按键、触摸事件 | Input | `/dev/input/event*` |
| 摄像头采集 | V4L2/Media | `/dev/video*`，复杂管线还有媒体拓扑 |
| CAN、以太网 | 网络 | `ip link` 中的接口，应用使用套接字 |
| 串口 | TTY | `/dev/tty*` |

`/dev/i2c-N` 是应用直接操作**I2C 总线**的通用入口，并不等于 RTC 的标准时间接口。若芯片驱动已占有该地址，应用应使用它提供的 RTC 接口，避免另一个程序直接改寄存器。同样，`can0` 是网络接口，不是 `/dev/can0` 字符设备。

子系统之所以重要，是因为它把同一类器件交给应用的方式统一起来。RTC 驱动可以各自处理不同寄存器，但应用读取时间时不必知道板上是 PCF8563 还是另一颗 RTC。IIO 驱动可以把原始采样值、比例系数和缓冲采样接口交给应用；网络驱动则把数据包交给网络栈。**先决定器件属于哪个功能子系统，再考虑驱动的用户接口**，通常比先设计一个私有 `ioctl` 更容易与现有工具和应用协作。

## 5 用一颗 RTC 走完验证路径

按“事实 → 描述 → 匹配 → 功能”逐级检查，每一步都要有可观察证据：

1. **硬件事实**：确认电源电压、地址、SDA/SCL 和上拉、复位状态；总线不响应时先测量这些条件。
2. **运行中的描述**：确认新 DTB 被加载、控制器状态为 `okay`、RTC 子节点存在。源码里有节点，不代表板上运行的是它。
3. **驱动绑定**：看 `dmesg` 中控制器与 RTC 的信息，查看 `/sys/bus/i2c/devices/` 下对应设备是否有 `driver` 链接。设备存在但没有驱动链接，回到 `compatible`、配置、模块或 `probe` 错误；也要考虑供电等依赖尚未就绪引起的延后探测。
4. **功能验证**：找到对应 `/dev/rtcN`，用 `hwclock -r -f /dev/rtcN` 读取；在允许设置时间的测试环境中写入后重启，再读回，确认外部 RTC 真正工作。编号 `N` 可能改变，先在 sysfs 中核对名称。

I2C 扫描工具只能作为有限的辅助。`i2cdetect` 扫到数字，通常表示该地址有响应，却不能证明型号、寄存器和 RTC 功能正确；显示 `UU` 通常表示地址被内核驱动占用，也不是功能测试。有些设备不适合被通用扫描访问，先查芯片手册与板级说明。没有响应时，依次查**供电 → 引脚复用 → 上拉/波形 → 总线编号与地址**，比修改 `read()` 有效。

下面把三种常见现象展开成实际判断：

- **运行中看不到 `rtc@51`**：先核对编译出的 DTB 是否包含节点、U-Boot 实际加载哪个 DTB。此时改 RTC 驱动毫无作用，因为内核还没有被告知这颗芯片存在。
- **能看到 I2C 设备却没有 RTC 接口**：检查设备与驱动的 `compatible`、配置和模块；若 `dmesg` 有探测错误，再根据错误核对供电、中断或寄存器读写。仅有节点不表示 `probe()` 一定成功。
- **`/dev/rtcN` 存在但时间明显错误**：确认 `rtcN` 真是外接芯片而非 SoC 内的另一个 RTC，再核对晶振、备用电池、电压、时间设置和重启后的保持情况。此时重新选择 I2C 控制器通常不能解决问题。

板上最小的观察命令可以集中在几项，编号由实际系统确定：

```bash
cat /proc/cmdline                    # 确认实际启动参数
ls /sys/bus/i2c/devices/           # 控制器与设备有没有建立
ls -l /sys/bus/i2c/devices/*/driver # 设备是否绑定驱动
ls /sys/class/rtc/                 # RTC 子系统有没有注册设备
dmesg | grep -i -e i2c -e rtc      # 看探测与传输错误
```

`/sys` 路径中的设备编号、`rtcN` 编号及工具是否预装都会因系统而异。若最小根文件系统没有 `grep` 或 `hwclock`，先用已有的 `dmesg`、`cat` 和 sysfs 看同一批证据，或把工具作为用户空间依赖加入根文件系统。

## 6 什么时候才需要写新驱动

如果控制器已经工作，设备树也正确，但当前内核找不到能管理这颗器件的驱动，先确认相同或兼容型号是否已有驱动、厂商补丁是否缺失、所用内核版本是否较旧。确实要写时，再选合适的总线与功能子系统。[Linux 内核：I2C 驱动开发](https://docs.kernel.org/i2c/writing-clients.html)

一份 I2C 芯片驱动的最小职责可以按生命周期理解：

```text
匹配表声明支持的器件
→ probe() 取得设备及资源，验证芯片，注册 RTC/IIO/hwmon 等接口
→ 子系统收到用户请求时，驱动通过 I2C 读写寄存器并转换数据
→ 设备移除或模块卸载时，释放需要手动管理的资源
```

最容易漏的是**注册用户接口**。只写匹配表并在 `probe()` 打一行日志，内核知道这颗芯片存在，应用却仍无处读取结果。如果只是单个实验程序短期访问简单 I2C 器件，也可以由用户程序通过 `/dev/i2c-N` 通信；这时要自己处理寄存器协议、单位转换和并发访问，并确认没有内核驱动同时占用地址。

以“新温度传感器”为例，可以按职责把真正需要写的部分拆开：`probe()` 确认芯片及供电、取得可选中断等资源；读取函数按手册访问温度寄存器并处理符号位、比例和单位；最后向 hwmon 或 IIO 注册，使应用从标准接口取得温度。若芯片还支持阈值中断，再补充中断处理，而不必因为芯片有一个中断脚就把所有读取放进中断回调。这样设计的关键是**器件如何工作及数据怎样交给现有子系统**，不是机械地补齐 `open/read/write/ioctl` 四个函数。

选择 hwmon 还是 IIO 也取决于用途。以低频查看温度、供电电压和风扇状态为主的器件常归入 hwmon；需要通道、量程、采样频率或连续采样的传感器常归入 IIO。应先查看同类现有驱动和子系统约定，再定用户接口。若现有内核已经有成熟驱动，移植补丁或补设备树支持通常比重写一份私有字符驱动更稳妥。

写代码时按问题需要选择机制。总线 API 负责传输，`devm_*` 资源管理可简化清理，子系统 API 负责对外接口；涉及中断和并发时再选择合适的锁与上下文约束。具体 `probe` 函数签名、辅助 API 和绑定要求会随内核版本变化，复制代码前先看目标内核的头文件与同子系统现有驱动。

## 7 换一种器件，哪些判断会变化

| 场景 | 不变的主线 | 必须新增或换掉的判断 |
| --- | --- | --- |
| SPI 闪存 | 查原理图、启用控制器、匹配芯片驱动、验证功能 | `reg` 是片选；核对 SPI 模式和最高频率；用户接口可能是 MTD 或块设备 |
| 板载 UART | 描述接线、启用控制器、验证用户接口 | 通常没有带地址的子设备；检查波特率与外部电平转换 |
| 以太网 | 描述硬件、匹配驱动、验证链路 | 同时检查 MAC、MDIO 上的 PHY、`phy-mode`、复位与 RGMII 延时；`ip link` 有接口不代表链路已通 |
| USB 外接设备 | 先保证控制器和 PHY 工作 | 设备插入后由总线枚举；用 `lsusb` 及其设备类接口确认，不照搬 I2C 子节点 |
| 摄像头传感器 | I2C 控制器与传感器也要匹配 | 还需电源、时钟、CSI/ISP 的 endpoint 连接及各端格式；传感器 `probe` 成功不等于 `/dev/video*` 能出图 |

表中的差异可以用两个例子再体会一次。**网口没有链路**时，先区分 MAC 驱动是否注册了接口与 PHY 是否报告链路。前者不成立，回到 MAC 节点、驱动和时钟；前者成立而链路 down，重点看 PHY 的 MDIO 地址、复位、供电、`phy-mode` 和线缆。给 MAC 新增一个字符设备不会让物理链路建立。

**摄像头有 I2C 应答却没有图像**时，I2C 只证明控制通路的一部分：传感器还要拿到电源、时钟并退出复位，图像数据还要从 MIPI CSI 进入接收器与 ISP，链路两端的 endpoint 及格式要一致。检查应沿“传感器识别 → 媒体拓扑 → 管线配置 → 采集帧”的顺序走。V4L2 用户程序只负责在管线就绪后取帧，无法凭 `open(/dev/video0)` 修复错误的硬件连接。

面对新板子，可以把最终决定压缩成三句话：**先确定物理连接和功能目标；再确认内核是否已有相应控制器与器件驱动；最后沿设备树、绑定和用户接口逐层验证。** 这样才知道该改硬件描述、编译选项、驱动实现，还是开机服务。
