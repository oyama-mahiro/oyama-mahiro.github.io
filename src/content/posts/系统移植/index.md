# [系统移植] 嵌入式 Linux 移植

“把 Linux 移植到一块板上”不是只编出一个 `Image`，也不是把发行版镜像拷到 SD 卡。目标是让**这块板**从上电走到用户程序，并让它实际连接的存储、串口、网络及其他外设工作。本文建立一张可以用于判断和排错的地图：每一层接收什么、交付什么；换了 SoC、核心板或底板时，究竟需要改哪些东西。

RK3588 是贯穿示例，不是一份可直接烧录到所有 RK3588 板卡的步骤清单。具体镜像布局、DDR 初始化程序、U-Boot 配置、设备树和根分区位置必须以**板厂文档、原理图及正在使用的源码版本**核对。

## 1 先看清交付链：上一级把什么交给下一级

```text
上电
→ 片内 BootROM：按芯片规定的启动方式找到第一段可执行代码
→ 早期加载器：准备 DRAM，并加载后续固件/U-Boot
→ U-Boot：取得内核 Image、板级 DTB、可选 initramfs 和启动参数
→ Linux 内核：初始化硬件与驱动，建立根目录，执行第一个用户程序
→ init / 系统服务：启动登录、网络配置以及你的应用
```

这条链有两个不同的“成功”：**内核开始打印日志**只表示前几级已经把内核运行起来；**出现 shell 或登录界面**还要求根文件系统和 init 可用。底板上新增的网口、摄像头没有工作，也不能因为已经看到 shell 就宣布移植完成。

| 层 | 主要输入 | 要交给下一层的结果 | 典型可观察证据 |
| --- | --- | --- | --- |
| BootROM | 启动拨码/熔丝、启动介质上的规定格式 | 在片内 SRAM 中运行的加载器 | 往往没有可读日志；需结合板厂工具与后续输出判断 |
| 早期加载器 | DDR 参数、后续镜像 | 可用的 DRAM 与下一阶段程序 | DDR 初始化日志，若平台启用串口输出 |
| U-Boot | 存储/网络中的镜像与环境配置 | 内核、DTB、可选 initramfs 及命令行 | `U-Boot` 信息、提示符或启动日志 |
| 内核 | 镜像、DTB、命令行、可选 initramfs | 设备驱动、可挂载的根以及 PID 1 | `Linux version`、驱动和挂载日志 |
| 根文件系统与 init | 程序、库、配置及服务定义 | 可用的用户空间 | shell、登录服务和目标应用 |

BootROM 固化在 SoC 内，开发者通常不“移植 ROM”；要做的是遵守它要求的启动介质和镜像格式。U-Boot 的早期阶段可能采用 TPL/SPL，也可能采用厂商 miniloader；RK3588 启动还常涉及 BL31（Arm Trusted Firmware）。这些部件的组合随板卡和方案而变，别把示例中的文件名和偏移量当成芯片的统一常数。[U-Boot：Rockchip 平台说明](https://docs.u-boot.org/en/stable/board/rockchip/rockchip.html)、[U-Boot：TPL/SPL 启动阶段](https://docs.u-boot.org/en/stable/usage/spl_boot.html)

### 1.1 为什么要分出“早期加载器”

SoC 刚复位时，板上的 DRAM 还没有初始化。BootROM 能使用的通常是容量较小的片内 SRAM，不足以直接容纳完整 U-Boot，更不用说 Linux。于是先运行一段小程序，按当前板子的内存颗粒和布线初始化 DRAM；内存可用后，再把后续固件与完整 U-Boot 读入 DRAM。**DDR 颗粒或走线改变，影响的是这一早期阶段**，即使 Linux 内核源码一行没变，板子也可能停在 DDR 日志之前。

RK3588 的方案可能使用 U-Boot 的 TPL/SPL 与 Rockchip 提供的 DDR 二进制，也可能使用厂商 loader。BL31 是 Arm Trusted Firmware 的一部分，负责 EL3 安全世界中的运行时服务，并把普通世界的启动交给后续程序；它不是 Linux 的 init，也不是根文件系统。知道这些名称的目的，是看到串口日志时能判定**哪一级已经执行**，而不是记住某个板厂镜像包里的每个文件名。[U-Boot：Rockchip 平台说明](https://docs.u-boot.org/en/stable/board/rockchip/rockchip.html)

### 1.2 内核启动之后也还有两次交接

U-Boot 跳入 Linux 后，内核根据 DTB 建立设备并初始化能够在此时使用的驱动。接着它要得到一棵根目录：可能直接挂载 SD/eMMC 上的分区，也可能先展开 initramfs，在其中执行 `/init`，由 `/init` 寻找并切换到持久根。最后 PID 1 依据根里的配置启动其他程序。**串口出现 `Linux version`、根挂载成功、登录服务出现**是三个不同检查点，分别证明不同的交接已经完成。[Linux 内核：rootfs 与 initramfs](https://docs.kernel.org/filesystems/ramfs-rootfs-initramfs.html)

## 2 “移植”到底改什么：先确定变化范围

同叫移植，任务规模可能完全不同。先确定你手里的板子与已能启动的参考板相比改变了哪里。

| 当前场景 | 通常沿用什么 | 优先改变什么 |
| --- | --- | --- |
| 同一块板，只换内核或发行版 | BootROM、DDR 参数、原理图连接 | 内核版本与配置、匹配的模块、DTB、根文件系统兼容性 |
| 同一 SoC、不同底板，沿用核心板 | SoC 支持与核心板 DDR 启动方案 | 板级设备树中的引脚、供电、PHY、外设；必要的驱动选项 |
| 同一 SoC、不同内存/启动存储设计 | SoC 大部分驱动 | 早期 DDR/启动方案、镜像布局、存储驱动和根位置 |
| 换了 SoC 或新架构 | 用户应用的一部分 | 启动链、工具链、SoC 支持、设备树、驱动和镜像布局都要重新核对 |

这里的**核心板**通常带 SoC、DDR 和部分启动存储；**底板**可能带网口、摄像头、串口连接器、电源与各类传感器。如果核心板已经能从 SD 启动，做一块新底板时，一般从现有可启动的引导方案出发，在板级设备树与驱动配置中描述新的接线。若底板改变了启动介质或早期供电，U-Boot 也可能需要修改。是否要改某一层，由硬件变化决定，而不是由“这是新板”三个字决定。

开始前收集一份最小资料包：**原理图、SoC/板厂启动说明、能启动的参考镜像及日志、对应源码和配置、分区或镜像布局**。记录当前版本和启动介质。没有这些基线，后面很难判断是代码问题，还是刷入了旧镜像。

### 2.1 一个具体任务：已有核心板，换一块底板

假设 RK3588 核心板已经带 DDR 和 eMMC，可以在参考底板上进入 Linux。新底板把原有一路串口接到新插座，新增一颗 I2C RTC，并把网口 PHY 换到另一种接线方式。此时按硬件变化拆任务：

1. **先确认共同部分**：核心板的 DDR、eMMC 和原有引导镜像未变，就先用原方案启动，保存 U-Boot 到登录提示的完整串口日志。不要在还没比较差异时重新制作 DDR loader。
2. **再改板级硬件描述**：核对新串口引脚复用、RTC 所在 I2C 总线与地址、PHY 的 MDIO 地址、复位与 `phy-mode`。公共 SoC `.dtsi` 描述片内控制器，板级 `.dts` 描述这些新接线。
3. **补驱动配置**：检查内核是否已有 RTC 芯片与 PHY 驱动，决定编进内核还是安装模块。只在源码缺少实现时补驱动；设备树不能替代驱动代码。
4. **最后看用户空间**：串口节点、`/dev/rtcN` 和网卡出现后，各自做收发、时间读回、网络传包。若希望开机自动同步时间、配置网卡地址，再把服务和配置写入根文件系统。

这个例子中，新底板可能只需要板级 DTB、配置与根中的服务变化；如果新底板还改变了启动电源、启动介质或 U-Boot 使用的网口，也要回到引导程序。**变化发生在哪一级，就从那一级及其下游重新验证**，而不必每次从零移植全部软件。

## 3 主机上的工具链与产物怎样对应

开发主机通常是 x86_64，RK3588 上运行的是 AArch64 程序。交叉编译器在主机运行，生成目标板能执行的文件；它并不决定板上的设备树或启动分区位置。

| 主机上构建的东西 | 常见产物 | 板上由谁使用 |
| --- | --- | --- |
| 引导程序和所需固件 | 按该板方案打包的启动镜像 | BootROM/早期加载器/U-Boot |
| Linux 内核 | `Image` 等内核镜像 | U-Boot 加载并启动 |
| 板级设备树 | `.dtb` | U-Boot 传给内核，内核据此认识硬件 |
| 内核模块 | `.ko`，按内核版本放进 `/lib/modules/` | 内核启动后按需加载 |
| 用户空间 | 根文件系统目录或镜像 | 内核挂载后执行 init 与应用 |

这几份产物必须是一组能相互配合的版本。只更新 `Image`，不更新它对应的 DTB 和模块，可能导致节点属性变化或模块无法加载；只更新 DTB，驱动配置却没有对应选项，设备仍不会工作。刷机或复制之前，最好给每份产物记下构建版本、文件哈希和目标分区，启动后再核对 `uname -r`、运行中的设备树和 `/lib/modules/`。

`ARCH=arm64` 表示目标内核架构；`CROSS_COMPILE=aarch64-linux-gnu-` 是常见交叉工具前缀，但具体工具链要与所用内核/SDK 配合。用户程序还要关心目标根文件系统的 ABI 与动态库版本；一个能生成 AArch64 指令的程序，仍可能因缺少运行库而无法启动。

### 3.1 “文件生成了”与“板子用到了”之间的距离

构建完成后，主机上可能同时留下多份旧 `Image`、旧 `.dtb` 和旧根镜像。开发板可能从 eMMC 启动，却被你更新了 SD 卡；U-Boot 可能从一个 FAT 分区加载 DTB，而你把新文件放到根分区 `/boot`；厂商打包流程可能又把旧产物复制回输出目录。因此要沿**构建路径 → 打包/复制路径 → U-Boot 加载路径 → 运行时证据**追踪同一份产物。

比较可靠的做法是给构建产物记录哈希，保存 U-Boot 实际加载的文件名与分区，启动后核对 `/proc/cmdline`、`uname -r` 和运行中的设备树。Linux 能启动但新增设备完全没有变化，先确认 DTB 是否真换了；模块报版本不符，先确认它与当前运行内核来自同一次构建。这样比反复改源码有效。

### 3.2 “编译进内核”和“放进根里”何时不同

`Image` 里的内置驱动在内核早期就可用；`.ko` 模块需要被某个已经运行的环境加载。如果根文件系统就在 eMMC 上，那么访问 eMMC、识别分区并挂载根所需的能力，必须已经内置，或放在启动时先加载的 initramfs 中。把 eMMC 控制器驱动仅放在 eMMC 根分区的 `/lib/modules`，会形成“要挂根才能读取模块，要读取模块才能挂根”的循环。

普通业务外设不一定需要早期加载。例如用户空间起来之后才使用的 RTC 或摄像头，可以随模块安装在根里。判断依据是**哪个阶段第一次需要它**。这也是裁剪内核配置时必须保住控制台、启动存储、根文件系统和必要时 initramfs 支持的原因。

## 4 U-Boot：让内核带着正确的描述起跑

U-Boot 最关键的交付，不是显示一个提示符，而是把**内核、正确的板级 DTB、可选 initramfs 和启动参数**装入合适的内存位置，再跳转到内核。内核镜像只包含通用的执行逻辑；板上串口、存储、供电和外设的连接来自 DTB。设备树的 `.dts/.dtsi` 是源文件，`.dtb` 是编译结果。启动时加载了哪个 DTB，比你改了哪个 `.dts` 更重要。

内核命令行常见的两项是 `console=` 和 `root=`：前者指定日志与控制台使用的串口，后者指定真正根文件系统的位置。它们的值要与板上的设备、分区和驱动一致。`root=/dev/mmcblk...` 的编号可能因启动介质或枚举顺序变化；条件允许时可用稳定标识，并从实际启动日志核对结果。

再加上几个经常影响启动判断的参数：`rootwait` 让内核等待稍后出现的根设备；`rootfstype=` 可指定根的文件系统类型；`init=` 可用于指定要执行的初始用户程序。它们都不是万能修复项：如果存储驱动根本没编译，等待再久也不会出现设备；如果根里缺少动态加载器，改 `root=` 也不会使 init 变得可执行。应先从日志分辨“找不到块设备”“无法识别文件系统”“已挂载但无法执行 init”。

设备树还有一个常见混淆：U-Boot 自己运行时可能使用**自己的控制 FDT**，而它传给 Linux 的是**另一份内核 DTB**。这两份描述可能来自不同位置。U-Boot 命令行里串口或网口能工作，并不能证明内核加载的板级 DTB 正确；反过来，Linux 外设正常，也不意味着 U-Boot 的同一外设已配置。定位时要问清“这个现象发生在 U-Boot 阶段还是内核阶段”。

对一块已有可启动镜像的板子，先保留原有引导链，确认它**实际从哪里加载内核和 DTB**：启动脚本、环境变量、extlinux 配置或厂商打包文件。复制新文件到一个同名目录并不保证 U-Boot 会用它。修改后通过串口观察加载路径、文件大小、传给内核的命令行，并在 Linux 中核对运行时的 `/proc/cmdline`。

如果连 U-Boot 都没有起来，优先检查启动拨码、介质、镜像布局、DDR 初始化和调试串口。此时修改根文件系统或应用程序不会改变现象。具体烧录偏移和内存加载地址属于板级方案，应照对应板卡文档操作，不能从其他 RK3588 板子的文章照抄。[U-Boot：Rockchip 板卡构建与启动](https://docs.u-boot.org/en/stable/board/rockchip/rockchip.html)

## 5 内核：区分“有代码”“描述了设备”“设备真正工作”

内核移植主要涉及三个互相配合的对象：

1. **内核源码与补丁**决定是否有该 SoC、控制器和外设的实现。优先选一棵对这块 SoC 和板子已有支持的内核；厂商树和主线树的设备树、驱动及配置可能不同。
2. **内核配置**决定某个驱动编进镜像（`y`）、编成模块（`m`），还是不编译。启动根所需的存储控制器、分区和文件系统支持必须在挂载根之前可用；若编成模块，需要由 initramfs 等早期环境提供。
3. **板级设备树**说明实际接了哪些器件、使用哪组引脚、供电、中断、地址和片选。设备树写了节点，仍不代表存在能匹配它的驱动。

例如给新底板加一颗 I2C RTC：先从原理图确认它连接的控制器、引脚和地址；在当前内核的板级设备树里启用控制器、增加芯片子节点；在配置中启用控制器和 RTC 芯片驱动；最后看驱动是否绑定、`/dev/rtcN` 是否能读时间。相关的匹配与验证方法见[《Linux 驱动入门》](/posts/驱动开发/)。

`probe()` 成功只表示驱动完成了当前初始化，不能替代实际读写。网口例子更明显：MAC 驱动注册出 `eth0`，但 PHY 地址、复位、RGMII 模式或走线延时不对，链路仍可能一直 down。摄像头传感器在 I2C 上被识别，也不表示 CSI/ISP 管线已通。**每个功能要选自己的终点证据**，例如 RTC 读回时间、网口有链路并能传包、摄像头能采到正确格式的帧。

调试时只改一个明确的点，并保存上一份能启动的内核与 DTB。裁剪配置也从工作基线出发，确认某功能确实未使用后再移除。为了把镜像变小而一口气关闭大量选项，会让早期存储或控制台失效，反而失去定位依据。

### 5.1 从参考配置到板级改动

移植新底板时，先选择**已经能启动该 SoC/核心板**的配置与设备树作为起点。内核的 defconfig 是配置起点，不会自动知道底板多了哪颗器件；板级设备树描述连接，也不会自动打开对应 Kconfig 选项。每加入一项功能，分别检查“设备树节点存在且属性正确”“驱动已编译或模块可加载”“真实硬件响应”“用户接口可用”四项。

例如 `status = "okay"` 的 I2C 控制器节点出现在运行时设备树，但板上没有 `i2c-N`，先查控制器驱动、时钟或探测错误；`i2c-N` 存在却没有 RTC，查子节点、地址、供电与芯片驱动；RTC 已出现却读数错误，则核对外部晶振、备用电源和时间设置。把不同症状落到不同环节，比笼统地“重新编一次内核”更容易找出原因。

### 5.2 修改设备树时分清三种内容

- **SoC 固有资源**：寄存器地址、中断线、控制器内部时钟等，通常来自 SoC 公共 `.dtsi`，不应从另一块板的示例中随意复制并覆盖。
- **板级接线**：实际启用哪路控制器、引脚复用、GPIO 复位、电源、总线子设备和地址，由原理图和板级 `.dts` 决定。
- **驱动认识的绑定格式**：`compatible` 与属性名称由设备树绑定文档约定。硬件相同但拼错属性，驱动也可能拿不到它需要的资源。

这三类信息来源不同。**硬件决定值，绑定文档决定写法，内核源码决定有哪些标签和驱动**。这种分工也解释了为什么“找一块 RK3588 板子的 DTS 全部照抄”常会失败：SoC 相同，不代表底板上的电源、PHY 地址、引脚组与走线相同。[Linux 内核：设备树使用模型](https://docs.kernel.org/devicetree/usage-model.html)

## 6 根文件系统：内核怎样交出控制权

根文件系统不是一个固定文件名，而是**挂在 `/` 的那份目录内容**。它包含 `/bin`、`/lib`、`/etc` 等目录、需要的程序与库，以及第一个用户空间程序 init。内核本身打印日志时还没有普通用户程序；完成早期初始化后，才执行 init，交由它启动 shell、网络和业务服务。

要把三个概念分开：

| 概念 | 它回答的问题 | 例子 |
| --- | --- | --- |
| 存储与分区 | 字节放在什么介质的哪块区域 | SD/eMMC 的某个分区 |
| 文件系统格式 | 怎样把分区中的字节组织成文件和目录 | ext4、SquashFS、F2FS |
| 挂载点 | 这份文件树在 Linux 路径中出现在哪里 | 根分区挂在 `/`，proc 挂在 `/proc` |

例如把 SD 卡第二分区格式化为 ext4，再放入 `/sbin/init`、shell、库和配置，只是**做好了一份根**；U-Boot/内核还必须通过命令行或 initramfs 找到它、内核必须具备 SD 控制器与 ext4 支持，才能把它挂到 `/`。`/etc/fstab` 是用户空间起来之后配置其他挂载的常见位置，无法替代启动早期寻找初始根的机制。

从空目录到可启动的根，可以沿“**目录和文件 → init → 依赖 → 挂载**”来理解。仅有 `/bin/sh` 而没有它需要的动态加载器与库，内核仍可能无法执行；脚本形式的 `/init` 若指定了不存在的解释器，也会失败。进入用户空间后，init 通常还要挂载 `proc`、`sysfs`、`devtmpfs` 等，让 `/proc`、`/sys`、`/dev` 提供运行时信息与设备入口。这些路径看起来位于根目录之下，实际内容可能来自另外挂载的文件系统。

对新板的调试，最小 initramfs 的价值不是代替最终发行版，而是把问题拆开：先用一个已知能运行的内存根取得 shell，证明内核与基本串口可用；再在 shell 中查看 SD/eMMC 设备、分区和文件系统；最后让系统切换到持久根。如果最小内存根能启动，持久根不能启动，排查重点就收窄到存储、根参数、文件系统和用户空间，而不是回头修改 BootROM。

### 6.1 initramfs 与持久根各做什么

initramfs 是启动时提供给内核的 cpio 归档，展开后形成内存中的早期根；里面的 `/init` 可以加载模块、寻找真正根分区，再切换到持久根。有些板卡也直接用它作为最小系统。这使得“先取得一个 shell”与“先让 SD/eMMC 上的发行版启动”可以分开验证。[Linux 内核：rootfs 与 initramfs](https://docs.kernel.org/filesystems/ramfs-rootfs-initramfs.html)

持久根通常放在 SD、eMMC 等介质上，保存程序、配置、日志和服务定义。想让 SSH 或业务程序开机自动出现，需要把**程序及依赖、配置、init 能识别的启动项**一起放进这份根；在板上手动敲一次命令，只改变当前运行状态。发行版镜像和 BusyBox 最小根都遵循这条原则，但所用 init 与服务管理方式不同。先看根里实际采用的是 systemd、BusyBox init 还是其他实现，再写对应的启动配置。

选择根文件系统也看目标。BusyBox 最小根文件少、便于先验证启动链和做单用途设备，但包管理、服务管理和诊断工具需要自己安排；Debian/Ubuntu 一类发行版根提供更完整的用户空间，代价是体积、依赖与启动服务更多。Buildroot 可用于构建可重复的精简系统，厂商 SDK 也可能给出已经配好的根。它们是**取得根文件系统的不同方式**，不是四种互不兼容的 Linux 内核。先确定板子需要哪些应用与维护能力，再选根的制作方式；无论哪种，内核与根中的模块、ABI、init 都要配套。

`No working init found` 类错误说明内核已经走到执行用户空间的阶段，但 init 可能不存在、架构不对、解释器或动态库缺失，也可能根分区/文件系统选错；不能只靠一句错误就认定必须重编内核。[Linux 内核：定位 init 无法执行](https://docs.kernel.org/admin-guide/init.html)

### 6.2 模块和应用与根的版本关系

内核模块通常安装到根文件系统的 `/lib/modules/<内核版本>/`。更新内核镜像后，检查板上 `uname -r` 是否与该目录及模块构建版本一致。用户程序若动态链接，也要在根里有适合 AArch64 的加载器和动态库。根分区能挂上而程序报“找不到文件”，有时缺的不是程序本身，而是它声明的解释器或动态加载器。

因此制作镜像时，把“内核、DTB、模块、根文件系统”作为同一次交付来记录。采用板厂整卡打包工具时，工具只是按板卡规定布局组合已有产物；不会自动替你补齐模块、应用依赖或开机服务。

## 7 按启动现象定位当前卡在哪层

以下现象是**排查入口**，不是一条日志对应唯一原因。串口电平、线序或波特率不对时，即使系统实际继续运行，也可能看不到任何字。

| 板上现象 | 已经能确认什么 | 下一步优先查什么 |
| --- | --- | --- |
| 串口全无输出 | 尚不能确定停在何处 | 串口接法和参数、启动介质/拨码、板厂烧录方式 |
| 有 DDR/早期固件信息，未见 U-Boot | 早期代码至少运行过 | 后续镜像位置、格式、DDR/固件组合、串口切换 |
| 有 U-Boot 提示符，内核无输出 | U-Boot 已运行 | 加载的 `Image`/DTB、启动命令、`console=`、内存地址 |
| 有 `Linux version`，根挂载失败 | 内核已执行 | `root=`、存储驱动、分区、文件系统支持、initramfs |
| 根已挂载，init 启动失败 | 内核已找到一份根 | init 路径、权限、架构、解释器和动态库 |
| shell 已出现，但底板外设无效 | 启动链和基本用户空间已通 | 该外设的供电、设备树、驱动绑定和功能测试 |
| 手动配置后有效，重启又失效 | 运行时功能可用 | 根里的持久配置与服务启动项 |

定位时先保留**串口完整启动日志**，记录最后成功的阶段和第一条相关错误。`Starting kernel ...` 后无字可能是控制台参数错误，不能直接断言内核死机；`/dev` 中缺少节点，也可能是设备根本未绑定，不能直接通过手工创建节点解决。

### 7.1 例子：U-Boot 能启动，随后找不到根

假设串口依次出现 U-Boot、`Starting kernel ...`、`Linux version`，最后报无法挂载根。前两级已经把控制权交给 Linux，因此先不动 DDR loader。接下来逐项核对：

1. 看 `/proc/cmdline`（若能进入 initramfs）或串口早期日志中的 `root=`，确认它指向**实际启动卡的根分区**。板子同时插了 SD 和 eMMC 时，固定写死的设备编号尤其容易指错。
2. 看内核日志里有没有 SD/eMMC 控制器和块设备、有没有分区表。没有块设备，就回到控制器驱动、供电、设备树和引脚；有块设备但没有预期分区，就看镜像布局与刷写结果。
3. 分区存在后再看根文件系统类型。内核是否在挂根前具备 ext4 等驱动？若根由 initramfs 寻找，initramfs 是否包含必要模块与脚本？
4. 根已经挂上但报 init 无法执行，则检查根里的 init 路径、架构、执行权限、解释器和动态库，不再把它当作“内核没跑起来”。

同一个“没有登录提示”横跨好几层；完整日志中的**最后一个已成功事件**，比故障表面更能决定下一步操作。

### 7.2 例子：shell 已出现，但新底板网口不通

这时启动链和根已基本可用，重点转到板级硬件。先用 `ip link` 看有无网络接口；没有接口，查 MAC 设备树节点、驱动和探测日志。有接口而链路一直 down，查 PHY 的供电、复位、MDIO 地址、`phy-mode`、连接线和对端；链路 up 却无法通信，再查 IP 地址、路由与用户空间网络配置。三个现象对应**驱动创建接口、物理链路建立、网络参数正确**三个不同检查点。只因为 `ping` 失败就重编整个根文件系统，往往会错过真正的原因。

## 8 一块板怎样才算移植完成

按照由下到上的顺序验收：

1. **可重复启动**：断电重启后，BootROM、加载器、U-Boot 能稳定把同一组内核与板级 DTB 启动起来。
2. **内核识别板子**：串口与启动存储可靠；运行中的设备树与原理图对应，必需的控制器和驱动已绑定。
3. **用户空间可用**：根挂载在 `/`，init、shell 和必要的库能运行；`uname -r` 与模块目录对应。
4. **底板功能完成**：按目标逐项做功能测试，如 RTC 时间读回、网口传包、摄像头出帧；设备“出现”只是中途证据。
5. **结果可复现**：保存源码版本、配置、DTB、模块、镜像布局和验证日志；用交付镜像冷启动，而不是依赖开发时手工执行的临时命令。

若之后只增加一颗传感器，通常从第 2、4 项的设备树和驱动工作继续，不必重做 DDR 初始化。若换了启动存储或 DDR，则要回到第 1 项。**移植的核心能力，是依据变化范围与启动证据，知道该回到哪一层修改。**

交付时可以留下一份简短的“板卡事实表”：硬件版本、启动介质、DDR/引导方案、内核与 DTB 版本、根文件系统位置、主要驱动配置，以及 RTC、网口、摄像头等目标功能各自的验证结果。下一次换底板或升级内核时，先与这份表比较变化，再决定从启动链的哪一级继续，而不是重新猜一遍整台系统。
